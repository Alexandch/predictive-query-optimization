# Predictive Query Optimization

Десктопная система анализа и оптимизации SQL-запросов PostgreSQL. Версия
`0.8.23` адаптивно оценивает время выполнения, проверяет индексные и структурные
оптимизации на реальной БД и не применяет изменения без явного подтверждения.

Проект написан на Python 3.11+, интерфейс реализован на PyQt6. Для доступа к
PostgreSQL используется `psycopg`; ORM в проекте нет, поскольку анализатору
необходимы исходный SQL, `EXPLAIN` и системные каталоги СУБД.

## Возможности

Глубокий анализ теперь пробует до трёх индексных кандидатов по рейтингу
на шаг: отказ или тайм-аут первого не останавливает всю проверку. Каждая
отклонённая проба откатывается до следующей; принятый план тоже откатывается
по завершении теста. В интерфейсе видны проверенные варианты и причины
отказа. [Протокол и пример](docs/index-candidate-retry.md).

Улучшены индексные кандидаты: равенства перед диапазоном, альтернативы для
фильтра/сортировки, ORDER BY без WHERE. Проверка существующих индексов
учитывает INCLUDE и не считает частичный, выраженческий или неподходящий
индекс безусловной заменой. В принятом плане показываются пересечение,
ключи/payload, размер, построение и ограничения оценки цены записи.
[Протокол, пример и издержки](docs/index-candidate-tradeoffs.md).

Переписывание фильтрующих JOIN расширено на цепочки INNER JOIN: они
переносятся в один общий EXISTS с сохранением связей дочерних таблиц и
внешнего DISTINCT. Проверка EXCEPT ALL выполняется последовательно в
двух направлениях, снижая пиковую нагрузку. Есть пример с подтверждённым
ускорением и примеры, корректно отклонённые из-за замедления.
Подробнее: [переписывание SQL](docs/sql-rewrite-workflow.md).

Переписывание коррелированных агрегатов расширено на составные ключи и
COUNT(DISTINCT column). Сохраняются все условия связи, NULL и дубликаты;
COUNT DISTINCT по кортежам и произвольные выражения пропускаются.
Пример: `examples/aviation-composite-distinct-rewrite.sql`.

Добавлен кандидат переписывания нескольких коррелированных SUM/COUNT/AVG
над одним источником в одну общую группировку и LEFT JOIN. Разные фильтры
и ключи не смешиваются; сохраняются NULL, нулевые COUNT и дубликаты родителей.
Старый вариант с отдельными группировками также проверяется; применение
доступно только после проверки результатов и фактического выигрыша.
[Ограничения и пример](docs/sql-rewrite-workflow.md).

Проведены два дополнительных этапа обучения на процентилях, DISTINCT и
окнах: 66 SQL для расширения данных и ещё 24 для нового контроля объединённых
признаков plan-v2. Убедительного улучшения относительно текущей тестовой
модели не получено, новые веса не подключены. Контроли и пользовательские
примеры остаются вне обучения. [Протокол и отрицательные результаты](docs/ordered-training.md).

Для тестовой приёмки подключена отдельная XGBoost plan-v1 с признаками
потоков плана: на 24 внешних контрольных SQL MAE составила 332 мс против
609 мс у основных весов. Проверка ограничена локальными aviation/retail.
Основные веса сохранены; в настройках можно вернуть прежнюю модель.
Быстрый прогноз не выполняет SQL, старые калибровки с новыми весами не смешиваются.
[Результаты и безопасный откат](docs/heavy-fresh-training.md).

Добавлен групповой XGBRanker (`rank:pairwise`) с явным NOOP, разделением
train/internal validation/final и запретом финальных измерений до прохождения
валидации. На 30 внутренних validation-SQL нашёл все 8 полезных вариантов
против 6 у стоимости плана, но статистический gate пока не пройден;
модель не активировалась. [Протокол и ограничения](docs/rewrite-pairwise-experiment.md).

Проверен выбор среди 2–3 переписываний одного SQL: 57 контрольных запросов,
152 кандидата. Замороженная модель не превзошла простую стоимость плана
(нашла 3 полезных варианта против 9), поэтому ранжирование в приложение
не подключено. [Протокол и отрицательный результат](docs/rewrite-ranking-experiment.md).

Проведён первый отдельный эксперимент обучения оценки ускорения переписываний:
621 пара, 69 семейств в пяти схемах; контрольный MAE в логарифмической шкале
снизился с 0,760 до 0,349 относительно оценки по правилам. Модель сохранена
как офлайн-кандидат, в приложение не подключена; это ещё не проверенный ранжировщик.
[Протокол, ограничения и артефакты](docs/rewrite-efficiency-experiment.md).

В 0.8.23 добавлены два конкретных преобразования сложных SQL: коррелированный
агрегат в проекции → предварительная группировка с LEFT JOIN; DISTINCT над
фильтрующим INNER JOIN → EXISTS с сохранением DISTINCT. COUNT сохраняет ноль
при отсутствии дочерних строк, остальные агрегаты — NULL. Правила ограничены
одним ключом корреляции и простыми квалифицированными выражениями; неоднозначные
случаи пропускаются. Любой кандидат проходит EXCEPT ALL и реальные замеры.
Исправлен перенос HAVING при ROLLUP/CUBE/GROUPING SETS. Подробнее и примеры:
[docs/sql-rewrite-workflow.md](docs/sql-rewrite-workflow.md).

Добавлен пакетный read-only сбор пар SQL по реальным внешним ключам:
девять правил, ограничение времени/числа проверок, продолжение после остановки,
журнал и заранее назначенные группы development/control. Выполнено 63 проверки
в трёх схемах; действующие модели не заменялись.
[Порядок запуска и результаты](docs/rewrite-batch.md).

Подготовлен отдельный исследовательский этап обучения оценки эффективности
переписываний: аудит локального журнала, явный выбор development/control,
проверка утечек между семействами SQL и экспериментальный XGBoost для оценки
ускорения. Это пока не новый ранжировщик в приложении: он не активируется
автоматически и не меняет действующие модели. Требования к данным и команды:
[docs/rewrite-learning.md](docs/rewrite-learning.md).

В 0.8.22 добавлен локальный журнал переписываний: обе версии SQL, правило,
оценочные/фактические планы, отдельные прогоны, медианы, настройки PostgreSQL
и причины отказа. Сохраняются также ошибки, отсутствие кандидатов и неполные
проверки; отсутствующее время не заменяется нулём. Просмотр и JSON/CSV-экспорт —
во вкладке «История», независимо от служебной схемы pqo. Отдельная галочка
под правым редактором отключает локальное сохранение. SQL содержит литералы:
перед экспортом проверьте, нет ли в нём чувствительных данных.
Записи не включаются в обучение автоматически; тестовые проверки помечены
отдельно. Журнал входит в архив пользовательских артефактов существующего
резервного копирования. Подробности: [docs/rewrite-journal.md](docs/rewrite-journal.md).

В 0.8.21 исходный SQL и вариант отображаются рядом в двух редакторах. Вариант
автоматически заполняется при проверке переписывания; его можно изменить и
отдельно сравнить с исходным через «Проверить вариант и измерить оба SQL».
Исходный текст при сравнении не заменяется. Проверка выполняется в read-only
REPEATABLE READ-транзакции: EXCEPT ALL сравнивает мультимножества на текущем
снимке, затем измеряются медианы обоих вариантов. Это не универсальное
доказательство эквивалентности и не проверка порядка строк.
После редактирования прежнее разрешение на применение теряет силу.
Генератор использует девять правил, в том числе NOT EXISTS и проверку
NOT MATERIALIZED для повторного CTE. Отказ теперь различает отсутствие
кандидатов, разные результаты, ошибки проверки и недостаточный выигрыш.
Примеры и ограничения: [docs/sql-rewrite-workflow.md](docs/sql-rewrite-workflow.md).

В 0.8.20 быстрый анализ полностью исключает импорт PyTorch, включая чтение
метаданных и весов: одиночный DQN использует `.npz` рядом с `.pt`.
SHA-256 исходных весов проверяется, чтобы не использовать устаревший экспорт.
Обучение автоматически создаёт оба файла; для прежних внешних моделей нужен
явный экспорт через `pqo.dqn.export_dqn_numpy_artifact(path)`.
Фоновые задачи запускаются в потоках Python, а результат передаётся в основной
поток окна через сигналы Qt. Закрытие окна блокируется до завершения задач.
`PQO_SMOKE_RUNS` задаёт число последовательных анализов для `--quick-smoke-test`;
режим также проверяет, что PyTorch действительно не был импортирован.

Обычный анализ не выполняет пользовательский SQL. Он получает оценочный
план, собирает признаки структуры SQL, кардинальностей, стоимости плана и
статистики БД, после чего XGBoost выдаёт прогноз. Реальные `EXPLAIN ANALYZE`
оставлены для явно запускаемой калибровки и фактической проверки оптимизаций.

Прогноз появляется до завершения расчёта индексных рекомендаций. В строке
состояния отдельно показана длительность расчёта прогноза и всего анализа;
это не время выполнения SQL. При запуске приложения модели загружаются
в фоне. Кэш моделей обновляется при замене файла, а признаки индексных
кандидатов используют общий разобранный SQL.

В версии 0.8.18 основной XGBoost заменён кандидатом `sql-v2`: добавлены признаки
CTE, оконных функций, DISTINCT-агрегатов и FILTER. На восьми новых SQL из
отложенных семейств MAE без калибровки снизилась с 371,60 до 118,41 мс.
Это небольшой эксперимент, а не гарантия точности на любой БД.
Протокол, ограничения и сравнение с прежней моделью:
[docs/window-cte-development.md](docs/window-cte-development.md).
Оценка из истории конкретного SQL теперь явно подписана как результат
предыдущих измерений, а не как самостоятельный ML-прогноз. Профили привязаны
к весам модели: прежние файлы сохраняются, но к новым весам не применяются.

Фактический совет принимается только при одновременном выполнении трёх условий:
исходное время не ниже пользовательского порога, абсолютная экономия не меньше
`5 мс` и относительный выигрыш не меньше `5%`. Значения настраиваются в интерфейсе.

Интерфейс разделяет уровни доказательности. Вероятности `NOOP/INDEX/REWRITE` —
только предварительная ML-навигация. Проверенный глубоким анализом индекс имеет
приоритет над предварительным `NOOP`. Структурные советы по JOIN, агрегациям,
сортировкам и materialized view показываются отдельно в общем анализе и не
примешиваются к результам глубокой индексной проверки или проверки переписывания.

## Безопасность экспериментов

При глубоком анализе выполняются один прогрев и пять контрольных замеров.
Кнопка «Отменить анализ» прерывает выполняющийся SQL; управление возвращается
после отката транзакции. Ожидание блокировок ограничено пятью секундами
(или меньшим заданным лимитом SQL). Тайм-аут исходного замера отображается
как нижняя граница, не добавляется в калибровку и не записывается как точное
время выполнения. Признак сохраняется в истории и CSV/JSON-экспорте.
Служебная таблица `pqo.sequential_analysis` обновляется при первом сохранении;
для отдельного обновления существующей БД предусмотрен скрипт
`database/init/009_sequential_measurement_status.sql`.

Система принимает только один `SELECT` или `WITH`-запрос. Пробные индексы,
переписывания, локальный `work_mem` и тестовые materialized view проверяются в
изолированной транзакции. В конце выполняется `ROLLBACK`; база пользователя не
изменяется. Команда DDL выводится только как рекомендация для осознанного
применения администратором.

## Быстрый запуск из исходников

Требуются Python 3.11+ и Docker Desktop.

```powershell
Copy-Item .env.example .env
docker compose up -d --wait
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\pqo-desktop.exe
```

Тестовая PostgreSQL 17 доступна на `localhost:55432`; стандартные логин, пароль
и база указаны в `.env.example`. При первом создании Docker volume автоматически
загружаются схемы `aviation`, `retail`, `logistics`, `chbenchmark`, `pagila` и
служебная схема `pqo`.

Для подключения своей БД откройте «Настройки», задайте host, port, database,
user, password и разрешённые схемы, затем проверьте соединение. У пользователя
PostgreSQL должны быть права на чтение таблиц, планов и каталогов. Для глубоких
проверок нужны права на временное создание индекса или materialized view внутри
откатываемой транзакции.

## Итоговый эксперимент

Финальная оценка не переобучает модели и не изменяет запечатанные контрольные
наборы. Она объединяет независимые результаты XGBoost/DQN и выполняет пять
повторов поддерживаемых структурных проверок:

```powershell
docker compose up -d --wait
.\.venv\Scripts\python.exe -m pqo.final_experiment_cli --repetitions 5
```

Текущий прогон подтвердил две из трёх автоматически измеренных рекомендаций:

| Сценарий | До, мс | После, мс | Результат |
|---|---:|---:|---|
| Перенос фильтра `HAVING` | 24,140 | 24,584 | отклонён: ускорения нет |
| Удаление внутреннего `ORDER BY` | 72,004 | 13,510 | подтверждён, −81,2% |
| Чтение materialized view | 514,106 | 0,012 | подтверждено; создание 442,819 мс |

Materialized view ускоряет повторное чтение готовой сводки, но требует затрат на
`REFRESH` и допустимой задержки данных. Поэтому результат нельзя трактовать как
ускорение одноразового запроса. Все пробные объекты итогового прогона откатились.

Полный отчёт: [docs/final-experiment.md](docs/final-experiment.md). Машиночитаемые
результаты находятся в `models/final_experiment`.

## Зафиксированные метрики моделей

Таблица ниже содержит исторические результаты прежнего XGBoost
(`737acd01…`), а не внешнюю оценку новых весов `sql-v2`. Для текущей модели
внутренние MAE составляют 13,75 мс (parameter) и 34,58 мс (unseen-template);
из-за изменения обучающего набора внутренние разбиения не полностью совпадают.
Запечатанные logistics/CH-контроли на новой модели в этом этапе не оценивались.

| Модель и контроль | Основной результат |
|---|---:|
| XGBoost, parameter holdout | `R² = 0,9701`, `MAE = 14,18 мс` |
| XGBoost, неизвестные шаблоны | `R² = 0,7761`, `MAE = 47,75 мс` |
| XGBoost, исключённая logistics | `R² = 0,8636`, `MAE = 114,85 мс` |
| XGBoost, внешний CH-benCHmark | `R² = −0,6772`, `MAE = 188,56 мс` |
| DQN, внутренний test | accuracy `56,10%`, regret `0,0749` |
| DQN, logistics control | accuracy `50,00%`, regret `0,0603` |
| Последовательная DQN | accuracy `68,73%` против STOP `64,82%` |

Внешний CH-контроль показывает ожидаемое ограничение: абсолютное время новой БД
нельзя надёжно предсказывать без локальных измерений и калибровки. Поэтому
приложение не выдаёт прогноз за фактическое время и подтверждает оптимизации
реальными замерами.

## Структура проекта

```text
src/pqo/              Python-логика, модели и PyQt6-интерфейс
database/init/        схема pqo, функции, триггеры и учебные БД
dataset/postgresql/   зафиксированные обучающие и контрольные наборы
models/               выбранные модели и проверяемые метрики
tests/                модульные и PostgreSQL-интеграционные тесты
docs/                 техническая и экспериментальная документация
scripts/              сборка, проверка и резервное копирование
packaging/            конфигурация Windows-установщика
```

Поток анализа:

```text
SQL -> EXPLAIN без ANALYZE + каталоги БД -> XGBoost -> быстрый прогноз
 |                                      |
 +-> DQN/правила -> кандидаты оптимизации
                                        |
                 явная глубокая проверка -> измерить -> применить/откатить
```

## Основные команды

```powershell
# единый анализ XGBoost + DQN
.\.venv\Scripts\pqo-analyze.exe models\xgboost\xgboost_query_time.joblib models\dqn\dqn_index_advisor.pt "SELECT ..." --threshold-ms 50

# структурные рекомендации
.\.venv\Scripts\pqo-structure.exe "SELECT ..." --analyze

# обучение XGBoost на подготовленном CSV
.\.venv\Scripts\pqo-train.exe dataset\postgresql\multidomain_training.csv artifacts\model_candidate

# полная проверка проекта
powershell -ExecutionPolicy Bypass -File scripts\verify.ps1

# сборка актуального Windows-установщика
powershell -ExecutionPolicy Bypass -File scripts\build_windows.ps1
```

Новые модели сначала сохраняются как кандидаты. Контрольные наборы нельзя
добавлять в обучение: иначе итоговая оценка перестаёт быть независимой.

Калибровка не запускается при обычном ML-прогнозе. Её выполняют заранее по
файлу характерных SQL или пополняют при явных контрольных замерах. Готовый набор из 28 запросов
находится в `examples/manual-check-queries.sql`.
