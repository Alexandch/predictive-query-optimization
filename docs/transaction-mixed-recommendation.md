# Итог для смешанной нагрузки — 0.8.36

Второй согласованный этап. Движок реально выполняет ограниченную транзакцию
с SELECT и INSERT/UPDATE/DELETE на новых копиях одного закрытого снимка.
Теперь он оценивает **весь выбранный набор из 1–2 индексов для этой нагрузки**,
а не объявляет ускорение чтений доказательством общей пользы.
Контракт SQL, доверенного лабораторного сервера, ограничения каталогов,
CREATE/DROP и проверки очистки из [первого этапа](transaction-disposable-replay.md)
не расширены. Исходная БД и эталон не получают пользовательские DML.

## Как запустить

1. Открыть `examples/transactions/university-disposable-replay.sql` во вкладке
   «Транзакции», разобрать, получить планы и собрать индексных кандидатов.
2. Отметить 1–2 непокрытых кандидата. Открыть «Выполнение на копиях», указать
   отдельный лабораторный эталон, например `pqo_university_index_lab`.
3. Оставить две серии (по умолчанию). Указать до запуска минимальный общий
   выигрыш: по умолчанию 5 мс **и** 5%, бюджет новых индексов — 64 МиБ.
4. Явно разрешить CREATE/DROP одноразовых БД, проверить сервер/источник/эталон
   в дополнительном подтверждении. Production-сервер не использовать.
5. Прочитать итог, причины, таблицу фаз и таблицу эффекта. Положительное
   число означает ускорение, отрицательное — замедление. Для каждой команды
   доступны отдельные показатели; справа — также показатели каждой серии.

Для двух серий создаются семь БД: закрытый снимок и шесть свежих A1/B/A2.
Каждая команда выполняется ровно один раз в своём месте каждой транзакции;
клиентский BEGIN–COMMIT включает передачу результата, контрольные хеши,
настройку тайм-аутов и служебные проверки. SELECT/DML — execute+fetch,
поэтому их сумма не равна общему интервалу. Клонирование, построение индексов
и полное чтение снимков данных в клиентский интервал не входят.

## Зафиксированная политика

Перед первым подключением политика валидируется и связывается SHA-256 с
эффективным SQL (включая подставленные параметры), контекстом подключения/
разрешённых схем/тайм-аутов, эталоном, набором индексов и числом серий.
Пароль и исходный SQL не сериализуются в этой привязке. Это контроль
устаревания результатов, не криптографическая авторизация внешнего отчёта.
Изменение любого поля/параметра/набора/порогов сбрасывает вывод и требует новой
пробы; запоздалый callback не присоединяется к изменённому контексту.

Решение консервативное, по инженерным порогам, не статистический доверительный
интервал. База каждой метрики в серии — среднее A1 и A2. Сравнивается B.

- нужны минимум две полные серии с теми же командами/индексами;
- в каждой серии общий клиентский выигрыш должен быть положительным и
  достигать обоих заданных порогов; неудачная серия не усредняется с удачной;
- регрессия суммарных SELECT, DML или любой отдельной команды более 2 мс
  **и** более 10% блокирует рекомендацию, даже если общий прогон ускорился;
- дрейф A1/A2 любой метрики более 2 мс **и** более 20% блокирует вывод;
- те же пороги нестабильности проверяются между сериями отдельно для базовых
  и индексных времён; это относится и к отдельным командам;
- максимум размера новых индексов до и после COMMIT не должен превышать
  зафиксированный бюджет; рост от записи учитывается;
- необходимы полные совпадения исходных состояний, результатов SELECT/RETURNING,
  затронутых строк и итоговых данных, а также отдельное подтверждение удаления
  всех созданных БД. Эти условия проверяются повторно, не только по флагу успеха.

Итоги: `recommended` — набор прошёл все условия для измеренного сценария;
`not_recommended` — стабильные полные замеры не подтвердили общий выигрыш,
обнаружили регрессию или превышение размера; `inconclusive` — одна серия,
дрейф, ошибка/отмена, неполные/некорректные данные либо неподтверждённая очистка.
При нескольких проблемах приоритет имеет «недостаточно надёжных данных»;
подробные причины сохранены. Пропуски, NaN, бесконечности и невозможные
интервалы не заменяются нулями.

Сводная таблица показывает медианы серий, а не объединённые выборки.
Решение всё равно проверяет каждую серию. Построение индекса показывается
отдельной медианой разовой стоимости: оно не вычитается из каждого прогона,
а окупаемость без заданного горизонта нагрузки не утверждается.

## Ограничения вывода

Это оценка уже выбранного набора: нет глобального оптимума, автоматического
создания постоянных индексов, доказательства использования каждого индекса
или обобщения на произвольные транзакции. Измерения включают фиксированный
порядок A1/B/A2 и прогрев чтением снимков; это не холодный кэш, production-
конкуренция или независимый mixed-holdout. Предыдущий «Контроль SELECT» не
подменяет контроль смешанной нагрузки. Повторный запуск после изучения
результата не становится исторически независимым экспериментом.

Новый режим не пополняет обучение/калибровку и не сохраняет SQL автоматически.
Журнал владения копиями содержит только контекст сервера и имена/OID/владельцев,
не данные/пароли. Очистка прежних журналов автоматически не запускается.

CLI: `python -m pqo.transaction_replay … --series 2 --minimum-gain-ms 5
--minimum-gain-percent 5 --maximum-index-mib 64` с прежним явным
`--confirm-laboratory-copy-and-disposable-databases`. JSON содержит политику,
привязку, реальные замеры, `recommendation` и причины. Exit 0 означает
корректность/очистку эксперимента, **не обязательно полезность индекса**;
признак пользы — `recommendation.status == "recommended"`.

Следующий пункт плана — переписывание отдельных SELECT в поддерживаемом
контексте транзакции, с неизменным порядком остальных команд и новой сверкой
результатов/конечных данных. В этой версии оно не реализуется.

Этот следующий пункт добавлен отдельно в 0.8.37:
[переписывание SELECT внутри транзакции](transaction-select-rewrite.md).
Текущий документ и протокол ниже описывают индексную оценку 0.8.36.

## Проверка 03.11.2026

Полный набор: 603 теста, 546 прошли, 57 opt-in сценариев пропущены без
специального разрешения. Затем все 169 тестов транзакционного блока прошли
с разрешёнными PostgreSQL-проверками, без пропусков. Отдельно проверены 16
детерминированных сценариев политики: положительный исход, общий проигрыш,
регрессия DML и отдельной команды при неизменной сумме DML, обе границы
порогов, дрейф внутри/между сериями, рост размера, неполные/повреждённые
данные, NaN/Infinity, ошибка/отмена/очистка и устаревшая привязка.
Шесть GUI-тестов включают queued worker, блокировку повторных действий,
смену политики/контекста, отрицательный итог и сброс таблицы эффекта.

Реальный queued GUI прогон исходников выполнил две серии на шести свежих
копиях закрытого снимка. Клиентские A1/B/A2: 84.426 / 39.207 / 72.384 мс и
67.854 / 41.092 / 71.644 мс. Исходные состояния, результаты команд и итоговые
данные совпали; отсутствие всех семи созданных БД подтверждено. Индекс —
10.945 МиБ, медиана построения 124.8 мс. Вывод `inconclusive`: дрейф первого
SELECT и его исходных времён между сериями, несмотря на общий выигрыш.

0.8.36 собрана и установлена: PyInstaller/Inno Setup завершили сборку,
встроенный frozen smoke прошёл, установщик вернул 0, версия в реестре и
SHA-256 установленного EXE совпали со сборкой. PowerShell-обёртка сборки
снова вернула 1 из-за native stderr warnings; успешность не предполагалась
по её коду, а проверена по `Successful compile`, установке и следующим
десяти запускам установленного EXE (все exit 0):

`--smoke-test`, `--transaction-smoke-test`, `--transaction-trial-smoke-test`,
`--transaction-comparison-smoke-test`, `--transaction-parameters-smoke-test`,

`--transaction-replay-smoke-test`, `--rewrite-smoke-test`, `--startup-smoke-test`.

В установленном GUI две серии дали 126.324 / 38.709 / 66.936 мс и
