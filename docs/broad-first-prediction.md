# Расширение обучения первого прогноза

Дата эксперимента: 27.10.2026.

Цель — улучшить прогноз для ранее не измеренного SQL, а не воспроизвести
медиану из точечной калибровки. Приложение и основные веса при запуске
эксперимента не меняются.

## Зафиксированный протокол

Новый генератор `src/pqo/broad_workload.py` содержит 48 SQL: 16 семейств
по три масштаба данных. Используются схемы aviation и retail. Добавлены
GROUPING SETS, ROLLUP/CUBE, статистические агрегаты, оконные рамки ROWS/RANGE,
процентильные ранги и повторное использование материализованных CTE.

Разбиение задано в генераторе до сбора времени:

- обучение — 8 семейств, 24 SQL;
- выбор кандидата — 4 семейства, 12 SQL;
- итоговая проверка — 4 других семейства, 12 SQL.

Варианты одного семейства не переходят между частями. Проверяется отсутствие
совпадений нормализованного SQL с базовым обучением и предыдущими контрольными
наборами. Старые контрольные SQL, пользовательские примеры и закрытые наборы
logistics/CH в обучение не добавляются. Семейство здесь определяется формой
отчёта и предметной схемой; это не проверка переноса на неизвестную БД.

База обучения — только обучающая часть предыдущего эксперимента:
`artifacts/complex-aggregation-development-v2/training.csv`. Добавляются
исключительно новые TRAIN-строки. Каждому запросу предшествует один прогрев,
затем собираются три замера; целевая величина — их медиана. Выполнение идёт
через существующий read-only EXPLAIN ANALYZE, с настроенным statement_timeout
(по умолчанию 30 секунд на оператор). Запись в служебную БД отключена.
Калибровка и история конкретного SQL не используются.

До сбора фиксируются два варианта XGBoost с прежними настройками деревьев
и балансировкой семейств: целевая переменная identity либо log1p. Кандидат
выбирается только по MAE проверочной части. Итоговая часть не участвует
в выборе или обучении; после её просмотра параметры не подбираются.
Скрипт собирает её замеры вместе с остальными, но не использует их для выбора.

Условия допуска не ослаблены: улучшение MAE и median Q-error на проверочной
и итоговой частях, регресс на 500 известных SQL не более 10%, прохождение
существующего внутреннего правила `assess_candidate`. Известные 500 SQL —
регрессионный тест, а не независимая оценка качества. Даже положительное
решение в report.json само по себе не заменяет файлы основной модели.

## Воспроизведение и аудит

```powershell
.\.venv\Scripts\python.exe scripts/complex_aggregation_experiment.py --workload broad --base artifacts/complex-aggregation-development-v2/training.csv --output artifacts/broad-first-prediction-20261027-v2
.\.venv\Scripts\python.exe scripts/audit_first_prediction.py artifacts/broad-first-prediction-20261027-v2/report.json
```

Для повторного обучения по тем же замерам предусмотрен `--reuse-measurements`;
проверяются совпадение протокола, хэшей базового датасета и основной модели.
Для нового эксперимента нужен новый каталог. Базовые CSV и артефакты локальные,
не включены в Git; одного исходного кода без них недостаточно для повторения.

`error-audit.json` дополняет report.json ошибками по семействам, числом
расхождений более чем вдвое и пятью худшими ошибками. Этот аудит не обучает
и не выбирает модель повторно. Предварительный запуск в каталоге без `-v2`
остановлен на EXPLAIN из-за отсутствующего AS перед псевдонимом даты;
измерения и обучение в нём не запускались. Исправлен только синтаксис,
состав семейств и разбиение сохранены.

## Полученные результаты

Все 48 SQL прошли PostgreSQL EXPLAIN, собраны 144 измерения. В расширенном
обучающем CSV 14 000 строк замеров и 6 554 уникальных SQL. Два кандидата
сохранены отдельно в `artifacts/broad-first-prediction-20261027-v2/`.
По заранее выбранному критерию validation MAE победил вариант identity.

На проверочных 12 SQL:

- MAE основной модели — 525,01 мс, выбранного кандидата — 265,32 мс;
- median Q-error — 1,478 и 1,330 соответственно;
- доля ошибок не более 20% — 16,7% и 33,3%.

На итоговых 12 SQL:

- MAE — 679,63 → 761,19 мс, ухудшение примерно на 12%;
- median Q-error — 1,210 → 1,246;
- доля ошибок не более 20% — 50% → 41,7%;
- число расхождений более чем вдвое осталось равным трём.

На 500 известных SQL MAE немного улучшилась: 14,74 → 14,26 мс. Однако
итоговые критерии не выполнены; внутреннее правило также отклонило
кандидата из-за ухудшения parameter-holdout R². `promotion_allowed=false`,
`primary_replaced=false`. Хэш основной модели остался
`2543cde0e5084621951bcff9d77ea4e2a1f33f70f994cce1af8dddd2aea08080`.

### Что показал аудит

Для итогового авиационного CUBE MAE уменьшилась с 1874,14 до 1626,36 мс,
а для месячного RANGE — с 483,02 до 225,04 мс. Но розничный ROLLUP по
покупателю ухудшился с 316,93 до 1129,89 мс; именно поэтому общий результат
не подтверждает улучшения. Самый тяжёлый CUBE занимает 7472 мс, тогда как
оба варианта модели дают около 3 секунд.

Вывод: расширение набора само по себе не обеспечило устойчивого улучшения
первого прогноза. Следующая проверяемая гипотеза — признаки типа и количества
группирующих наборов, ordered-set агрегатов и оконных рамок. Сейчас sql-v2
не различает эти конструкции достаточно подробно. Это гипотеза по итогам
диагностики, а не доказанная причина ошибок. Для её оценки нужен новый
протокол и новый итоговый контроль; просмотренную часть нельзя повторно
использовать для подбора параметров как независимую проверку.

## Ограничения

Четыре итоговых семейства — всё ещё небольшая проверка. Время зависит от
кэша, нагрузки и окружения; три повтора не устраняют эту вариативность.
Полученные результаты не означают точного прогноза для любого запроса
и не распространяются автоматически на другие серверы PostgreSQL.
