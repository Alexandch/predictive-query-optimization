# Сценарная нагрузка от индексов при записи — 0.8.34

## Что добавлено

«Транзакции» → «Запись и индексы» связывает набор новых индексов с явными
командами записи, пересечениями SET с ключами/INCLUDE и пользовательским
сценарием повторений/затронутых строк. Это не новый замер DML и не модель
времени записи. По уже полученным планам и метаданным расчёт выполняется
локально, без нового подключения, пользовательского SQL, DDL, записи в историю
или обучения. Получение исходных планов/каталогов остаётся отдельным действием.

В отличие от прежних качественных предупреждений теперь можно сравнить
масштаб прямой нагрузки одного индекса/пары/трёх кандидатов, увидеть отдельное
влияние INCLUDE на UPDATE, поставить свой структурный лимит и сопоставить
результат с отдельным фактическим замером SELECT того же варианта.

## Как попробовать на синтетическом примере

1. Открыть `examples/transactions/university-shared-index.sql`, разобрать,
   получить оценочные планы и собрать кандидатов. Пользовательские команды
   не выполняются; для реальной рабочей системы используйте тестовую копию.
2. Отметить кандидат `enrollments(student_id)` с INCLUDE, содержащим `status`.
   Перейти во внутреннюю вкладку «Запись и индексы» (при нехватке ширины — стрелки).
3. В источнике набора выбрать «Отмеченные кандидаты, включая DML».
   Альтернатива — выбранная строка ранее измеренного сравнения: тогда рядом
   с оценкой записи показывается именно её замер SELECT, веса и размер индексов.
4. Для DML №3 (UPDATE) явно ввести 10 повторов и 100 строк за вызов; для №4
   (INSERT) — 50 и 1; для №5 (DELETE) — 2 и 100. Это условные допущения примера,
   не считанные фактические строки и не скрытые значения по умолчанию.
5. Задать сценарный лимит 1000 и нажать «Оценить запись без выполнения».
   Для одного индекса известная экспозиция составит 1250: 1000 + 50 + 200.
   Лимит превышен, хотя это не утверждение о превышении времени/ресурса PostgreSQL.
6. Сравнить с тем же ведущим ключом без INCLUDE status: прямой счётчик для
   одного индекса не обязан измениться, но исчезнет пересечение SET со status
   в новом индексе. Это показывает ограничение одной скалярной метрики:
   подробная оценка HOT/состава нужна отдельно.

Чтобы оценить кандидата только для DML, отметьте его флажок. Такие флажки
доступны для структурного сценария, но по-прежнему не включают его в сравнение
SELECT и не разрешают пробу ускорения UPDATE. Покрытый существующим индексом
кандидат повторно как новый не считается.

## Единицы и допущения

Для каждой явной команды записи задаются:

- повторы 1–10000: число появлений команды в условном наборе, не частота из БД;
- строки за вызов 0–1000000000: предполагаемое число затронутых строк,
  не число возвращённых RETURNING и не автоматическая оценка планировщика;
- пустое поле строк: неизвестно, в отличие от явного 0.

Для простого INSERT/UPDATE/DELETE прямой показатель равен:

`повторы × предполагаемые строки × число новых индексов целевой таблицы`.

Единица — «строка × новый индекс», то есть структурная экспозиция. Это не
количество фактических операций B-tree, не записи WAL, не объём записанных
байтов и не миллисекунды. Вставка новой индексной записи, возможное обслуживание
при UPDATE и будущая очистка после DELETE имеют разную физическую цену.
Общий счётчик не делает их равноценными по стоимости.

Если прямой DML обращается к другой таблице, прямой показатель для выбранного
набора может быть 0; неизвестные триггеры/каскады не превращаются от этого в 0.
Для сложных записей (изменяющий CTE, MERGE, ON CONFLICT, SELECT INTO,
несколько пишущих узлов) численная экспозиция не объявляется полной даже
при введённых строках. Команды с неизвестной экспозицией перечисляются отдельно,
известная часть суммы не называется полной нагрузкой.

У простого ModifyTable с одним дочерним потоком справочно показаны Plan Rows
дочернего узла. Это оценка потока плана, не доказанное число изменённых строк;
значение корневого ModifyTable может быть 0. В формулу оно не подставляется.
Смысл оценок описан в [руководстве PostgreSQL по EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html).

## HOT, INCLUDE и неизвестные зависимости

Показываются отдельно столбцы SET, пересекающиеся с ключами и INCLUDE новых
индексов, и новые для индексации столбцы относительно известных существующих
индексов. Само присутствие столбца в SET не доказывает изменение его значения
(например, SET x=x); отчёт формулирует риск, а не измеренную потерю HOT.

Отсутствие пересечения с новым индексом не означает бесплатный UPDATE:
HOT также требует места на странице, а при не-HOT обновлении обслуживание
обычных индексов может понадобиться и без изменения их собственных ключей.
Проверка консервативна; она не выдаёт вероятность будущего HOT.
Основание: [PostgreSQL 17, Heap-Only Tuples](https://www.postgresql.org/docs/17/storage-hot.html).

Если известный столбец уже участвует в существующем индексе, новый индекс не
объявляется причиной первого ограничения HOT по этому столбцу. Если присутствуют
неподдержанные существующие индексы/выражения/частичные предикаты, генерируемые
столбцы, триггеры, правила, секции или неполные метаданные, новый набор зависимостей
не считается установленным. Даже простой BRIN либо нестандартные опции могут
дать консервативное «неизвестно»: приложение не объявляет их автоматически
блокирующими HOT. Описанные в PostgreSQL исключения для суммаризующих индексов
не заменяются неверным общим запретом.

Накопленная доля HOT показывается только при сопоставимых счётчиках
0 ≤ n_tup_hot_upd ≤ n_tup_upd и n_tup_upd > 0. Это история таблицы,
не частота операций текущего набора и не коэффициент для умножения нагрузки.
Ширина данных/байты INCLUDE не оцениваются по одному числу столбцов;
[документация CREATE INDEX](https://www.postgresql.org/docs/17/sql-createindex.html)
описывает дополнительные ограничения и влияние INCLUDE на размер/дедупликацию.

## Каталоги и неполный охват

При прежнем чтении метаданных дополнительно получаются тип отношения,
генерируемые столбцы, признаки пользовательских триггеров/правил/потомков,
входящие FK с CASCADE/SET NULL/SET DEFAULT для UPDATE/DELETE. Это SELECT
каталогов, не выполнение функций триггеров. Метаданные сохраняются и для
таблиц без собственных кандидатов, чтобы не терять побочную запись в другом
целевом отношении. Неустановленный флаг не трактуется как доказанное отсутствие.

Триггеры, правила, наследование/секции, возможные каскады, неизвестные функции,
усечённый каталог или неподдержанный контекст делают структурный охват
неполным. Каскадный флаг консервативный: он не означает, что конкретный UPDATE
действительно изменит ссылочный ключ. Сами каскады/триггеры/целостность не
воспроизводятся и не оцениваются по времени.

Источники полей: [pg_trigger](https://www.postgresql.org/docs/17/catalog-pg-trigger.html),
[pg_constraint](https://www.postgresql.org/docs/17/catalog-pg-constraint.html),
[pg_attribute](https://www.postgresql.org/docs/17/catalog-pg-attribute.html).

## Сценарный лимит и измеренные чтения

Лимит задаётся пользователем: целое 0–1000000000000000 либо пустое поле.
Это не системный/обученный порог безопасности или пригодности индекса.

- известная часть уже больше лимита — «сценарный лимит превышен», даже если остаток неизвестен;
- все прямые показатели известны и охват полный — «в пределах заданного сценарного лимита»;
- есть неизвестные строки/сложность/побочные операции — «данных недостаточно»;
- пустой лимит — «не задан», а не бесконечный безопасный бюджет.

Строка сравнения должна иметь полный измеренный срез SELECT, подтверждённый
откат и тот же состав индексов/SQL/контекст. Замер может быть с отрицательным
выводом: он так и показывается, не становится рекомендацией. Вариант из одной
серии не называется устойчивым. Три отмеченных кандидата не наследуют замер пары.

Выигрыш SELECT в миллисекундах и структурный счётчик записи имеют разные
единицы, поэтому **чистый выигрыш транзакции не вычисляется**. Лимит и оценка
не меняют предпочтение сравнения, контрольный результат, решения применения,
историю или модель. Внешняя нагрузка и обслуживание существующих индексов
не охвачены. Для итогового решения нужна фактическая изолированная проверка
записи и восстановления исходного состояния — следующий режим, пока его нет.

## Интерфейс и проверки

Изменение строк/повторов/лимита/источника набора/выбранного варианта сбрасывает
только оценку записи; ранее полученные чтения не пересчитываются. Новый SQL,
привязки параметров, подключение или сбор кандидатов также сбрасывают ввод
сценария, чтобы не переносить строки на другой DML. Во время фонового локального
расчёта другие анализы заблокированы, отмена доступна, устаревший callback
не восстанавливает результат. Данные сценария живут только в памяти.

```powershell
$env:PQO_UNIVERSITY_TESTS='1'
$env:PQO_TRANSACTION_TRIAL_TESTS='1'
.venv\Scripts\python.exe -B -m unittest discover -s tests -p 'test_transaction*.py' -q
```

Проверка готового приложения `--transaction-write-smoke-test` предназначена
только для известных синтетических университетских БД. Она получает планы/
каталоги, затем проверяет локальную арифметику 1250, неизвестные строки,
пересечение INCLUDE status и отображение. DML/DDL не исполняются, временные
индексы этой проверкой не создаются. `PQO_SMOKE_PREVIEW=1` добавляет снимки UI
1740×1030 и 1280×800. Реальные тесты сравнивают строки и каталог индексов до/после.

### Нативный запуск Windows

После успешных offscreen проверок первоначальная сборка аварийно завершилась
при обычном запуске: сначала исключение COM 0x8001010d, затем access violation
во время обхода стеков фонового импорта. Сбой повторился в исходниках; отключение
WMI его не устранило. В локальном A/B отключение faulthandler позволило окну
работать; режим all_threads=False сохранил диагностику текущего потока и также
прошёл запуск/прогрев моделей. Поэтому на Windows изменён только этот режим,
а не алгоритм рекомендаций, модель или порядок выполнения SQL.

Это локально подтверждённая связь с обходом фоновых стеков, не утверждение
об универсальной причине всех сбоев CPython/Qt. Аналогичные риски многопоточного
дампа зафиксированы в [трекере CPython](https://github.com/python/cpython/issues/131580).
Журнал может содержать строку «Windows fatal exception» для first-chance
исключения, которое Windows затем обработала: одна такая строка не доказывает
завершение процесса. Успех проверяется кодом возврата, рабочим event loop,
завершением прогрева и отсутствием незавершённых задач.

Добавлены две unit-проверки режима faulthandler и `--startup-smoke-test`: обычное
окно, загрузка моделей и 20 секунд event loop без запросов. Исходный прогон с
QT_QPA_PLATFORM=windows завершился с exit 0, модели прогреты, окно видимо,
active_workers=0. Дальнейшая упаковка использует эту исправленную версию.
