# Фактическая проверка общих индексов на копии — 0.8.29

## Границы этапа

Это проверка **одного индекса для чтений** из текста транзакции, не replay
транзакции. Выполняются все допустимые самостоятельные SELECT/WITH, в том числе
чтения других таблиц. INSERT/UPDATE/DELETE и целиком изменяющие CTE пропускаются.
Изменения данных предыдущих команд не воспроизводятся. Цена записи, триггеры,
каскады, конкурентная нагрузка и итоговое время транзакции не измеряются.
Автоматического постоянного применения индексов нет.

Даже откатываемый CREATE INDEX берёт блокировки, расходует место/ресурсы и
создаёт нагрузку на общий сервер. Пробы нельзя запускать на production.
Другое имя БД и checkbox — защита от случайного выбора исходной БД, но не
доказательство того, что пользователь не указал другую рабочую БД. Достоверность
копии подтверждает пользователь. READ ONLY не является песочницей для
недоверенных функций/операторов/расширений с внешними эффектами.

## Подготовка учебной копии

Для локального университетского примера создана отдельная БД
`pqo_university_index_lab` из `pqo_university_unseen`. Для нового развёртывания:

```powershell
.venv\Scripts\python.exe -B -m pqo.transaction_index_trial create-university-lab
```

Команда создаёт только эту именованную копию учебной БД, не перезаписывает
существующую, не выполняет DROP и не завершает чужие подключения. Нужны CREATEDB
и доступ к исходной учебной БД. Активные подключения к шаблону могут помешать
созданию; их нельзя принудительно обрывать ради пробы. После неудачной подготовки
не выполняется разрушительная автоматическая очистка.

Для другой предметной области копию готовит администратор отдельно. В приложении
указывается только другое имя БД на том же сервере, с тем же пользователем и
разрешёнными схемами. В строке «Настройки» оставьте исходное подключение: сама
проба заменяет имя БД только в своём подключении.

## В интерфейсе

1. Открыть `examples/transactions/university-shared-index.sql` на вкладке
   «Транзакции», разобрать, получить планы и подобрать индексные кандидаты.
2. Выбрать кандидат `enrollments(student_id, registered_at)` без INCLUDE.
3. Указать `pqo_university_index_lab`, отметить подтверждение отдельной копии.
4. Нажать «Проверить выбранный индекс на копии», прочитать отдельное подтверждение.
5. В разделе «Проба на копии» посмотреть A1/B/A2, использование индекса,
   причины отказа, размер/построение и подтверждение отката.

С 0.8.29 в списке отдельно указаны SELECT и поиск внутри команд записи.
Например, `enrollments(offering_id)` в этом примере нужен структурно только
UPDATE №3. Проба SELECT для него отключена: это не измерение UPDATE и не
доказательство бесполезности индекса для записи. Само API повторно проверяет
применимость ключа к чтениям по каталогам копии до запуска SELECT/CREATE INDEX.
Совпадения имени таблицы или столбца в проекции недостаточно. Используются
те же консервативные привязки SQL-областей, что при генерации кандидатов;
CTE lineage и перемещение предикатов не угадываются.

После пробы строка и карточка выбранного индекса показывают отдельный итог
для чтений, копию, суммы медиан, причины отказа и состояние отката. Ошибка или
отмена не считается проверенным ускорением. Результаты нескольких индексов
в текущем анализе не заменяют друг друга; при выборе восстанавливается своя
проба. Это память текущего сеанса, не постоянный журнал и не дообучение.
При изменении SQL, подключения, имени копии или новом подборе кандидатов
эта привязка сбрасывается.

Пороги минимального выигрыша берутся из полей абсолютного и процентного
выигрыша на основном экране. Порог исходного времени основной одиночной
рекомендации здесь не применяется. Значения порогов и число замеров фиксируются
в результате пробы; изменение полей позже не подменяет старый результат.

Изменение SQL, основного подключения или имени копии сбрасывает соответствующие
результаты. Противоречащие операции блокируются на время работы. Отмена
прерывает SQL на сервере; завершение отображается после выхода из транзакции.
Автосохранения SQL/истории/калибровки и дообучения моделей нет.

## Сравнение A/B/A

Для каждого этапа: один прогрев каждого SELECT и три замера, по очереди для
всех чтений. A1 — без нового индекса. B — с одним временным индексом. Затем
savepoint с индексом безусловно откатывается, A2 — снова без него.

Для базовой медианы объединяются шесть замеров A1 и A2. Для B берётся медиана
трёх замеров. Сумма медиан означает каждый SELECT **один раз** и не является
прогнозом/замером времени всей транзакции или частот production.

Подтверждение пользы для измеренных чтений выдаётся, только если:

- пробный индекс реально указан в одном из измеренных планов;
- сумма медиан даёт положительный выигрыш и проходит оба заданных порога;
- ни одно чтение не ухудшилось одновременно более чем на 2 мс и 10%;
- ни у одного чтения A1/A2 не разошлись одновременно более чем на 2 мс и 20%;
- все чтения/этапы завершились, а отсутствие пробного индекса после отката
  подтверждено отдельным подключением к копии.

При ошибке/отмене/неподтверждённом откате успешное ускорение не выдаётся.
Это наблюдение на конкретной копии, прогретом кэше и текущей нагрузке, не
гарантия той же производительности в эксплуатации. Одна проба не оценивает
комбинацию нескольких индексов и не измеряет конкурирующие записи.

## Ограничения и защита

Другая БД и явное подтверждение обязательны до подключения. Допускается 1–20
SELECT, хотя бы один имеет структурное применение ведущего ключа кандидата
в прямом условии/соединении или начале ORDER BY. Для повторной привязки
допускается не более 64 таблиц чтений. Сессионные команды/DDL из
пользовательского текста не исполняются и блокируют пробу. Параметры без
значений, неизвестные функции, SELECT INTO и блокировки строк не допускаются.
Кандидат проверяется повторно по столбцам/индексам **копии**; существующее
покрытие приводит к отказу от создания дубликата. Пока поддерживаются обычные
таблицы, не секционированные.

У каждого SELECT-фрагмента — rollback-only savepoint и READ ONLY. Родительская
транзакция нужна только для собственного CREATE INDEX и также обязательно
откатывается. DML из исходного текста туда не отправляется. Пробное имя
`pqo_tx_trial_<случайный идентификатор>` уникально; чужие индексы не удаляются.
После отката отдельное read-only подключение проверяет отсутствие этого имени.
При неуспехе проверки показывается имя индекса, но автоматического DROP нет.

Общий бюджет — 120 с, statement_timeout — не более 30 с и остатка бюджета,
lock_timeout — 1 с. Одна проба на копию защищена advisory lock. Размер индекса
проверяется после построения: 64 МиБ — порог отказа, не обещание заранее
ограниченного расхода диска. Копия должна иметь достаточно свободного места.

Источники поведения СУБД:
[EXPLAIN ANALYZE действительно выполняет запрос](https://www.postgresql.org/docs/17/sql-explain.html),
[блокировки CREATE INDEX](https://www.postgresql.org/docs/17/sql-createindex.html),
[копирование через CREATE DATABASE TEMPLATE](https://www.postgresql.org/docs/17/sql-createdatabase.html).

## Проверка на учебном примере

На первой пробе `enrollments(student_id, registered_at)` сумма медиан двух
SELECT составила 25,184 → 0,187 мс. Индекс использован обоими чтениями,
построение около 176 мс, размер около 7,23 МиБ. Три команды записи пропущены.
Это единичный прогон, не финальная оценка стабильной производительности.

Автотест дополнительно включает чтение students по PK и проверяет, что оно
не исключено из набора замеров. Проверяются строки enrollments студента 17001
и полный каталог индексов university в исходной БД и копии до/после. Отдельный
тест отменяет пробу уже после реального создания индекса и подтверждает его
отсутствие. Контроль регрессии/дрейфа проверяется также детерминированными тестами.

```powershell
$env:PQO_UNIVERSITY_TESTS='1'
$env:PQO_TRANSACTION_TRIAL_TESTS='1'
.venv\Scripts\python.exe -B -m unittest discover -s tests -p 'test_transaction*.py' -q
```
