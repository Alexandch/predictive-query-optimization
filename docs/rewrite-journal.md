# Локальный журнал проверок переписывания

Версия 0.8.22. Модели и обучающие наборы на этом этапе не заменяются.

## Использование

Под правым редактором включена отдельная галочка «Сохранять проверки SQL
в локальный журнал». Она не связана с «Сохранять в историю pqo»: служебные
таблицы в пользовательской БД не нужны. Автоматическая проверка и сравнение
варианта из правого редактора записываются после запуска пользователем.
Быстрый ML-прогноз не запускает проверку переписывания и не создаёт таких записей.

Во вкладке «История» есть отдельный локальный журнал: «Обновить журнал» и
«Экспорт журнала JSON/CSV». Просмотр показывает последние 200 проверок; экспорт
охватывает все записи. SQL доступен в подсказке строки, полные планы — в JSON.
Повторное применение/возврат текста и индексные эксперименты не выдаются за
новые парные проверки переписывания и не включены в этот журнал.

Обычный путь установленного приложения:
`%LOCALAPPDATA%\PredictiveQueryOptimization\artifacts\rewrite-journal`.
При запуске исходников — `artifacts/rewrite-journal` в проекте; переменная
`PQO_APP_DATA_ROOT` переопределяет корень пользовательских данных.

## Состав записи

Одна проверка — один `run-<UTC-время>-<UUID>.json`, версия схемы 1. Отдельные
файлы образуют единый журнал в интерфейсе, не перезаписывая прошлые проверки.
Сохраняются:

- исходный SQL, все кандидаты, правило и версия генератора, автоматический
  или ручной источник;
- время начала/обновления/завершения, этап и статус;
- SHA-256 идентификатора подключения вместо открытых host/database/user;
  пароль и DSN не копируются в журнал;
- хэши точного нормализованного SQL и формы с заменёнными литералами;
- версия PostgreSQL, безопасный список настроек с единицами измерения;
- исходный пробный замер, оценочные EXPLAIN-планы, фактические планы
  прогрева и каждого замера, раздельные последовательности времени;
- результат EXCEPT ALL, медианы, выигрыш, пользовательские пороги и причины
  отказа, тип/SQLSTATE/этап ошибки и известный признак statement timeout.

Мультимножества проверяются на одном REPEATABLE READ-снимке. Это не доказательство
эквивалентности на всех возможных данных или порядка строк. Время — серверный
замер из EXPLAIN ANALYZE, не длительность записи журнала на диск.

## Отказы и качество данных

`no_candidates` не выполняет SQL, но фиксирует отсутствие вариантов. Кандидаты
ниже порога помечаются `not_checked`: это не отрицательные примеры эффективности.
Несовпадение строк, ошибка подключения, валидации или тайм-аут не получают
вымышленного нулевого времени. При аварии останется `running` с последним
успешно сохранённым этапом, а не якобы завершённый эксперимент.

`runtime_training_eligible` — только техническая полнота: совпали строки,
есть оба набора положительных конечных измерений и итоговые времена. Этот флаг
может быть true и для замедляющего/недостаточно полезного варианта — такие
примеры нужны ранжировщику. Он не разрешает автоматически обучаться на записи.
Ошибки и несовпадения можно рассматривать отдельно для классификации пригодности,
но не подставлять их в регрессию времени.

Все обычные записи имеют `dataset_role=unassigned`, тестовые запуски приложения
— `dataset_role=test`, `source=smoke_test`. Никакое обучение из журнала пока не
запускается. Перед будущим обучением нужны явное выделение development-данных,
отделение контрольных семейств/БД и повторная проверка полноты. Хэш формы помогает
группировать варианты литералов, но не заменяет ручную проверку семейств и утечек.

## Надёжность и конфиденциальность

JSON записывается во временный файл, сбрасывается на диск и атомарно заменяет
последнюю версию проверки. Параллельные операции используют разные UUID. Ошибка
записи не отменяет результат SQL-проверки: интерфейс показывает предупреждение.
Повреждённая запись отмечается отдельно и не блокирует просмотр остальных.
Автоматического удаления или ротации результатов нет.

Журнал находится внутри каталогов артефактов, уже включённых в
`scripts/backup_windows.ps1`. Временные `.rewrite-*.tmp` исключаются из ZIP;
архив содержит последнюю целую версию JSON. Если архив сделан в процессе
проверки, она может остаться незавершённой — такие данные не считаются полными.
Проверен архивный round trip на отдельном тестовом каталоге, а не выполнено
новое полное резервное копирование пользовательской БД. Для защиты от потери
диска само место резервных копий должно быть внешним/отдельным и расписание
должно работать.

Сохраняется полный SQL и фильтры из планов: они могут содержать персональные
данные и секреты в литералах. Файлы не шифруются этим механизмом. Они не
отправляются в сторонние сервисы; экспорт/резервные копии тоже следует хранить
с учётом чувствительности данных. CSV экранирует начало формул для просмотра
в таблицах, поэтому для точного исходного текста используйте JSON.

## CLI

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pqo.rewrite_journal --directory artifacts/rewrite-journal
.\.venv\Scripts\python.exe -X utf8 -m pqo.rewrite_journal --directory artifacts/rewrite-journal --export artifacts/rewrite-export.json
```

Для отдельного CLI-эксперимента у `python -m pqo.rewrite_cli` есть необязательный
`--journal-directory`. В Python API `evaluate_sql_rewrites` и
`evaluate_sql_variant` принимают `journal_directory`; по умолчанию он None,
чтобы исследовательские и контрольные сценарии не начинали скрыто писать
пользовательские данные. `journal_source` позволяет явно отметить источник.
