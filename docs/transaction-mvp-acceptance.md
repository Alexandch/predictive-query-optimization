# Сквозная приёмка транзакционного MVP

Это четвёртый согласованный этап после выполнения записи на одноразовых БД,
оценки всего смешанного сценария и замены отдельного SELECT. Проверка доступна
из исходников, не требует переобучения моделей и не меняет установленный GUI.

## Повторяемый прогон на трёх новых БД

```powershell
.\.venv\Scripts\python.exe -B -u -m pqo.transaction_acceptance `
  --output artifacts/transaction-acceptance-my-run `
  --confirm-trusted-laboratory-server
```

Параметры сервера читаются из `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`
и `POSTGRES_PASSWORD`, как в остальных CLI проекта. Пароль не передаётся в
командной строке и не записывается в протокол. Нужен доверенный **лабораторный**
сервер с правом CREATEDB; флаг не делает production безопасным. Существующий
каталог результатов не перезаписывается.

Прогон создаёт три новые БД из `template0`, а не из пользовательской БД.
Схемы retail, logistics и university содержат разные предметные имена/объёмы:
80000 заказов, 65000 отправлений и 72000 записей на обучение соответственно.
В каждой есть вторая контрольная таблица с NULL. Это **синтетические фикстуры**,
не три независимые production-базы и не контроль обобщающей способности ML.
Существующие `query_optimizer`, `pqo_university_unseen` и лабораторный эталон
этот CLI вообще не открывает. Создание/удаление фиксируется по точному
случайному имени, OID и владельцу; удаления по маске, FORCE и завершения
чужих подключений нет. Неоднозначные исходы требуют ручной проверки.

Для каждого домена выполняются четыре сценария:

- смешанная транзакция с селективными агрегатными чтениями и индексом фильтра;
- точечный поиск по уже имеющемуся PK с дублирующим индексом;
- удаление лишней внутренней сортировки SELECT после UPDATE;
- синтаксически допустимый, но неверный SELECT: пропускает изменённую UPDATE
  строку, хотя конечные таблицы остаются теми же.

Дополнительно на retail проверяются отмена после записи, ошибка уникальности
после записи, локальный отказ от неизвестной функции и каталоговый отказ при
DEFAULT. Итого 16 сценариев. Реальный `statement_timeout` после UPDATE отдельно
проверяет PostgreSQL-тест `test_transaction_replay.py`: ограничение применяется
только к следующему SELECT, чтобы исключить случайный тайм-аут подготовки.

В каждой законченной пробе две серии A1/B/A2 и семь свежих БД, включая закрытый
снимок. Каждая фаза начинает с одинаковых данных, DML выполняется по порядку
с COMMIT только в копиях. Сравниваются все результаты/RETURNING, число строк,
типы, порядок при ORDER BY и конечное состояние обеих таблиц. Исходная
фикстура дополнительно проверяется до/после по полным отпечаткам данных и
каталогу индексов. Её удаление также подтверждается отдельным подключением.

`report.json` сохраняется после каждого случая; `recovery/` содержит метаданные
владения копиями. В отчёте нет строк таблиц, текстов пользовательских запросов
или паролей. Сохраняются фиксированные параметры генератора, SHA-256 кода,
измерения каждой фазы, причины решений, контрольные хеши и результаты очистки.
При неподтверждённом удалении дальнейшие пробы немедленно прекращаются.
После прерывания не удалять все БД по префиксу: проверить точные имена и
идентичности по манифестам.

## Что означает успешная приёмка

`status=passed` означает, что пройдены проверки корректности, отрицательных
случаев и очистки. **Не означает, что все кандидаты получили рекомендацию.**
Для положительного сценария допускается `inconclusive`: шум нельзя превращать
в подтверждённое ускорение. Для дублирующего PK-индекса рекомендация запрещена;
неверный SELECT, отмена, ошибка и каталоговый отказ также не могут дать её.

Пороговая политика зафиксирована до запуска: общий выигрыш каждой серии не
меньше 5 мс **и** 5%; отказ при регрессии команды свыше 2 мс **и** 10%, дрейфе
свыше 2 мс **и** 20%; размер индексов до/после записи не больше 64 МиБ.
Построение индекса показывается отдельно. Автоповторов до удачного ответа,
удаления неудачных серий, подбора порогов по результату и обучения нет.

Код завершения 0 означает пройденные проверки; 3 — провал проверки матрицы.
Неожиданная ошибка останавливает запуск с ненулевым кодом и отдельным типом
ошибки в протоколе. Синтаксический отказ до фактической пробы не считается
измерением времени.

## Регрессия и установленный интерфейс

```powershell
# Без подключения к БД, PostgreSQL-проверки пропускаются по умолчанию
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -q

# Только на ранее подготовленном лабораторном сервере проекта
$env:PQO_UNIVERSITY_TESTS='1'
$env:PQO_TRANSACTION_TRIAL_TESTS='1'
$env:PQO_DISPOSABLE_REPLAY_TESTS='1'
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p 'test_transaction*.py' -q
```

Вторая команда использует отдельные учебные БД проекта и временные тестовые
фикстуры. Не включать эти opt-in флаги на произвольном сервере.

Для установленного EXE отдельно проверяются обычный анализ, планы транзакций,
пробы/сравнение индексов, параметры, контроль, запись, воспроизведение DML,
замена SELECT, два редактора переписывания и запуск обычного окна Windows.
Smoke-пробы используют собственный `PQO_APP_DATA_ROOT`: рабочие настройки,
история, калибровка и журнал пользователя не должны пополняться.

## Границы MVP и записка

Поддержка произвольной production-транзакции не заявляется. Последовательный
исполнитель принимает закрытый набор простых команд; JOIN/CTE/окна, функции
с побочными эффектами, триггеры, каскады, DEFAULT/identity и контексты сессии
могут требовать отказа. Планирование без выполнения и реальный replay имеют
разные ограничения, их нельзя описывать как один универсальный режим.

В записке следует отразить реальные три режима: предварительная гипотеза,
подтверждённая корректность на конкретных данных и рекомендация по измеренному
общему эффекту. Отдельно описать отказ/неопределённость, очистку, ограничения и
сценарий пользователя. Прогноз XGBoost не выдавать за фактическое время, сумму
SELECT — за время транзакции, а синтетическую приёмку — за ML-эксперимент.
Технический протокол не заменяет обновление пользовательского DOCX и схем.
