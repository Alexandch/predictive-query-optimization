## В подраздел 4.1 после алгоритма одиночного переписывания

Анализ транзакций выделен в отдельный программный путь. Локальный разбор
сохраняет порядок команд и определяет операции чтения и записи без подключения
к PostgreSQL. Получение оценочных планов выполняется отдельным действием через
EXPLAIN без ANALYZE. Команды при этом рассматриваются относительно исходного
состояния базы: последующий SELECT не видит изменений предшествующего UPDATE,
поскольку запись ещё не выполняется. Стоимость плана не интерпретируется как
время транзакции.

Фактическая проверка смешанного сценария осуществляется только на доверенном
лабораторном сервере. Приложение создаёт закрытый снимок отдельного эталона и
новые одноразовые базы для каждой фазы сравнения. В A1 и A2 выполняется исходная
транзакция, а в B – тот же набор команд с проверяемыми индексами либо с заменой
одного SELECT. Команды исполняются последовательно с COMMIT; поэтому чтения
учитывают предыдущую запись. Исходное подключение не используется для запуска
транзакции. Неподдерживаемые конструкции отклоняются до выполнения.

Корректность контролируется по совпадению начальных состояний, всех результатов
SELECT и RETURNING, количества строк и конечных данных проверяемых таблиц.
При наличии ORDER BY сравнивается последовательность строк, иначе –
мультимножество с сохранением дубликатов и NULL. Контрольные значения
представляются отпечатками SHA-256, без записи содержимого таблиц в отчёт.
Равенство конечных данных само по себе недостаточно: SELECT способен вернуть
неверный результат, не изменяя таблицы. Проверка относится к конкретным данным,
а не доказывает эквивалентность для любых возможных состояний базы.

Итоговое решение учитывает общее время BEGIN–COMMIT, время чтения и записи,
регрессии отдельных команд, размер индексов до и после DML и нестабильность
измерений. Стоимость построения сообщается отдельно. Для рекомендации нужны
две полные серии и прохождение абсолютного и относительного порогов в каждой.
Ошибка, отмена, различие результатов, неполная серия или неподтверждённое
удаление копий блокируют подтверждение. Созданные базы отслеживаются по
точному имени, OID и владельцу; их отсутствие проверяется новым подключением.

Для переписывания выбранного SELECT модули transaction_select_rewrite и
transaction_replay сохраняют остальные команды и их порядок. Поддерживаются
ограниченные одиночные правила и ручной вариант. Изменение проверяется в том
месте транзакции, где действительно выполняется SELECT, а не отдельно до
записей. Внешние ORDER BY и LIMIT сохраняются. Обновлённый текст показывается
рядом с исходным, автоматического применения к исходной базе нет.

## В подраздел 4.3 после описания интеграционных проверок

Сквозная приёмка от 10 ноября 2026 года проведена на трёх отдельно созданных
синтетических базах предметных областей retail, logistics и university.
Матрица включает 16 сценариев: полезный индекс, дублирование существующего
первичного ключа, удаление внутренней сортировки, неверную замену SELECT
после UPDATE, отмену, нарушение уникальности и отказы ограниченного
исполнителя. Во всех случаях подтверждена ожидаемая реакция и очистка.
Существующие пользовательские базы этой матрицей не открывались.

В окончательном прогоне переписывание retail-сценария сократило измеренное
общее время с 277,404 до 22,993 мс; индексные варианты logistics и university –
с 43,869 до 13,223 мс и с 47,698 до 13,026 мс соответственно. Результаты
отдельных запросов и конечные таблицы совпали. У других кандидатов
наблюдаемая разница медиан не привела к рекомендации из-за дрейфа или
непрохождения порогов. Приведённые значения характеризуют конкретную
лабораторную нагрузку, а не гарантируют такой эффект в эксплуатации.

Общий набор содержит 631 тест: 570 пройдены, 61 интеграционная проверка
пропущена без специальных флагов запуска. Отдельно все 197 транзакционных
проверок выполнены с подключением к лабораторному PostgreSQL, без пропусков.
Все 11 проверок установленного приложения завершились успешно. Реальный
тайм-аут после UPDATE привёл к SQLSTATE 57014, отказу от рекомендации и
подтверждённому удалению копий. Эти проверки не добавляются в обучение.

Поддержка последовательной записи ограничена простыми транзакциями без JOIN,
CTE, произвольных функций, триггеров, DEFAULT и сессионного контекста. Наличие
оценочного плана для более сложного SQL не разрешает его фактический запуск
в этом режиме. Испытания не моделируют конкурентную production-нагрузку и
не отменяют необходимость отдельной копии и согласованных прав доступа.

## В главу 5 после требований к правам роли

Для фактических транзакционных проб дополнительно требуется доверенный
лабораторный сервер, отдельная эталонная база и роль с правом CREATEDB и
владением эталоном. Такие права не являются условием быстрого прогноза и не
должны выдаваться рабочей роли только ради анализа. Создание и удаление копий
требуют явного подтверждения пользователя. При неподтверждённой очистке
дальнейшие прогоны прекращаются; точные имена и сведения о владельце доступны
в манифестах восстановления. Удаление баз по общему префиксу не допускается.

## В подраздел 6.2 после одиночного переписывания

Для исследования BEGIN … COMMIT используется вкладка «Транзакции», а не
редактор одиночного SQL. Сначала выполняется локальный разбор, затем при
необходимости запрашиваются оценочные планы и собираются общие индексные
кандидаты. Эти действия не выполняют команды записи. Фактическая проба на
копиях является отдельной операцией и требует повторного подтверждения
сервера, эталона и допустимости DML.

Для замены отдельного чтения нужно открыть внутреннюю вкладку
«Переписывание SELECT» и подготовить варианты без подключения. Исходный SELECT
показывается слева, редактируемая замена – справа. Предварительный просмотр
позволяет проверить различия и порядок всей транзакции. После выбора эталона,
числа серий и порогов пользователь разрешает создание одноразовых баз и
запускает проверку замены в контексте всей транзакции.

В результате необходимо отдельно прочитать подтверждение совпадения данных,
статус удаления копий и решение об измеренном эффекте. Ускорение отдельного
SELECT не подтверждает пользу индекса для всех команд. Сообщение о
неопределённости означает, что имеющихся измерений недостаточно для вывода;
оно не равнозначно найденной оптимизации. Изменение текста, параметров или
подключения делает прежнюю проверку неприменимой к новому сценарию.

## Проверки при переносе в Word

- не увеличивать число подпунктов и сохранить названия глав;
- не распространять описание EXCEPT ALL одиночного режима на транзакционный
  режим, где сравниваются результаты каждой команды и полные данные;
- не заменять существующие рисунки 4.2–4.3 так, чтобы они перестали соответствовать
  описанному одиночному алгоритму; транзакционный путь пояснить отдельно;
- при добавлении рисунка интерфейса снять актуальную вкладку и обновить
  перекрёстные ссылки, не использовать старый экран как новый результат;
- сохранить среднее тире, оформление списков, шрифты, отступы, подписи и
  переносы заголовков по образцу;
- обновить содержание и проверить все страницы после рендеринга.
