# Обновление обучающих времён в текущем окружении

Этап от 27.10.2026 проверяет гипотезу сдвига старых целевых времён. В предыдущем
парном контроле медианные отношения исторических времён к свежим на двух
известных когортах составили 2,63 и 2,78. Эти результаты не добавляются
в обучение и не используются как коэффициент коррекции модели.

## Аудит определения времени

В начальном коммите `abd227c` и текущем `plan_features.py` цель получается
одинаково: поле Actual Total Time корневого узла EXPLAIN JSON преобразуется
во float без умножения/деления на тысячу. `dataset.py` передаёт эту величину
в обучающий CSV. Production использует identity-цель, а не забытое обратное
преобразование log1p. Ошибка единиц этим просмотром не обнаружена.

В обычном collect_to_csv собираются отдельные выполнения; прогрев и повторы
добавлялись отдельными экспериментальными скриптами. В старом базовом CSV
нет достаточного снимка окружения, чтобы восстановить нагрузку, аппаратные
условия и политику прогрева для каждой записи. Поэтому систематический
сдвиг обнаружен, но его конкретная причина не установлена.

## Новый зафиксированный протокол

Источник SQL — исторический обучающий пул из 94 семейств, без переноса старых
целевых времён. До замеров исключены все контрольные SQL предыдущих этапов,
включая 76 SQL общего парного контроля. Из каждого семейства выбираются
до четырёх представителей по диапазону **оценочной стоимости**, не по
историческому времени. Один представитель, если возможно, назначается
контролем новых параметров детерминированным хэшем. Малые семейства сохраняются.

Итоговое назначение до сбора:

- 265 обучающих SQL из 94 семейств;
- 94 SQL параметрического контроля — по одному на семейство;
- 36 новых контрольных SQL — 12 форм отчётов по три масштаба.

Последние — новые параметры уже использованных отчётных форм paired_workload,
а не неизвестные семейства запросов. Новые тексты не пересекаются с обучением
или предыдущими контролями. Параметрический контроль может быть известен
старой production-модели по историческому обучению; для новых кандидатов
он полностью исключён из fit. Это не unseen-template оценка.

Все три части назначены до замеров, перемешаны фиксированным seed. Manifest
содержит точные SQL, хэши исходного CSV и моделей, хэши реализации и снимок
окружения. Настройки PostgreSQL проверяются каждые 20 запросов и после сбора.
Снимок включает версию, память, JIT, parallel workers, планировочные стоимости,
оценки таблиц, платформу клиента и протокол времени; пароль не сохраняется.
Снимок не изолирует физическую машину и не гарантирует постоянства внешней
нагрузки. Настройки сервера скрипт не меняет.

Для каждого SQL один прогрев и три EXPLAIN ANALYZE, target — медиана корневого
Actual Total Time в миллисекундах. Работа только на чтение; служебная история
и калибровка не пополняются. Модель получает признаки отдельного обычного
EXPLAIN и каталога, а не фактическую статистику выполнения. В CSV включаются
три целевых измерения; фактические буферы не выдумываются для этих строк.
Для аудита сохраняется последний фактический план каждого запроса.

При ошибке или таймауте SQL остаётся в checkpoint. Обучение на урезанной
«успешной» части не разрешается. Возобновление дописывает отсутствующие
случаи, не перемеряя завершённые или неудачные результаты.

## Обучение и оценка

Новые кандидаты sql-v2 и plan-v1 обучаются **только на свежих 795 измерениях
265 SQL**. Исторические 14 тысяч строк не подмешиваются; объём обновлённого
набора существенно меньше — это репрезентативный срез, не полная замена
всего прежнего датасета. Настройки XGBoost прежние, identity-цель,
балансировка семейств, без поиска гиперпараметров.

Кандидат выбирается по MAE 94 параметрических SQL. Выбор сохраняется
в selection.json до оценки 36 новых SQL. В финале сравниваются production,
прежний plan-v1 и выбранная свежая модель. Общие критерии фиксируются заранее:

- MAE новых SQL ниже production минимум на 10%, median Q-error не выше,
  доля ошибок до 20% не ниже;
- на параметрическом контроле MAE и P90 абсолютной ошибки растут не более
  чем на 10%, median Q-error — не более чем на 5%;
- верхняя граница парного bootstrap-интервала по 12 новым семействам ниже нуля.

Последний интервал ориентировочный: формы отчётов не являются случайной
выборкой. Замеры финальной части собираются вперемешку с остальными,
но не входят в fit или выбор кандидата. Автоматической замены основной
модели нет; прежнее внутреннее правило не отменяется.

## Воспроизведение

```powershell
# Зафиксировать SQL, окружение и критерии, не измеряя запросы
.\.venv\Scripts\python.exe scripts/renew_training_targets.py
# Выполнить зафиксированный протокол
.\.venv\Scripts\python.exe scripts/renew_training_targets.py --run
# Если сбор прерван: дописать только отсутствующие случаи
.\.venv\Scripts\python.exe scripts/renew_training_targets.py --run --resume
```

Артефакты — `artifacts/renewed-targets-20261027`, вне Git. Для воспроизведения
нужны исходный CSV, замороженные модели и тестовая PostgreSQL. При изменении
протокола, реализации или окружения нужен отдельный эксперимент.

## Результат

Все 395 SQL успешно измерены, без таймаутов. Сохранено 1185 фактических
запусков после прогрева. Настройки PostgreSQL не менялись. Медиана отношения
максимального времени к минимальному внутри трёх повторов — 1,046.
На 265 обучающих SQL медианное отношение старой цели к свежей — 2,69;
это подтверждает сдвиг и вне прежнего 40-запросного диагностического среза.
Причина сдвига всё ещё не установлена.

По 94 параметрическим запросам выбран свежий plan-v1:

- production: MAE 171,18 мс, median Q-error 2,722, ошибки до 20% — 8,5%;
- свежий sql-v2: MAE 93,37 мс, median Q-error 1,170, ошибки до 20% — 58,5%;
- свежий plan-v1: MAE 70,76 мс, median Q-error 1,133, ошибки до 20% — 63,8%.

На этих новых параметрах улучшение существенное: MAE ниже production
на 58,7%, при этом контрольные тексты не входили в обучение свежих моделей.
Значение median Q-error не означает такую же ошибку для каждого запроса.

На 36 новых текстах:

- production: MAE 391,34 мс, median Q-error 2,041, ошибки до 20% — 13,9%;
- прежний plan-v1: MAE 364,70 мс, median Q-error 1,850, ошибки до 20% — 5,6%;
- свежий plan-v1: MAE 384,43 мс, median Q-error 1,526, ошибки до 20% — 27,8%.

Типичная кратность ошибки уменьшилась, но MAE относительно production
снизилась всего на 1,8%, а относительно прежнего кандидата выросла.
Предварительно требуемые 10% улучшения MAE не достигнуты. Парная разница
по новым семействам — −6,91 мс; ориентировочный 95%-й интервал
[−138,78; +124,64] мс пересекает ноль.

Самые крупные остаточные ошибки:

- авиационная сводка по участникам с повторно используемым CTE:
  факт 1126 мс, прогноз 3812 мс;
- авиационные пересекающиеся окна: факт 5081 мс, прогноз 2425 мс;
- авиационная групповая сводка: факт 2926 мс, прогноз 1397 мс.

Это диагностика оставшихся проблем, не основание подбирать параметры
по этой же итоговой части. `external_quality_pass=false`,
`primary_replaced=false`. Файл production сохранил SHA-256
`2543cde0e5084621951bcff9d77ea4e2a1f33f70f994cce1af8dddd2aea08080`.

## Интерпретация и ограничения

Свежая компактная модель стала гораздо точнее на новых параметрах известных
семейств, но устойчивого переноса на все отчётные формы не показала.
Нельзя приписать всё улучшение только обновлению времён: одновременно
снизился размер набора с тысяч SQL до 265, изменилась выборка и использован
контракт plan-v1. Сравнение sql-v2 и plan-v1 на одинаковом свежем CSV
показывает вклад признаков только для параметрической части; свежий sql-v2
на финальной части после выбора не проверялся.

Практический следующий шаг — расширение **свежей обучающей нагрузки**
для многопроходных CTE и больших потоков перед несколькими оконными
сортировками, с новым заранее отложенным контролем. Текущие 130 контрольных
SQL и старые контрольные наборы остаются вне обучения. Возвращать старые
времена ради числа строк или корректировать прогнозы по итоговым ответам
этого эксперимента нельзя.

## Проверки реализации

Прошли 79 тестов: выбор SQL независимо от исторических целей, разделение
контроля, снимок окружения без пароля, признаки, обучение, прогноз, DQN и UI.
Проверено отсутствие контрольных SQL в training.csv и фактических времён
во входах модели. Для всех 395 запросов последний сохранённый замер совпал
с Actual Total Time корня сохранённого плана. Отдельный прогноз свежим
артефактом через predict_sql_query вернул источник `ml`, без калибровки
и без выполнения запроса.
