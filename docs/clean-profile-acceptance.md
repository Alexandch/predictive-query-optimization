# Приёмка чистого профиля на локальном SSL стенде

Проверка отделяет настройки приложения, журналы и PostgreSQL от рабочего
окружения. Она создаёт новый локальный кластер PostgreSQL на свободном порту,
две предметные БД без служебных объектов, отдельную роль только для чтения и
роль с правами создания служебной БД. Существующие серверы не открываются.
Это не испытание другого компьютера или реального внешнего сервера.

## Повторяемый запуск

Для Windows нужны готовые PostgreSQL binaries и OpenSSL. Docker не требуется.
Используйте **новый каталог с латинским путём**: OpenSSL в Windows PostgreSQL
не всегда открывает ключи по абсолютному пути с кириллицей. Обычный каталог
проекта и пользовательские настройки не перемещаются.

```powershell
.venv/Scripts/python.exe scripts/clean_profile_acceptance.py `
  --postgres-bin 'C:/Program Files/PostgreSQL/18/bin' `
  --openssl 'C:/Program Files/Git/mingw64/bin/openssl.exe' `
  --output C:/Users/chues/AppData/Local/Temp/pqo-clean-new-run `
  --confirm-local-laboratory
```

Для проверки именно собранного приложения добавьте `--executable` с полным
путём к EXE. Без него проверяется исходный код через `python -m pqo.desktop`.
Существующий каталог результатов не перезаписывается.

## Что проверяется

- новый кластер с собственными SCRAM-паролями и сертификатом;
- действительное SSL-соединение `verify-full`, отказ без SSL и с неверным именем сервера;
- пустой INI, отсутствие прежней калибровки и комплектная plan-v1;
- загрузка нескольких схем и создание/подготовка служебной БД через реальные GUI workers;
- прогнозы для двух источников и история с правильным источником в отдельной БД;
- недоступная служебная БД не уничтожает прогноз и не вызывает запись истории в источник;
- роль только для чтения не создаёт индекс, но получает прогноз и проверяет переписывание SELECT;
- строки SQL выделяются в редакторах, корректность не приравнивается к ускорению;
- повторный запуск отдельного процесса восстанавливает профили, SSL, схемы и модель,
  но не пароли и не результаты предыдущего анализа;
- данные, индексы и отсутствие `pqo` в обоих источниках не изменились;
- рабочий реестр, активная модель и резервные веса совпадают до/после;
- собственный кластер остановлен по проверенным пути и порту.

Порог запуска фактического SQL-переписывания для маленькой фикстуры заранее
равен 0 мс; пороги ускорения остаются 5 мс **и** 5%. Отсутствие рекомендации
допускается. Это функциональная приёмка, не контроль точности ML и не замер
production-нагрузки. В сценарии нет DML replay: он проверяется отдельной матрицей.

## Изоляция настроек

`PQO_SETTINGS_FILE` — абсолютный путь к отдельному INI. При неверном пути
запуск отклоняется, без возврата к рабочему реестру. `PQO_APP_DATA_ROOT`
отдельно задаёт каталог журналов/профилей измерений. Сам по себе он не
подменяет настройки подключения: это сохраняет прежний контракт smoke-инструментов.
Без `PQO_SETTINGS_FILE` обычное приложение продолжает использовать прежний
профиль Windows, не мигрируя и не очищая его.

Пароли генерируются на прогон и передаются дочернему GUI только через среду,
не командную строку. Одноразовый файл пароля initdb удаляется. В `report.json`
нет паролей, DSN и содержимого таблиц; сертификат, остановленный кластер и
снимки интерфейса остаются в каталоге диагностики. Автоматического удаления
чужих БД, завершения чужих подключений и удаления каталогов нет.
