# Итоговый эксперимент

## Цель и протокол

Эксперимент фиксирует итоговое состояние системы без дополнительного обучения.
Он использует ранее запечатанные контрольные наборы и отдельную живую нагрузку
для структурных рекомендаций. Контрольные данные не объединяются с обучающими.

Для каждой автоматически проверяемой структурной рекомендации выполняются пять
чередующихся измерений исходного и пробного варианта. Время сравнивается по
медиане. Переписывание SQL дополнительно проверяется через `EXCEPT ALL` в обе
стороны. Пробные объекты создаются в транзакции, после которой всегда выполняется
`ROLLBACK`.

Команда воспроизведения:

```powershell
docker compose up -d --wait
.\.venv\Scripts\python.exe -m pqo.final_experiment_cli --repetitions 5
```

## XGBoost

| Контроль | Запросы/измерения | MAE, мс | R² |
|---|---:|---:|---:|
| Parameter holdout | 1 295 | 14,18 | 0,9701 |
| Полностью неизвестные шаблоны | 1 368 | 47,75 | 0,7761 |
| Исключённая из обучения logistics | 150 | 114,85 | 0,8636 |
| Production-like aviation | 600 | 637,76 | 0,3758 |
| Внешний CH-benCHmark | 200 | 188,56 | −0,6772 |

Модель хорошо восстанавливает зависимость внутри представленных доменов и
переносится на logistics, но не даёт универсальной оценки абсолютного времени на
любой аппаратной конфигурации и неизвестной схеме. Для пользовательской БД
необходима локальная калибровка; прогноз следует интерпретировать как оценку, а
не как измерение.

## DQN

| Контроль | Accuracy | Mean regret | Сравнение |
|---|---:|---:|---|
| Внутренний test | 56,10% | 0,0749 | random: 26,42% / 0,2549 |
| Logistics | 50,00% | 0,0603 | random: 21,43% / 0,2557 |
| Production-like aviation | 14,81% | 0,1093 | NOOP: 22,22% / 0,1501 |
| Внешний CH-benCHmark | 30,77% | 0,1118 | random: 34,62% / 0,0983 |
| Последовательная DQN | 68,73% | 0,0650 | STOP: 64,82% / 0,1002 |

Обычная DQN заметно зависит от домена и не превосходит все baseline на каждом
внешнем наборе. Последовательная модель показывает преимущество над STOP:
разница accuracy `+3,91` процентного пункта, 95%-й bootstrap-интервал
`[+0,65; +7,17]`; разница regret `−0,0352`, интервал
`[−0,0526; −0,0196]`. Поэтому DQN используется для выбора кандидатов, а решение
подтверждается фактической проверкой PostgreSQL.

## Структурные рекомендации

| Правило | До, мс | После, мс | Изменение | Решение |
|---|---:|---:|---:|---|
| Неагрегатный HAVING → WHERE | 24,140 | 24,584 | −1,84% | отклонить |
| Удаление внутреннего ORDER BY | 72,004 | 13,510 | +81,24% | принять |
| Materialized view для сводки | 514,106 | 0,012 | +99,998% | принять условно |

Создание materialized view заняло `442,819 мс`. Его преимущество относится к
повторному чтению уже рассчитанной сводки. При проектировании необходимо отдельно
учесть частоту `REFRESH`, размер объекта и допустимую устарелость данных.

Для CROSS JOIN дополнительно обнаружены правила `cartesian-join` и
`large-nested-loop`. Они оставлены для ручной проверки, поскольку система не
может автоматически придумать корректное условие связи без знания предметной
области.

Всего обнаружено пять рекомендаций, три проверены автоматически, две получили
измеренное подтверждение. Эквивалентность результатов подтверждена во всех трёх
автоматических сценариях. Все изменения откатились.

## Вывод

Итоговый эксперимент подтверждает практическую ценность системы как помощника,
который сочетает ML-оценку с измерениями. Он также фиксирует ограничение:
универсальная переносимость абсолютного времени и индексной политики на любую
новую БД не доказана. Безопасная стратегия — локальная калибровка, генерация
кандидатов и обязательная фактическая проверка перед применением.

Исходные числа находятся в `models/final_experiment/summary.json` и
`models/final_experiment/structural_results.csv`.
