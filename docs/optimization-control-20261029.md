# Контроль оптимизаций: 29.10.2026

## Протокол

Девять заранее заданных сценариев: индексный, переписывание COUNT → EXISTS с
удалением внутренней сортировки, точечный поиск по первичному ключу — в каждой
из схем aviation, retail, logistics. Это локальная диагностика известных схем,
не независимая отложенная выборка, не обучение и не подбор модели по контролю.

Данные: 50 000 рейсов, 1 000 000 связей билетов с рейсами, 150 000 заказов,
600 000 строк заказов, 150 000 отправлений и 750 000 событий доставки.
PostgreSQL 17.11. Полный SQL каждого сценария, хеш модели, параметры,
индексные пробы и результаты сохранены в
`artifacts/optimization-control-20261029/report.json`.

Три замера, минимум исходного времени 5 мс, экономии 2 мс и 5%; тайм-аут
одного SQL 8 секунд. Для индексов — до трёх кандидатов и один принятый шаг.
Запись в историю pqo отключена; DDL откатывается. Журналы переписывания
сохранены отдельно и защищены от включения в обучение как источник `test`.
Ни веса моделей, ни профиль калибровки не менялись.

## Обнаруженный недостаток и исправление

До исправления лучший SQL выбирался по максимальной абсолютной экономии
относительно собственного парного исходного замера. При дрейфе времени это
не всегда выбирало самый быстрый измеренный SQL. В logistics:

- одиночное EXISTS: 805,317 → 171,198 мс, экономия 634,119 мс;
- сочетание: 764,577 → 146,340 мс, экономия 618,237 мс.

Старое правило предпочло одиночный вариант, хотя сочетание имело меньшую
медиану выполнения. Теперь после проверки эквивалентности и прохождения
порогов выбирается наименьшая наблюдаемая медиана нового SQL. При равенстве
сохраняется порядок генерации. Отказы и неполные замеры не участвуют в выборе.
Это не статистическое доказательство превосходства при малых различиях.

Исходный отчёт сохранён без подмены результатов: он относится к коду до
исправления выбора. Регрессионный тест использует приведённые времена;
новые повторные измерения не выдаются за результаты первоначального прогона.

## Проверка жизненного цикла

Отдельно успешно выполнены шесть тестов на реальном PostgreSQL: применение
управляемого индекса, повторный замер и откат; отмена SQL с удалением пробного
индекса; восстановление savepoint и бюджета после тайм-аута; завершение
глубокого анализа тяжёлого LATERAL при тайм-ауте; сравнение SQL с дубликатами;
отказ при изменении числа дубликатов. После них инвентаризация индексов также
совпала с исходной.

Фоновая проверка интерфейса `--rewrite-smoke-test` прошла: сравнение равных
результатов, отказ при потере дубликатов, исходный редактор не изменяется.
Общий набор: 370 выполненных тестов, 40 opt-in интеграционных пропущены;
перечисленные шесть интеграционных запущены отдельно. Проверки редактора
дополнительно покрывают применение/возврат SQL и блокировку повторных операций.

## Повторение и следующий этап

```powershell
.venv\Scripts\python.exe -m pqo.optimization_control --output artifacts/optimization-control-new-run --timeout-ms 8000 --repetitions 3
```

Каталог должен быть новым: прежний отчёт не перезаписывается. Ошибки отдельных
сценариев записываются, затем проверка продолжается; изменение инвентаризации
индексов останавливает запуск без попыток удалить неизвестные индексы.

Это проверенная исходная версия для демонстрационных сценариев, а не гарантия
для произвольных SQL. Следующий этап подготовки защиты — выбрать примеры из
этого отчёта, воспроизвести их в интерфейсе и согласовать с запиской. Изменения
правил или генерации индексов добавляются по конкретным выявленным пропускам,
а не ради обязательной рекомендации на каждом запросе.
