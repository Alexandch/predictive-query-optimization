# Индексные кандидаты и цена применения

Этап 27.10.2026. Модели DQN/XGBoost, размерности входных векторов и формат
безопасных IndexAction не изменены. Изменены эвристики генерации и проверка
реального покрытия существующими индексами. Это может изменить рейтинг
действий старой модели; итоговое решение по-прежнему требует замера.

## Что изменено

Составные кандидаты теперь начинают с равенств, а не с первого упомянутого
в SQL предиката. Для `range AND equality ORDER BY sort` рассматриваются
варианты с приоритетом фильтра и сортировки. Сохраняются одиночные ключи,
лимиты трёх ключей/INCLUDE и общего числа действий. При одном ORDER BY
без WHERE тоже появляется кандидат. Это не доказательство оптимального
порядка столбцов: селективность, направление сортировки и план проверяет БД.

Проверка существующего индекса учитывает все ключи и INCLUDE-столбцы.
Обычный `(a)` больше не отсекает `(a) INCLUDE(b)`, если `b` отсутствует.
Напротив, `(a,b)` или `(a) INCLUDE(b)` могут покрывать этот кандидат.
Проверяется именно префикс ключей и полный набор запрошенных payload-столбцов.

Индекс считается безусловной заменой только при наличии пригодного обычного
B-tree: valid/ready, без предиката и выражений, со стандартными operator
classes, коллациями столбцов и стандартными параметрами порядка ключей.
Позиции выражений не удаляются из массива атрибутов. Частичный индекс,
например `(a) WHERE c>0`, не считается заменой общему `(a)` для любого SQL.
Специальный/обратный индекс может быть полезен, но этот консервативный тест
его не признаёт полной заменой. Это иногда оставляет лишнего кандидата,
который всё равно должен пройти пробное построение и замер.

Близкие индексы с теми же ведущими ключами, но неполным покрытием,
показываются как пересечение. Приложение не удаляет и не заменяет их
автоматически, особенно индексы ограничений PRIMARY KEY/UNIQUE.

## Что объясняет приложение

Для принятого шага выводятся ключи, INCLUDE, число пересекающихся индексов,
измеренный размер и построение, число индексов на таблице и накопленные
счётчики записи. Счётчики не являются частотой операций или будущей нагрузкой.
При отсутствии сохранённого значения пересечения выводится «сведения не
сохранены», а не ложное утверждение об отсутствии похожих индексов.

INCLUDE хранит payload, не задаёт порядок поиска. Возможность index-only
scan зависит и от MVCC-видимости. Обновление индексируемых/INCLUDE-столбцов
может препятствовать HOT. Задержка INSERT/UPDATE/DELETE и влияние на другие
SELECT здесь не измеряются и не выдаются в процентах. Обычный CREATE INDEX
может блокировать запись; поддержка CONCURRENTLY в управляемом транзакционном
применении этим этапом не добавлялась.

Дополнительно вычисляется только грубая окупаемость построения:
`ceil(creation_time_ms / (before_time_ms - after_time_ms))` повторений SELECT.
Она не учитывает запись, диск, кэш, изменение данных и нагрузки; это не
полная экономическая оценка. При недостаточных измерениях число не выводится.

## Проверка

Каталожная интеграционная проверка создаёт TEMP-таблицу и индексы в одной
сессии и откатывает их: обычный, покрывающий, частичный, выраженческий,
hash, pattern_ops и нестандартная коллация. Реальные таблицы не меняются.
Unit-тесты проверяют порядок ключей, обратную запись равенств, ORDER BY без
WHERE, покрытие INCLUDE и честное объяснение издержек.

Локальная демонстрация `examples/logistics-index-order-check.sql`:

- DQN выбрала `(facility_id, event_type, event_time)`;
- три замера после прогрева: медианы 26,441 → 0,024 мс;
- размер 5,14 МиБ, построение 668,27 мс;
- грубая окупаемость только построения – 26 повторений;
- инвентаризация индексов до/после совпала; все пробные изменения откатились.

Для этого короткого SQL в демонстрации порог исходного времени – 5 мс,
минимальная абсолютная экономия – 2 мс, относительная – 5%. При стандартном
пороге приложения 50 мс такой запрос будет корректно пропущен. Результат
зависит от окружения, кэша и уже установленных индексов.

Другой пример, `examples/logistics-index-tradeoffs.sql`, с дополнительным
диапазоном даты не сформировал принятого шага (`non_positive_reward`).
Этот отрицательный результат сохранён в `artifacts/index-tradeoffs-check`,
положительный – в `artifacts/index-tradeoffs-order-check`. Нельзя заключать,
что для первого запроса вообще не существует полезного индекса: на том
этапе проверялся первый выбранный моделью кандидат. В следующем этапе
добавлены [ограниченные повторные пробы](index-candidate-retry.md), которые
нашли полезный второй вариант для этого SQL. Полного перебора всё равно нет.

```powershell
.venv\Scripts\python.exe scripts/check_index_tradeoffs.py --example examples/logistics-index-order-check.sql --output artifacts/index-tradeoffs-order-check
```
