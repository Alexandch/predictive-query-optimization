# Служебная схема и данные

Исследуемые БД и служебное хранилище имеют разные подключения. В служебной БД
находится схема `pqo`; исследуемым источникам она не требуется. Настройка и
миграции описаны в [connections.md](connections.md).

## Схема pqo

| Таблица | Назначение |
| --- | --- |
| `query_run` | SQL, статус запуска и контекст источника |
| `query_features` | признаки структуры SQL |
| `execution_plan` | JSON-план и агрегированные признаки плана и каталога |
| `model_prediction` | прогноз и версия модели |
| `index_recommendation` | индексные кандидаты и их статусы |
| `recommendation_audit` | изменения статусов индексных кандидатов |
| `sequential_analysis` | итог последовательного индексного анализа |
| `sequential_analysis_step` | проверенные шаги и измерения |
| `structural_recommendation` | структурные гипотезы |
| `structural_validation` | результаты их фактической проверки |

План и признаки связаны с запуском по `query_run_id`. Один запуск может иметь
несколько прогнозов и рекомендаций. Шаг определяется парой
`(sequential_analysis_id, step_number)`; аудит и проверки зависят от рекомендации.
Удаление служебного анализа удаляет зависимые записи, а не предметные данные.

`query_run.target_context` хранит адрес сервера, БД, роль и выбранные схемы
без пароля. Это позволяет различать результаты одинакового SQL из разных БД.
Сохранение регистрации, признаков и плана выполняется транзакционно.

Авторитетное описание полей, ограничений и процедур — SQL-миграции в
[database/init](../database/init). Для отдельной служебной БД используются
миграции 001–009 и 012–014; предметные схемы устанавливаются отдельно.

## Статусы и аудит

Функция `pqo.register_query_run` регистрирует запуск. Процедура
`pqo.set_recommendation_status(bigint, text, text)` блокирует строку рекомендации,
проверяет ожидаемый старый статус и выполняет допустимый переход:

- `proposed` → `accepted` или `rejected`;
- `accepted` → `applied`;
- `applied` → `reverted`.

Неверный переход, отсутствующая строка или устаревшее ожидаемое значение
отклоняются. Guard-триггер также контролирует прямой UPDATE, а отдельный триггер
записывает аудит. Статус и аудит откатываются вместе. Процедура не выполняет DDL;
принятие в истории не означает, что индекс создан.

## Демонстрационные схемы

Локальный Docker-стенд содержит `aviation`, `retail`, `logistics`, `chbenchmark`
и `pagila`: авиаперевозки, торговлю, логистику, складские заказы и видеопрокат.
Их схемы и начальные данные лежат в `database/init`. Повторный запуск контейнера
не загружает данные заново в существующий том.

Отдельная синтетическая БД `pqo_university_unseen` создаётся модулем
`pqo.unseen_database` из [university.sql](../database/unseen/university.sql).
Она используется примерами и тестами транзакций; это не внешний рабочий сервер.
Порядок подготовки — в [testing.md](testing.md).

Источники и роли наборов данных описаны в
[dataset/postgresql/README.md](../dataset/postgresql/README.md).
Происхождение и лицензия Pagila сохранены в
[vendor README](../database/vendor/pagila/README.md).
