# Последовательное выполнение на одноразовых БД — 0.8.35

Это первый из согласованных этапов: **реальная запись на новых копиях**.
Проверяются конкретные результаты и состояние. В исходной 0.8.35 итоговая
рекомендация не формировалась; в 0.8.36 добавлена отдельная
[оценка смешанной нагрузки](transaction-mixed-recommendation.md). Переписывание внутри
транзакции и окончательная сквозная проверка остаются следующими этапами.

В 0.8.37 отдельно добавлено [переписывание SELECT в контексте транзакции](transaction-select-rewrite.md).
Описанный здесь исходный индексный исполнитель не стал принимать произвольные подзапросы.

## Как попробовать

1. Настройки источника: `pqo_university_unseen`, разрешённая схема `university`.
   Лабораторный эталон — уже подготовленная отдельная `pqo_university_index_lab`.
   Убедиться, что она не используется другим приложением в момент снимка.
2. Во вкладке «Транзакции» открыть
   `examples/transactions/university-disposable-replay.sql`, разобрать,
   получить оценочные планы и собрать кандидатов. Эти действия сами DML не запускают.
3. Отметить 1–2 непокрытых кандидата, например `enrollments(student_id)`
   с INCLUDE `enrollment_id, registered_at, status`.
4. Открыть внутреннюю вкладку «Выполнение на копиях». Ввести лабораторный
   эталон, оставить две серии A1/B/A2 (0.8.36), явно разрешить CREATE/DROP одноразовых БД.
5. Нажать кнопку выполнения и проверить повторное подтверждение сервера,
   источника, эталона и числа копий. **Только доверенный тестовый сервер,
   не production.** Нужны CREATEDB и право клонировать эталон; обычно владение им.
6. В результате отдельно прочитать равенство исходных состояний, результатов,
   итоговых данных и подтверждение удаления копий. Один успешный прогон
   не объявляет индекс устойчивой рекомендацией.

Эталон и исходная БД не получают пользовательские SELECT/DML от этого движка.
Из эталона читаются каталоги/размер; административные CREATE/DROP выполняются
через `postgres`. Получение старых планов/кандидатов отдельно обращается к
источнику без выполнения DML. Источник `postgres`/template0/template1 для
этого режима исключён, чтобы административное соединение не стало исходным.

## Протокол

Сначала создаётся одна закрытая копия эталона. Соединения с ней запрещены;
все следующие копии клонируются из неё, а не из меняющегося эталона.
Для каждой серии создаются новые БД A1, B и A2. В B заранее строятся выбранные
индексы. В каждой копии повторно проверяются каталоги и читается исходное
состояние, затем команды выполняются **один раз в исходном порядке** внутри
BEGIN … COMMIT. Последующий SELECT видит предыдущие записи этой же транзакции.
После COMMIT проверяются итоговые данные. Выполнившаяся копия удаляется
перед следующей; закрытая эталонная копия удаляется в конце.

Снимок охватывает все таблицы разрешённых схем, не только явные цели UPDATE.
Строки читаются потоково в полном порядке PRIMARY KEY, используются длины
записей и SHA-256 канонического JSON PostgreSQL вместе с описанием столбцов/PK.
Результаты команд проверяются по числу строк, именам/типам столбцов и SHA-256
значений с сохранением NULL, типов и дубликатов. При ORDER BY учитывается
последовательность; без него — мультимножество. RETURNING также проверяется.
Это проверка на конкретных данных, не математическое доказательство бизнес-семантики.
Равные ключи ORDER BY могут приводить к консервативному отказу; лучше добавлять PK.

Окончательное совпадение считается подтверждённым только при полном наборе
3 × число серий, одинаковых начальных состояниях, результатах и итоговых
данных, а также подтверждённой очистке. При ошибке/отмене следующий прогон
не запускается. Удаление проверяется отдельным подключением, не выводится
из успешного ROLLBACK.

## Что измеряется

- execute+fetch каждой команды, отдельно для SELECT и DML;
- клиентский интервал BEGIN–COMMIT, включая передачу/получение результатов,
  их контрольный хеш и служебные проверки/настройку тайм-аутов;
- время построения и суммарный размер новых индексов — отдельно.

Клонирование и полные снимки таблиц не включаются в клиентское время транзакции.
Поэтому оно не равно времени ожидания кнопки. Оно также не равно серверному
Execution Time или сумме медиан отдельных SELECT из прежнего режима. Сумма
execute+fetch не включает все накладные расходы общего интервала.

Условия режима: UTC, ISO, `jit=off`, `max_parallel_workers_per_gather=0`.
Чтение снимков прогревает страницы, построение индекса тоже влияет на кэш.
Одинаковые данные **не означают** одинаковый физический кэш/конкурентную нагрузку.
Показанные времена относятся к этому лабораторному протоколу, не обещают
производительность production и сами по себе ещё не дают рекомендации.

## Узкий поддерживаемый контракт

BEGIN … COMMIT, до 50000 символов и 2–20 команд, хотя бы один SELECT и один
INSERT/UPDATE/DELETE. Ровно одна физическая таблица в команде; явная схема;
простые ASCII-идентификаторы. INSERT только VALUES с явными столбцами, до 100
строк; UPDATE/DELETE обязательно с WHERE. Допускаются простые выражения,
сравнения, фиксированные литералы, ограниченные агрегаты и явные приведения.
Специальные now/today и физические системные столбцы исключены.

Не выполняются JOIN, CTE/подзапросы, пользовательские/неизвестные функции,
текущие даты/случайность, параметры без явной привязки, DEFAULT/ON CONFLICT,
MERGE, SELECT INTO, блокировки, SET, режимы BEGIN/savepoint и ROLLBACK-сценарии.
Нет скрытого преобразования ROLLBACK в COMMIT.

В разрешённых схемах нужно 1–8 постоянных обычных heap-таблиц с PK и
ограниченным набором встроенных типов. Не допускаются последовательности,
DEFAULT/identity/генерируемые столбцы, пользовательские типы/collation,
RLS, секции/наследование, правила, активные пользовательские триггеры,
CHECK/исключения, каскадные/внешние FK, выражения/частичные/нестандартные
существующие индексы. Поддерживаются обычные PK/UNIQUE и внутренние FK
NO ACTION/RESTRICT между проверяемыми таблицами. Расширения кроме plpgsql,
активные event triggers и подписки блокируют режим.

Это инженерные ограничения первой реализации, не заявление, что такие
объекты PostgreSQL вообще нельзя анализировать. Проверка не является
песочницей для враждебной БД, конфигурации сервера или другого суперпользователя.

Лимиты: эталон до 256 МиБ; снимок до 2 млн строк / 256 МиБ; не более 10000
затронутых/возвращённых строк команды и 8 МиБ её контрольного результата;
до двух новых индексов, суммарно до 64 МиБ после построения; 1–3 серии;
общий бюджет 300 с, отдельный statement до 30 с, lock_timeout 1 с.
Лимиты размера/строк проверяются после получения соответствующего результата,
а не резервируют память/диск заранее. Сервер должен иметь запас ресурсов.

## Очистка и аварийное прерывание

Имена pqo_replay_… генерируются случайно. Доступ PUBLIC отзывается до открытия
соединений. Автоматически удалить можно только имя, успешно созданное данным
вызовом, с тем же записанным OID и владельцем. Не используются FORCE,
pg_terminate_backend, удаление по префиксу/маске или перезапись эталона.
При неоднозначном CREATE, смене OID/владельца или чужом подключении приложение
оставляет явное предупреждение; «копии удалены» не предполагается.

В интерфейсе и CLI ведётся локальный журнал владения `artifacts/disposable-recovery/`:
намерение CREATE, имена, OID/владелец и подтверждённые удаления. Без SQL,
строк, пароля и автоматического восстановления/удаления. При жёстком завершении
процесса копии могут остаться: нужно сверить журнал и каталоги, а не выполнять
массовый DROP по префиксу. Обычная отмена прерывает выполняемый SQL; CREATE
заканчивается/достигает statement_timeout прежде, чем проверяется отмена, чтобы
успеть записать владение. Ожидание отмены на этом шаге может достигать 30 с.

Основание ограничений клонирования и очистки:
[CREATE DATABASE](https://www.postgresql.org/docs/17/sql-createdatabase.html),
[DROP DATABASE](https://www.postgresql.org/docs/17/sql-dropdatabase.html).

## Автоматические проверки

```powershell
$env:PQO_UNIVERSITY_TESTS='1'
$env:PQO_TRANSACTION_TRIAL_TESTS='1'
$env:PQO_DISPOSABLE_REPLAY_TESTS='1'
.venv\Scripts\python.exe -B -m unittest discover -s tests -p 'test_transaction*.py' -q
```

Новый opt-in создаёт собственные маленькие fixture-БД из template0 и удаляет
только их по проверенному OID. Проверяются последовательная видимость записи,
одинаковое начало, результаты/итоги, отказ каталогов, ошибка SQL и отмена после
UPDATE, а также сохранность эталона и отсутствие подключений движка к источнику.

`--transaction-replay-smoke-test` требует `PQO_REPLAY_COPY_CONFIRMED=1` и
`PQO_REPLAY_REFERENCE=pqo_university_index_lab`; допускает только известный
синтетический источник pqo_university_unseen со схемой university. Это настоящий
queued GUI worker, не подстановка результата. `PQO_SMOKE_PREVIEW=1` добавляет
снимки интерфейса. Пользовательская история, модель и калибровка не пополняются.
