# Замена SELECT внутри транзакции — 0.8.37

Третий согласованный этап: изменение **одного самостоятельного SELECT** с
сохранением остальных команд и их порядка. Результат проверяется не отдельно
до транзакции, а там, где SELECT действительно выполняется после предыдущих
записей. Автоматического изменения исходного редактора/исходной БД нет.

## Как попробовать

1. Во вкладке «Транзакции» открыть
   `examples/transactions/university-select-rewrite.sql`. Источник в настройках —
   `pqo_university_unseen`, разрешённая схема `university`.
2. Выбрать режим «Анализ и проверки», затем «Переписывание SELECT» в меню слева.
   Нажать «Подготовить замены SELECT (без подключения)». Для этой подготовки
   не нужны планы и индексные кандидаты, к БД она не подключается.
3. Выбрать `SELECT № 2: Удалить лишний ORDER BY…`. Слева виден исходный SELECT,
   справа — отдельная редактируемая замена. Основной редактор транзакции
   остаётся неизменным. С 0.8.41 изменения выделены в самих редакторах; при
   наведении показан исходный вариант. «Показать замену и порядок команд» выводит полную
   нормализованную транзакцию с единственной заменой, без запуска, в развёрнутом
   протоколе. «Вернуться к работе» возвращает редакторы. С 0.8.42 кнопка
   «Развернуть редакторы SQL» отдаёт им высоту настроек; повторное нажатие
   показывает настройки проверки. Их скрытие не даёт согласия на запуск.
4. Указать отдельный лабораторный эталон `pqo_university_index_lab`, две серии
   и пороги общего выигрыша (по умолчанию 5 мс **и** 5%). Явно разрешить
   реальный DML/COMMIT и создание/удаление одноразовых копий.
5. Нажать «Проверить замену в контексте всей транзакции на копиях» и проверить
   сервер/источник/эталон в повторном подтверждении. Только доверенный
   лабораторный сервер, **не production**. Нужны CREATEDB и владение эталоном.
6. Прочитать отдельно совпадение исходных состояний, всех результатов команд,
   итоговых данных, удаление копий и решение о времени. Общее время, SELECT/DML,
   отдельные команды, фазы и причины отказа доступны через «Открыть протокол»
   или «Протокол рядом».

Если подходящих правил нет, об этом выводится явное сообщение; доступен
ручной вариант для каждого SELECT. Он начинается с исходного текста, поэтому
для пробы его нужно изменить. В правый редактор допускается ровно один
конкретный SELECT: не вся транзакция, не несколько команд, без `$1`/SET/DML.
Отредактированный автоматический вариант проверяется заново как фактический
текст, а название первоначального правила не является доказательством.

Позиционные параметры исходной транзакции сначала задаются через обычный
локальный разбор и «Параметры SQL». Замены готовятся для эффективного SQL с
этими значениями, отдельно по каждой команде; исходный редактор с параметрами
не меняется. Изменение значений сбрасывает варианты и результаты. Значения
не сохраняются в настройки/историю и не используются для обучения.

## Что поддерживается

Сохраняется [закрытый контракт исполнителя](transaction-disposable-replay.md):
bare BEGIN … COMMIT, 2–20 простых команд, хотя бы SELECT и DML, одна физическая
таблица на команду, явная разрешённая схема, ограниченные типы/агрегаты,
простые UPDATE/DELETE с WHERE и INSERT VALUES с явными столбцами. Те же
ограничения каталогов: обычные heap-таблицы с PK, без RLS, DEFAULT/identity,
пользовательских триггеров, каскадов, расширений и внешних побочных эффектов.
До 256 МиБ эталона, 8 таблиц, 10000 возвращённых/затронутых строк на команду,
2 млн строк / 256 МиБ контрольного снимка; общий бюджет 300 с плюс очистка.

Только режим переписывания дополнительно разрешает **один SELECT в FROM**
под внешним агрегатом. Ровно два уровня SELECT и одна физическая таблица;
нет JOIN, CTE, скалярных/коррелированных подзапросов или новых функций.
Проверяются допустимые узлы и опции обоих SELECT, не только первый keyword.
Старый индексный режим автоматически не расширялся.

Локально используются четыре одиночных правила существующего реестра:

- цепочка OR по одному столбцу → IN;
- две включённые границы диапазона → BETWEEN;
- удаление внутреннего ORDER BY без LIMIT/OFFSET;
- перенос поддерживаемого неагрегатного HAVING-фильтра в WHERE.

Сочетания правил, JOIN/EXISTS-переписывания, CTE/окна и изменение DML на этом
этапе не выполняются. Правило, выходящее за закрытый контракт, не становится
исполняемым кандидатом. Бизнес-семантика сумм автоматически не исправляется.

## Сохранение контекста и проверка

Замена разбирается как один SELECT; номер обязан указывать на SELECT, не
UPDATE/INSERT/DELETE. Нельзя сменить физическую таблицу выбранной команды,
внешние ORDER BY (направление/NULLS в том числе) или LIMIT. Прочие команды
проверяются на точное равенство нормализованного представления и порядка;
комментарии/форматирование при этом не являются выполняемыми командами.
Синтаксически идентичная замена не измеряется как оптимизация.

Создаётся один закрытый снимок отдельного эталона. Для каждой серии из него
создаются свежие A1, B и A2. В A1/A2 выполняется исходная транзакция, в B —
та же транзакция с заменой одного SELECT. Никаких новых индексов не создаётся;
уже существующие индексы эталона одинаковы во всех фазах. DML реально
выполняется по порядку и фиксируется COMMIT только в одноразовых копиях.

Сравниваются исходные состояния, **каждый** результат SELECT/RETURNING,
имена и типы столбцов, число возвращённых/затронутых строк и состояние всех
проверяемых таблиц после COMMIT. Упорядоченный результат сравнивается как
последовательность, иначе — как мультимножество с NULL/типами/дубликатами.
Используются канонические значения, SHA-256 и длины записей; значения/строки
в отчёте не сохраняются. Равные ключи ORDER BY или различия представления
могут привести к консервативному отказу; полезен полный порядок по ключу.
Это проверка на конкретных данных, не доказательство для любых данных.

Совпадение конечных таблиц само по себе недостаточно: ручной SELECT может
вернуть другие строки при том же конечном состоянии. Любое несовпадение,
ошибка/отмена, неполные серии или неподтверждённая очистка блокируют вывод.
Удаление каждой созданной БД проверяется по имени/OID/владельцу и отдельным
подключением; FORCE, завершение чужих сеансов и удаление по маске отсутствуют.
Журналы владения не используются для автоматического удаления прежних копий.

## Оценка времени и границы

После подтверждённой корректности/очистки применяется та же
[политика смешанной нагрузки](transaction-mixed-recommendation.md): минимум две
полные серии, оба порога общего клиентского выигрыша в каждой, отказ при
регрессии отдельной команды или суммарных SELECT/DML > 2 мс **и** > 10%,
недостаточность данных при дрейфе A1/A2 или между сериями > 2 мс **и** > 20%.
Одна серия остаётся диагностической. Положительный общий выигрыш не разрешает
несовпадение результата или существенную регрессию другой команды.

BEGIN–COMMIT — клиентский интервал с передачей/получением результата, его
хешированием и служебными тайм-аутами; командные интервалы — execute+fetch.
Клонирование и полное чтение снимков вне измерения. UTC/ISO, jit=off,
parallel=0; чтение снимков прогревает кэш. Нет проверки production-конкуренции,
холодного кэша, общего оптимума или независимого контрольного набора.

Политика, исходный эффективный SQL, номер SELECT, фактическая замена,
подключение/разрешённые схемы/тайм-ауты, эталон и число серий связываются
контрольным SHA-256 до запуска. Пароля/SQL в этой привязке нет. Это контроль
устаревания, не авторизация внешних отчётов. Смена SQL/подключения/параметров
сбрасывает подготовку; смена варианта/порогов/эталона/серий сбрасывает результат.
Запоздалый callback не присоединяется; предупреждение о неочищенных копиях
не теряется даже для устаревшего ответа.

Отчёт хранится в памяти. SQL/значения автоматически не пополняют историю,
локальный журнал переписываний или обучение. Сам просмотр/ручное копирование
варианта не означает проверку или разрешение на production-выполнение.

Следующий согласованный этап — сквозная проверка MVP на нескольких БД,
положительных/отрицательных случаях, ошибках/отмене и актуализация записки
по фактическим, а не планируемым возможностям.

## Проверка исходников

Полный набор: 622 теста, 562 прошли, 60 opt-in сценариев пропущены без
специального разрешения. Отдельно все 188 тестов транзакционного блока
прошли с разрешёнными PostgreSQL-проверками, без пропусков.
Новые проверки охватывают закрытую грамматику, неизменность команд/порядка,
недопустимую замену DML/таблицы/ORDER BY/LIMIT, локальную генерацию без БД,
ручной вариант, фиксированную привязку, queued worker/повторные действия,
неподходящие правила и устаревший callback с предупреждением об очистке.

В тестовом PostgreSQL-примере UPDATE меняет значение до выбранного SELECT.
Его результат после замены совпал с отдельно вычисленным ожидаемым
результатом **с учётом этой записи**; все начальные/итоговые состояния и
результаты команд совпали, семь одноразовых БД удалены, источник не
подключался движком выполнения. Ручная замена с неверным фильтром отклонена:
конечные таблицы совпали, но SELECT вернул другой результат. Отмена после
записи также проверила очистку и сохранность лабораторного эталона.

Реальный queued GUI прогон примера university-select-rewrite выполнил две
серии. Клиентские A1/B/A2: 156.286 / 58.124 / 143.443 мс и
146.475 / 62.849 / 146.829 мс. Сводные медианы серий: 148.258 → 60.486 мс,
измеренный выигрыш 59.2%. Вывод `recommended`: в обеих сериях пройдены
оба порога общего выигрыша, значимых регрессий/дрейфа нет. Все результаты
и итоговые данные совпали, семь созданных БД удалены, новых индексов нет.
Это технический синтетический пример, не независимый production-бенчмарк
и не гарантия такого же ускорения на других данных/транзакциях.

Исходный интерфейс просмотрен в 1740×1030 и 1280×800: редакторы рядом,
пороги/подтверждение и решение доступны через вертикальную прокрутку;
длинный отчёт имеет отдельную прокрутку.
Артефакты: `artifacts/tests-0837-full.log`,
`artifacts/tests-0837-transactions-final.log`, `artifacts/validation-0837-source/`.
