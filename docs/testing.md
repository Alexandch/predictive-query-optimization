# Проверки проекта

## Модульные тесты

Из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
$env:QT_QPA_PLATFORM = "offscreen"
.\.venv\Scripts\python.exe -m pytest -p no:cacheprovider
```

PostgreSQL-тесты с отдельным разрешением пропускаются, пока не включён их флаг.
Такой пропуск не является успешной интеграционной проверкой. Он не мешает
модульным тестам парсера, моделей, интерфейса и политик рекомендаций.

## Подготовка локального стенда

```powershell
docker compose up -d --wait
```

Подключение берётся из [переменных окружения](connections.md), а не из профиля GUI.
Нужны доступная БД `query_optimizer` с исходными схемами и роль с CREATEDB для
тестов, создающих свои временные БД. Используйте отдельный доверенный стенд.

Для университетских тестов дополнительно нужны `pqo_university_unseen`
и `pqo_university_index_lab`. Если их ещё нет:

```powershell
.\.venv\Scripts\python.exe -m pqo.unseen_database create
.\.venv\Scripts\python.exe -m pqo.transaction_index_trial create-university-lab
```

Команды не предназначены для пересоздания существующих БД. Второй вызов
клонирует подготовленный источник; активные подключения к нему могут помешать.

## Интеграционные группы

| Флаг со значением `1` | Проверка |
| --- | --- |
| `PQO_INTEGRATION_TESTS` | базовый доступ к PostgreSQL, сбор и индексные проверки |
| `PQO_UNIVERSITY_TESTS` | планы и кандидаты университетского стенда |
| `PQO_TRANSACTION_TRIAL_TESTS` | реальные пробы SELECT на отдельной копии |
| `PQO_DISPOSABLE_REPLAY_TESTS` | последовательное выполнение и очистка собственных копий |
| `PQO_STATUS_INTEGRATION_TESTS` | процедура статусов, аудит и конкуренция |
| `PQO_CONNECTION_INTEGRATION_TESTS` | раздельные подключения, история и подготовка копий через pg_dump/pg_restore |

Полный прогон после подготовки стенда:

```powershell
$env:PQO_INTEGRATION_TESTS = "1"
$env:PQO_UNIVERSITY_TESTS = "1"
$env:PQO_TRANSACTION_TRIAL_TESTS = "1"
$env:PQO_DISPOSABLE_REPLAY_TESTS = "1"
$env:PQO_STATUS_INTEGRATION_TESTS = "1"
$env:PQO_CONNECTION_INTEGRATION_TESTS = "1"
.\.venv\Scripts\python.exe -m pytest -p no:cacheprovider --maxfail=1
```

`scripts/verify.ps1` поднимает Docker, включает только базовый
`PQO_INTEGRATION_TESTS` и проверяет комплектные модели. Он не заменяет включение
остальных пяти групп.

## Сквозная проверка транзакций

```powershell
.\.venv\Scripts\python.exe -m pqo.transaction_acceptance --output artifacts\transaction-acceptance --confirm-trusted-laboratory-server
```

Исполнитель создаёт собственные фикстуры и одноразовые БД на трёх схемах,
проверяет индексы, замену SELECT, несовпадение результатов, отмену и очистку.
Нужен новый каталог результатов. Фактические режимы и ограничения описаны в
[transactions.md](transactions.md). Технический успех не требует положительного
ускорения каждого сценария.

## Проверка приложения

Загрузка GUI-зависимостей и моделей без анализа SQL:

```powershell
.\.venv\Scripts\python.exe -m pqo.desktop --smoke-test
```

Для чистого профиля есть отдельный SSL-стенд с двумя источниками, служебной БД
и ролью только для чтения:

```powershell
.\.venv\Scripts\python.exe scripts\clean_profile_acceptance.py --postgres-bin "C:\Program Files\PostgreSQL\18\bin" --openssl "C:\Program Files\Git\mingw64\bin\openssl.exe" --output C:\Temp\pqo-clean-check --confirm-local-laboratory
```

Укажите свои установленные binaries и новый каталог с латинским путём.
С `--executable` проверяется собранный EXE, без него — исходники. Сценарий
проверяет SSL, новый запуск и перезапуск, профили, историю, отказ служебной БД,
read-only роль, переписывание и сохранность рабочих настроек. Он останавливает
собственный кластер и оставляет отчёт; чужие серверы не открывает.
Это локальная проверка, а не испытание удалённого сервера или другого компьютера.
Стенд также проверяет, что приложение может сопоставить сессии живой серверный
процесс и получить его CPU и выборки RSS. Для прогона нужна зависимость `psutil`
из группы `desktop` или `dev`.

Сборки Linux и macOS запускаются на своих ОС через workflow
[`desktop-platforms.yml`](../.github/workflows/desktop-platforms.yml).
Workflow проверяет модульные тесты, запускает упакованное приложение с
`--smoke-test` и сохраняет архив Linux или архив macOS `.app`. Проверка в
режиме offscreen подтверждает запуск и загрузку моделей.

Для нативной Windows-проверки используйте `QT_QPA_PLATFORM=windows`:
offscreen не воспроизводит все события оконной системы. Порядок проверки
установщика приведён в [windows-packaging.md](windows-packaging.md).

`--workflow-smoke-test` проверяет маршрут «Начало» → подключение → создание
эталона и рабочей БД → отдельное сравнение SELECT → возврат замены → полный
прогон транзакции. Нужны подготовленный `pqo_insert_source` (команда
`python -m pqo.unseen_database create-insert-select`), схема `retail`,
клиентские утилиты PostgreSQL, новый `PQO_SETTINGS_FILE`, отдельный
`PQO_APP_DATA_ROOT` и явный `PQO_WORKFLOW_COPY_CONFIRMED=1`.
Сценарий принимает только эту известную синтетическую БД. Он оставляет две
подготовленные БД `pqo_wflow_*` для независимой сверки; имена, OID и владельцы
сохраняются в журнале. Семь одноразовых БД полного прогона удаляются исполнителем.
Рабочие настройки пользователя для этой проверки использовать нельзя.

Более широкая проверка нового интерфейса из исходников:

```powershell
.\.venv\Scripts\python.exe scripts\workflow_acceptance.py --output artifacts\workflow-acceptance --confirm-local-laboratory
```

Нужны локальный доверенный PostgreSQL, CREATEDB и клиентские утилиты.
Сценарий создаёт собственные новые БД на схемах retail/logistics/university,
в нативном Qt-окне нажимает кнопки подготовки стенда, прогноза, глубокой проверки,
подбора общего индекса и переписывания. Проверяются весь порядок команд, данные,
неизменность источника и рабочих настроек, отмена после записи и удаление своих БД.
Отдельный SELECT, совпавший на начальных данных, обязан быть отклонён, если он
дал другой результат после предшествующего UPDATE. Пороги времени зафиксированы
до пробы; нестабильные замеры не превращаются в рекомендацию.
Нужен новый каталог: в нём остаются JSON-протоколы, SQL-примеры и снимки окон.
Это проверка GUI из исходников; установленный EXE проверяется отдельными
встроенными smoke-сценариями.

С `--matrix` тот же сценарий проверяет «Итоговую оптимизацию»: один закрытый
снимок, четыре варианта, 14 прогонов и 15 одноразовых БД при двух сериях.
Сверяются вручную рассчитанные результаты всех команд и итоговые строки;
`--domain retail` позволяет повторить только одну схему.
Нативная встроенная `--workflow-smoke-test` с дополнительным
`PQO_SMOKE_OPTIMIZATION=1` после обычного маршрута выполняет и эту проверку.
Она по-прежнему требует известный синтетический `pqo_insert_source`, отдельные
настройки, каталог артефактов и `PQO_WORKFLOW_COPY_CONFIRMED=1`.

На известных синтетических `pqo_university_unseen`/`pqo_university_index_lab`
GUI-проверки `--transaction-replay-smoke-test` и
`--transaction-select-rewrite-smoke-test` также принимают
`PQO_SMOKE_JOIN_REPLAY=1`: выбирается комплектный `university-join-replay.sql`.
Нужны отдельный `PQO_SETTINGS_FILE`, каталог `PQO_APP_DATA_ROOT` и соответствующие
подтверждения `PQO_REPLAY_COPY_CONFIRMED=1`, `PQO_REPLAY_REFERENCE=pqo_university_index_lab`
либо `PQO_SELECT_REWRITE_COPY_CONFIRMED=1`,
`PQO_SELECT_REWRITE_REFERENCE=pqo_university_index_lab`. Источник профиля должен
быть `pqo_university_unseen`, разрешённая схема — только `university`.
Проверки исполняют реальные DML на своих копиях; рабочий профиль использовать нельзя.
`PQO_SMOKE_ISOLATION_REPLAY=1` вместо JOIN-флага выбирает
`university-isolation-savepoints.sql`: нативные проверки дополнительно сверяют
фактический REPEATABLE READ и сохранение ROLLBACK TO при индексной пробе и замене SELECT.

`tests/test_transaction_replay.py` также проверяет видимость между двумя
подключениями для четырёх уровней изоляции, отсутствие преждевременного снимка
из служебной настройки тайм-аута, наследование режимов эталона, READ ONLY DEFERRABLE,
вложенные/повторные SAVEPOINT, полный ROLLBACK и реальный отказ 40001 с очисткой.
Все записи этих тестов направляются в собственные временные лабораторные БД.

`tests/test_transaction_defaults.py` использует тот же явный флаг
`PQO_DISPOSABLE_REPLAY_TESTS=1`. Проверяются serial, обе формы identity,
константные/неиспользуемые/запрещённые вызываемые DEFAULT, неявные столбцы,
SAVEPOINT и полный ROLLBACK, несовпадение SELECT, отмена после выдачи номера,
отрицательный шаг последовательности и сохранность номеров эталона.
Для нативных GUI-проверок этого сценария сначала создайте отдельный стенд
`python -m pqo.unseen_database create-defaults`, затем задайте
`PQO_SMOKE_DEFAULTS_REPLAY=1`, источник `pqo_defaults_source`, схему `retail`
и соответствующий `PQO_REPLAY_REFERENCE`/`PQO_SELECT_REWRITE_REFERENCE` равным
`pqo_defaults_index_lab`. Подтверждения и изолированный профиль обязательны,
как в описанных выше проверках. Строки, выданные ID и состояния последовательностей
сверяются во всех шести фазах; рабочие БД и настройки не меняются.

UPSERT проверяется в `tests/test_transaction_upsert.py` с тем же флагом
`PQO_DISPOSABLE_REPLAY_TESTS=1`: DO NOTHING/UPDATE/WHERE/RETURNING, EXCLUDED и псевдонимы,
составные и nullable ключи, NULLS NOT DISTINCT, DEFAULT обеих ветвей, четыре уровня
изоляции, COMMIT/ROLLBACK/SAVEPOINT, ошибка 21000, отмена и замена SELECT.
Проверяется порядок DEFAULT VALUES и ON CONFLICT после разбора, подстановки параметров
и формирования замены: генератор SQL не должен переставлять эти части команды.

Для нативного сценария создайте стенд `python -m pqo.unseen_database create-upsert`.
Задайте `PQO_SMOKE_UPSERT_REPLAY=1`, источник `pqo_upsert_source`, схему `retail`,
эталон `pqo_upsert_index_lab` в соответствующем подтверждённом режиме GUI-проверки.
Остальные флаги сценария JOIN/isolation/defaults отключите. Рабочий профиль не используется.

`tests/test_transaction_insert_select.py` добавляет проверки прямого SELECT/JOIN,
агрегатов, раскрытия звёздочек по каталогам, неявных столбцов, самовставки,
пустого источника, явного NULL, предыдущих UPDATE, UPSERT и SAVEPOINT.
Проверяются четыре уровня изоляции, замена отдельного SELECT, отмена и превышение
лимита строк. В отдельной пробе новый индекс меняет порядок источника:
бизнес-проекции совпадают, но автоматические ID связываются с другими строками.
Такая проба обязана отклонить рекомендацию по итоговым данным.

Нативный сценарий: `python -m pqo.unseen_database create-insert-select`,
`PQO_SMOKE_INSERT_SELECT_REPLAY=1`, источник `pqo_insert_source`, схема `retail`,
эталон `pqo_insert_index_lab`; остальные флаги выбора сценария отключены.
Оба GUI-режима проверяют шесть новых копий с одинаковым закрытым снимком:
индекс на источнике и замену самостоятельного SELECT при неизменном INSERT SELECT.

`tests/test_transaction_joined_dml.py` с `PQO_DISPOSABLE_REPLAY_TESTS=1` проверяет
UPDATE FROM/DELETE USING: составные немедленные уникальные ключи, LEFT/self JOIN,
списки источников, повторные совпадения DELETE, RETURNING, вызываемые DEFAULT,
serial, видимость предыдущей записи, четыре уровня изоляции и SAVEPOINT/ROLLBACK.
Отдельно проверяются отказ до копирования при неоднозначности/отложенном UNIQUE,
отмена после записи, ошибка 23505 и четырёхвариантная проверка с заменой SELECT.
Фикстуры создаются тестами; исходная БД и эталон остаются неизменными.

Нативный сквозной сценарий на существующем стенде INSERT SELECT выбирается
флагом `PQO_SMOKE_JOINED_DML=1` вместе с `--workflow-smoke-test`.
Он использует `retail-joined-dml-savepoints.sql`: UPDATE FROM, INSERT SELECT/UPSERT,
DELETE USING внутри откатываемой точки и замену SELECT 8.
`PQO_SMOKE_OPTIMIZATION=1` добавляет четырёхвариантное сравнение на одном снимке.
Используйте отдельные `PQO_SETTINGS_FILE` и `PQO_APP_DATA_ROOT`; после проверки
сверьте исходную БД, результаты, номера последовательностей и удаление всех
одноразовых копий. Подготовленные рабочая БД и эталон остаются для проверки;
удалять их можно только по записанным точным имени, OID и владельцу.

Восстановление подключения проверяется в `tests/test_transaction_auth.py`:
отсутствующий/неверный пароль, отмена ввода, смена профиля/SQL, блокировка действий
на время повторного EXPLAIN и отсутствие пароля в настройках. С флагом
`PQO_UNIVERSITY_TESTS=1` выполняется реальное получение планов примера с joined DML
после ошибки аутентификации; данные эталона сверяются до и после.
`PQO_SMOKE_AUTH_RECOVERY=1` добавляет эту проверку к нативному
`--workflow-smoke-test` на отдельном профиле и собственном стенде.

`tests/test_transaction_cte.py` с `PQO_DISPOSABLE_REPLAY_TESTS=1` проверяет
области видимости, цепочки, повторные ссылки и оба вида материализации,
агрегаты/NULL, CTE перед INSERT/UPDATE/DELETE, звёздочки/DEFAULT/serial,
четыре уровня изоляции, SAVEPOINT и полный ROLLBACK. Проверяются отказ при
неоднозначности до создания копий, EXPLAIN без записи, отмена и ошибка 22012,
сравнение четырёх вариантов и отказ неправильной замене SELECT.

`PQO_SMOKE_CTE=1` выбирает `retail-cte-savepoints.sql` в нативной проверке
`--workflow-smoke-test`. SELECT 8 проходит отдельное сравнение MATERIALIZED /
NOT MATERIALIZED, затем замена проверяется в полном контексте записи и отката.
Остальные подтверждения/изоляция профиля и очистка — как в сценарии joined DML.

`tests/test_transaction_predicates.py` проверяет корреляцию EXISTS/NOT EXISTS,
IN/NOT IN, NULL и дубликаты, затенение псевдонимов, границы CTE, раскрытие
звёздочек, сохранение команд и отказ скалярным/побочным конструкциям.
С `PQO_DISPOSABLE_REPLAY_TESTS=1` добавляются прогоны с записью на всех уровнях
изоляции, SAVEPOINT/ROLLBACK, EXPLAIN и кандидаты, полный контроль четырёх
вариантов, отмена, ошибки, очистка и отказ неправильной замене NOT IN.

`PQO_SMOKE_PREDICATES=1` выбирает `retail-predicate-savepoints.sql` в нативном
`--workflow-smoke-test`: SELECT 8 проверяется отдельно, затем замена JOIN на
EXISTS проходит полный контекст записи, UPSERT, SAVEPOINT и отката. Для общего
сравнения четырёх вариантов дополнительно задаётся `PQO_SMOKE_OPTIMIZATION=1`.

`tests/test_transaction_concurrency.py` с `PQO_DISPOSABLE_REPLAY_TESTS=1`
проверяет реальное ожидание записи, взаимоблокировку 40P01, конфликты 40001,
повторное чтение на четырёх уровнях изоляции, тайм-аут команды и отмену в фоне.
Перед удалением копии независимо читаются итоговые строки; проверяются исходные
данные эталона и отсутствие всех собственных БД. Ошибка 22012, неверное ожидание
блокировки, неподдерживаемые триггеры, расписания и отсутствие пароля не должны
выглядеть как успешный запуск. UI-проверки покрывают запрет повторного старта,
блокировку остальных действий, экспорт и отбрасывание устаревшего результата.

`--concurrency-smoke-test` выполняет семь сценариев через настоящий интерфейс
на известном синтетическом `pqo_insert_source` и эталоне `pqo_insert_index_lab`.
Нужны отдельные `PQO_SETTINGS_FILE`, `PQO_APP_DATA_ROOT` и явный
`PQO_WORKFLOW_COPY_CONFIRMED=1`; другие источники блокируются. Сценарии включают
четыре примера, READ COMMITTED для повторного чтения, REPEATABLE READ для
конфликтующей записи и отмену. В протоколе остаются фактические отчёты, строки
из двух известных синтетических записей, сведения о busy-блокировке UI и очистке.

`tests/test_transaction_resources.py` проверяет включённые счётчики корня без
двойного сложения детей, неизвестные значения вместо нулей, память операторов,
реальные temp spill и WAL, изоляцию копий, RETURNING, INSERT SELECT/UPSERT/CTE,
SAVEPOINT, последовательности и все уровни изоляции. Неправильная замена SELECT
и несовпадение числа выходных строк блокируют подтверждение профиля. Проверяются
отмена, ошибка выражения и отказ неподдерживаемым триггерам до клонирования.
Отдельный сквозной тест сравнивает UPDATE, DELETE и SELECT с альтернативными
фильтрами, итоговые записи триггера аудита и отказывает при расхождении данных.
Для PostgreSQL-проверок нужен `PQO_DISPOSABLE_REPLAY_TESTS=1`.

`--resources-smoke-test` на изолированном профиле и известном синтетическом
`pqo_insert_source` выполняет семь сценариев через реальный интерфейс: исходный,
индексы, SELECT, оба изменения, spill, полный ROLLBACK и отмена. Используется
`PQO_WORKFLOW_COPY_CONFIRMED=1`, эталон `pqo_insert_index_lab`; перед удалением
собственных копий независимо читаются две известные записи. Проверяются
счётчики, состояния, запрет повторного старта и отсутствие изменений источника,
эталона, пользовательских настроек и модели. Установленный EXE проверяется
отдельно от запуска из исходников.
