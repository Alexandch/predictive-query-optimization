# Общий фиксированный контроль production и plan-v1

Протокол от 27.10.2026. Назначение — сравнить два замороженных артефакта
на одних SQL и свежих общих целевых временах. Модели не переобучаются,
калибровка не применяется. Это отдельная проверка, а не задним числом
изменённое правило допуска предыдущего эксперимента.

## Состав, зафиксированный до замеров

Всего 76 SQL:

- 36 новых SQL — 12 семейств по три масштаба, авиация и торговля;
- 20 обычных SQL из разных семейств, сохранённых после восстановления планов;
- 20 SQL из разных семейств, отсутствующих в отфильтрованном обучении plan-v1.

Для известных SQL выбор одного примера на семейство и самих семейств
детерминирован хэшем, без использования фактического времени или ошибок
моделей. Обычная часть ограничена двумя JOIN, одним подзапросом и отсутствием
OVER(...). Известные запросы предназначены для поиска регрессий: они не
считаются независимым контролем обобщения. Исключённые запросы могли быть
известны production, но не входить в обучение кандидата — это существенная
асимметрия, которую проверка намеренно выявляет.

Новые SQL описаны в `paired_workload.py`: детальный top-N, групповые отчёты,
сводки по отобранным участникам, разные оконные сортировки, двухступенчатые
агрегации и top-N внутри групп. Проверяется отсутствие совпадений
нормализованного SQL с обучением и четырьмя предыдущими экспериментами.
Новые тексты не гарантируют совершенно новых структур: типовые паттерны
SQL пересекаются. Перенос на неизвестную БД не проверяется.

Manifest фиксирует точные SQL, порядок, когорты, seed, хэши обоих артефактов
и исходных CSV, параметры подключения без пароля, таймауты и критерии.
Порядок запросов перемешан фиксированным seed 20261027.

## Выполнение

Сначала обычный EXPLAIN и каталог БД формируют один набор признаков для
каждого SQL. Обе модели получают эти признаки, и **все прогнозы сохраняются
до первого фактического замера**. История SQL и калибровка не используются.

Затем каждому SQL соответствуют один прогрев и три запуска EXPLAIN ANALYZE
в режиме только чтения. Общая медиана сравнивается с обоими прогнозами:
двух отдельных серий для моделей нет. Учитывается используемый приложением
Actual Total Time корневого узла, не время передачи результатов клиенту.
Длительность расчёта модели записывается отдельно и не смешивается с целью.
Таймаут по умолчанию 30 секунд на оператор.

При ошибке или таймауте SQL остаётся в результатах, а полный контроль
не считается пройденным. Возобновление дописывает только отсутствующие
запросы, не перемеряя неудобные или уже завершённые случаи. Перед
возобновлением проверяются протокол, модели, CSV и идентичность кейсов.

## Критерии парной проверки

Установлены до замеров, в `paired_regression.CRITERIA`:

- на новых SQL MAE должна быть ниже как минимум на 10%, median Q-error
  и доля ошибок до 20% — не хуже;
- отдельно в каждой известной когорте MAE и P90 абсолютной ошибки могут
  вырасти не более чем на 10%, median Q-error — на 5%, доля ошибок до 20%
  может снизиться не более чем на пять процентных пунктов;
- верхняя граница ориентировочного парного bootstrap-интервала разницы
  абсолютных ошибок по новым семействам должна быть ниже нуля.

Bootstrap выполняет 10 000 повторов с фиксированным seed. Сначала парные
разницы усредняются внутри семейства, затем пересэмплируются семейства:
три масштаба не выдаются за три независимые структуры. Двенадцать
искусственно составленных семейств — небольшая и не случайная выборка,
поэтому интервал не доказывает универсальной точности модели.

Даже положительное `paired_quality_pass` не перезаписывает модель
и не отменяет провал предыдущего внутреннего правила. В отчёте явно
сохраняются `automatic_promotion=false` и
`previous_internal_gate_overridden=false`.

## Запуск

```powershell
# Только зафиксировать протокол, без выполнения запросов
.\.venv\Scripts\python.exe scripts/paired_regression_control.py
# Проверить тот же протокол и выполнить контроль
.\.venv\Scripts\python.exe scripts/paired_regression_control.py --run
# Только если первый запуск прерван
.\.venv\Scripts\python.exe scripts/paired_regression_control.py --run --resume
```

Каталог: `artifacts/paired-regression-20261027`. Manifest, прогнозы,
checkpoint измерений и report.json локальные, исключены из Git. Для
воспроизведения нужны указанные артефакты, CSV и тестовая БД.

## Полученные результаты

Все 76 SQL завершились успешно, без исключений и таймаутов; сохранены
228 фактических измерений после прогрева. Оба прогноза получены до измерений.
Параметры и критерии в процессе проверки не менялись.

Новые SQL (36 запросов):

- MAE: production 353,79 мс, plan-v1 299,03 мс — улучшение на 15,5%;
- P90 абсолютной ошибки: 1086,62 → 685,25 мс;
- median Q-error: 1,907 → 1,542;
- доля ошибок до 20%: 8,3% → 19,4%.

Сохранённые обычные SQL (20 запросов):

- MAE: 108,66 → 63,83 мс;
- P90: 182,46 → 153,14 мс;
- median Q-error: 2,513 → 2,509;
- доля ошибок до 20%: 0% → 5%.

SQL, исключённые из обучения plan-v1 (20 запросов):

- MAE: 72,09 → 79,32 мс — рост примерно на 10,04%;
- P90: 141,20 → 167,45 мс — рост на 18,6%;
- median Q-error: 2,903 → 2,859;
- доля ошибок до 20%: 0% у обеих моделей.

Парная разница средних ошибок новых семейств — −54,76 мс; ориентировочный
95%-й bootstrap-интервал: [−154,40; +46,10] мс. Он пересекает ноль, поэтому
устойчивое преимущество по семействам не подтверждено. Регрессионная часть
исключённых SQL также не прошла допуск. `paired_quality_pass=false`.
Ни прежнее правило допуска, ни рабочие веса не изменены.

Время только вычисления модели (без EXPLAIN и чтения каталога), медиана:
production 5,66 мс, plan-v1 5,15 мс. Это наблюдения данного запуска,
а не гарантированная задержка приложения.

Фильтр обычных запросов формальный: среди выбранных SQL есть GROUP BY/CUBE.
Их не исключали вручную после фиксации протокола. Известность определяется
историческим обучающим пулом, а не гарантией, что каждый такой SQL был
в обучении обеих моделей; например, часть поздних обучающих семейств
появилась уже после фиксации production-весов.

## Диагностика сдвига исторических целевых времён

После завершения контроля отдельный `scripts/audit_paired_targets.py`
сопоставил новые медианы с медианами старого исходного CSV для тех же SQL.
Он не корректирует прогнозы и не меняет решение парной проверки.

- Сохранённая когорта: медиана отношения старого времени к свежему — 2,63;
  для 19 из 20 SQL старое время больше свежего более чем в 1,5 раза.
- Исключённая когорта: медиана отношения — 2,78; соответствующее превышение
  наблюдается на всех 20 SQL.
- Обе модели завысили прогноз на 39 из 40 известных запросов.

Это свидетельство сдвига целевой переменной на выбранных SQL, а не
доказанная причина для всей базы обучения. Из этого сравнения нельзя
установить, связан ли сдвиг с нагрузкой, кэшем, окружением или различиями
старого протокола измерений. Порог 1,5 использован только в последующей
диагностике, не является условием допуска. Результат сохранён отдельно
в historical-drift.json; report.json и прогнозы не пересчитывались.

```powershell
.\.venv\Scripts\python.exe scripts/audit_paired_targets.py
```

Обоснованный следующий этап — аудит единиц и протокола исходных замеров,
фиксация окружения и получение актуальных обучающих времён с отдельным
новым контролем. Текущие 76 SQL не следует добавлять в обучение и затем
повторно объявлять независимой проверкой. Одного общего коэффициента,
подобранного по этим результатам, недостаточно для доказательства точности.
