# Демонстрация курсового проекта

Три сценария из фиксированного контрольного прогона, а не специально
подобранные после изменения данных. Начальные результаты и ограничения:
[контроль 29.10.2026](optimization-control-20261029.md).

## Подготовка

1. Запустить PostgreSQL с данными проекта и приложение:

   ```powershell
   .venv\Scripts\python.exe -m pqo.desktop
   ```

2. Проверить подключение к `query_optimizer`; нужны схемы aviation, retail,
   logistics и право создания индексов для индексной демонстрации.
3. Если ранее приложение применило индексный план — откатить его штатной
   кнопкой. Не удалять неизвестные или чужие индексы ради демонстрации.
4. Установить порог рекомендации **5 мс**, минимальный выигрыш **2 мс** и **5%**.
   Стандартные 50 мс могут корректно пропустить короткий индексный пример.
5. Включить сохранение в историю pqo и локальный журнал переписываний, если
   нужны записи для показа. SQL и литералы сохраняются локально. Измерения могут
   обновлять профиль БД, но обучение модели автоматически не запускается.

Время в примерах — результаты прежнего локального прогона, не обещание
получить те же числа на защите. Подготовить резервные снимки собственных
фактических результатов, не выдавая их за текущий запуск.

## 1. Индекс: проверка → применение → откат

Открыть `examples/defense/01-logistics-index.sql` и вставить в левый редактор.

- выполнить быстрый ML-прогноз; пояснить, что это оценка, а не выполнение SQL;
- выполнить глубокий анализ индексов; показать проверенные варианты, причины
  отказов, подтверждённый план и фактические замеры;
- показать размер индекса, время построения и предупреждение о цене записи:
  ускорение SELECT не доказывает отсутствие замедления INSERT/UPDATE/DELETE;
- нажать «Применить проверенные индексы и измерить», дождаться завершения;
- откатить применённые индексы штатной кнопкой, показать повторный замер;
- открыть историю: выбрать запись и показать протокол индексных проб.

Глубокая проверка создаёт пробные индексы с последующим ROLLBACK. Отдельная
кнопка применения сохраняет управляемый индекс до явного отката. Эти операции
не следует смешивать при объяснении. В контрольном прогоне: 26,866 → 0,029 мс.
Если PostgreSQL уже использует подходящий существующий индекс, отсутствие новой
рекомендации — допустимый результат; не менять данные ради нужного ответа.

## 2. Переписывание: два редактора и независимая проверка

Открыть `examples/defense/02-aviation-rewrite.sql`.

- выполнить быстрый прогноз, затем «Проверить безопасное переписывание SQL»;
- показать исходный текст слева и варианты справа: COUNT(*) > 0 → EXISTS,
  удаление внутреннего ORDER BY и их сочетание;
- переключить список вариантов: показать разницу текста, медианы и причины
  отказа; сам выбор SQL не запускает его и не меняет левый редактор;
- выбрать принятый вариант и применить его с повторным замером;
- вернуть исходный SQL штатной кнопкой и дождаться контрольного замера;
- показать локальный журнал проверки.

В контроле сочетание дало 949,183 → 12,162 мс. Применение разрешается только
после совпадения мультимножеств строк на текущем снимке и достаточного выигрыша.
EXCEPT ALL сохраняет проверку дубликатов, но не доказывает эквивалентность для
любых данных и не проверяет порядок строк. Лучшим считается вариант с меньшей
наблюдаемой медианой среди прошедших пороги, не математически оптимальный SQL.

## 3. Обоснованный отказ от изменения

Открыть `examples/defense/03-retail-no-change.sql`.

- выполнить быстрый прогноз и глубокую проверку;
- показать, что точечный поиск по первичному ключу уже короткий: индекс не
  рекомендуется при времени ниже порога;
- запустить проверку переписывания: подходящих безопасных правил нет, поэтому
  фактическая проверка вариантов не запускается и кнопка применения недоступна.

Это штатный отрицательный контроль. Система должна уметь отказаться от
неподтверждённого изменения, а не предлагать индекс на каждый SELECT.

## Как объяснить прогноз и ошибки

До измерения показывается оценка модели, после проверки — отдельный факт.
Если подпись сообщает оценку по предыдущим измерениям этого SQL, назвать её
именно так: это не независимый прогноз нового запроса. Не удалять профиль
пользователя для искусственного улучшения демонстрации.

Если запрос превысил лимит, показать остановку по тайм-ауту и отсутствие точного
времени; не называть лимит фактическим временем выполнения. Для показа отмены
использовать штатную кнопку и дождаться отката, затем проверить доступность
элементов управления. Не запускать одновременно второй анализ.

## Повторяемая диагностика без интерфейса

```powershell
.venv\Scripts\python.exe -m pqo.optimization_control --output artifacts/defense-rehearsal-01 --timeout-ms 8000 --repetitions 3
```

Нужен новый каталог. Команда сохраняет SQL, модель, настройки, результаты и
отказы, проверяет неизменность состава индексов; постоянно индексы не применяет.
Данные диагностического журнала исключены из обучения. Это не независимый
эксперимент обобщающей способности моделей на неизвестных БД.
