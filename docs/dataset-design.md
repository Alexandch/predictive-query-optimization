# Проектирование датасета PostgreSQL

## Единица наблюдения

Одна строка датасета соответствует одному выполнению одного SQL-запроса.
Одинаковый текст запроса допускается выполнять несколько раз: повторные замеры
нужны для оценки разброса времени из-за состояния кэша и нагрузки системы.
Перед обучением повторные измерения одинакового SQL агрегируются медианой.
Медиана устойчивее среднего к единичным задержкам операционной системы и БД,
поэтому модель прогнозирует типичное, а не случайно завышенное время.

Целевая переменная — `actual_total_time_ms` из корневого узла результата
`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`. Она не должна попадать в обучающий
вектор `X`.

## Статические признаки SQL

- `query_length` — длина запроса после удаления внешних пробелов;
- `join_count` — общее число операций JOIN;
- `where_condition_count` — число атомарных условий во всех WHERE;
- `subquery_count` — число вложенных SELECT, включая CTE и EXISTS;
- `has_group_by`, `has_order_by`, `has_distinct` — признаки конструкций SQL;
- `table_reference_count` — число ссылок на физические таблицы;
- `unique_table_count` — число различных физических таблиц;
- `select_expression_count` — число выражений во всех списках SELECT;
- `aggregate_function_count` — число агрегатных функций;
- отдельные счётчики INNER, LEFT, RIGHT, FULL и CROSS JOIN.

Разбор выполняется по AST PostgreSQL-диалекта, а не регулярными выражениями.
Поэтому ключевые слова внутри строк и комментариев не искажают признаки.

## Признаки плана выполнения

- начальная и полная стоимость корневого узла;
- оценка числа строк и ширины результата;
- суммарное оценочное число строк по всему дереву;
- число узлов, максимальная глубина и число используемых отношений;
- тип корневой операции;
- числа последовательных, индексных, index-only и bitmap-сканирований;
- числа hash-, merge- и nested-loop-соединений;
- числа операций сортировки и агрегации;
- суммарные `shared_hit_blocks`, `shared_read_blocks`, `temp_read_blocks` и
  `temp_written_blocks` по всем узлам дерева.

Категориальный `root_node_type` будет кодироваться в ML-пайплайне. Счётчики
буферов агрегируются по дереву, поскольку значения дочерних операций отражают
фактический профиль ввода-вывода запроса.

Счётчики буферов сохраняются для исследовательского анализа, но исключаются из
входного вектора прогнозной модели: они появляются только после фактического
выполнения `EXPLAIN ANALYZE`. При пользовательском прогнозе приложение получает
оценочные признаки через `EXPLAIN (FORMAT JSON)` и не выполняет сам запрос.

## Правила безопасного сбора

- сборщик принимает только один SELECT или WITH-запрос за вызов;
- `EXPLAIN ANALYZE` выполняется в транзакции `READ ONLY`;
- учётные данные передаются через переменные окружения;
- исходный SQL, JSON-план и оба набора признаков сохраняются вместе;
- все временные значения новой версии измеряются в миллисекундах.

## Методика итогового эксперимента

Каждый параметризованный запрос выполняется несколько раз, после чего повторы
одинакового SQL агрегируются медианой. Одинаковые SQL-тексты не разделяются
между обучающей и контрольной выборками. Гиперпараметры подбираются групповой
кросс-валидацией только на обучающей части. Дополнительно проводится более
сложный стресс-тест, в котором целые структурные шаблоны отсутствуют в
обучении.
