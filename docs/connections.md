# Подключения PostgreSQL — 0.8.40

У приложения два независимых назначения подключения:

- исследуемая БД — исходный SQL, оценочные планы, прогноз, индексные и SQL-пробы;
- служебная БД — схема `pqo`, история и решения по рекомендациям всех источников.

Они могут находиться на разных серверах. Внешняя исследуемая БД не требует
установки объектов приложения. Это поддержка PostgreSQL, не MySQL/SQL Server.
Пароли не включаются в профили, реестр, сведения об источнике и экспорт истории;
после перезапуска для нестандартных подключений их нужно ввести заново.

## Локальная демонстрация

На данном стенде отдельная `pqo_service` подготовлена на localhost:55432.
Прежняя история в `query_optimizer` и университетских БД не удалена и не
переносится автоматически: для старых строк нельзя достоверно угадать источник.
Новая служебная история начинается отдельно; модель XGBoost и резервные веса
при переключении источника не меняются.

1. Откройте «Настройки». Вверху выберите текущую университетскую БД либо
   профиль «Учебная БД» (`query_optimizer`).
2. Нажмите «Подключиться и загрузить схемы». Для `pqo_university_unseen`
   предметная схема одна — `university`; для `query_optimizer` доступны
   `aviation`, `retail`, `logistics`, `chbenchmark`, `pagila`. Отметьте нужные.
3. Ниже отдельно проверьте служебное подключение к `pqo_service`.
4. Нажмите «Сохранить настройки». Пароли сохранятся только в памяти сеанса.
5. Во вкладке «Анализ» включите «Сохранять в служебную историю» и выполните
   быстрый прогноз. В «Истории» обновите список: видны записи разных источников.
   Хост/порт/БД показаны в колонке «БД источника» и в карточке выбранной записи.

Верхний список «БД» переключает профили без переписывания всех полей.
При смене источника прежние планы, подтверждённые переписывания и кнопки их
применения сбрасываются. SQL слева остаётся: проверьте, что таблицы существуют
в новом источнике. На время фоновой работы переключение блокируется.

## Другой локальный или внешний сервер

1. «Настройки» → «Добавить подключение» → понятное название профиля.
2. Укажите действительные хост, порт, имя существующей БД и роль; введите пароль.
3. Настройте SSL по требованиям сервера. `require` требует шифрование;
   `verify-full` дополнительно проверяет доверенный CA и имя сервера, нужен
   соответствующий корневой сертификат. Режим по умолчанию следует libpq,
   он не означает обязательную проверку сертификата.
4. Загрузите схемы, отметьте нужные и сохраните настройки.
5. Введите SQL с явными именами схем, например `sales.orders`. Схема `public`
   не равна всем схемам сервера; впишите или выберите каждую нужную схему.

Сейчас допустимы имена схем из латинских букв, цифр и `_`, начинающиеся с
буквы/`_`; нестандартные кавычечные имена пока не поддерживаются анализатором.
Выбор схем — область работы анализатора, а не замена разграничению прав СУБД.

Сеть/firewall, `pg_hba.conf`, доступность порта, VPN и сертификаты должны
разрешать соединение. Параметры реального внешнего сервера пользователь
предоставляет сам; тестов на произвольном облачном сервере в выпуске нет.

## Подготовка служебной БД на другом стенде

В блоке «Служебная БД» укажите отдельные параметры.

- «Проверить служебную БД» только проверяет подключение и готовность схемы;
- «Создать служебную БД» после подтверждения создаёт пустую БД через `postgres`;
  нужны `CREATEDB` и доступ к `postgres`. Существующая БД не заменяется;
- «Подготовить служебную схему» после отдельного подтверждения создаёт/обновляет
  только служебные объекты `pqo` (миграции 001–009, 012–014), без предметных схем
  и учебных данных. Нужны соответствующие DDL-права на служебную БД.

Без прав создания администратор может подготовить служебную БД отдельно, а
в приложении использовать роль с необходимыми правами чтения/записи истории.
DDL не выполняется при выборе профиля, загрузке схем или быстром прогнозе.
Если история недоступна, готовый результат остаётся на экране с предупреждением;
автоматической записи в исследуемую БД вместо служебной нет.

Обычный прогноз использует `EXPLAIN` без `ANALYZE` и метаданные источника.
Глубокая проверка отдельно выполняет SELECT и временно создаёт индексы с откатом;
она требует прав и ресурсов. Для производственной базы используйте копию.
DML-транзакции остаются ограничены проверенным форматом и одноразовыми копиями:
профиль внешнего сервера сам по себе не даёт разрешение на выполнение DML.

## Проверка реализации

`tests/test_connections*.py` проверяют профили без секретов, несколько схем,
SSL/произвольный endpoint, сброс устаревших результатов и раздельную маршрутизацию.
Опциональный PostgreSQL-набор создаёт две новые предметные БД без `pqo` и одну
служебную: центральная история, отсутствие DDL/изменения данных источника,
отказ сервиса, откат индексной пробы и запрет переиспользования ID другой БД.
Все три лабораторные БД затем удаляются с проверкой имени/OID.

На доверенном локальном стенде с CREATEDB:

```powershell
$env:PQO_CONNECTION_INTEGRATION_TESTS='1'
.venv/Scripts/python.exe -m pytest tests/test_connections_postgres.py
```
