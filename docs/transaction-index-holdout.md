# Контроль общих индексов на новых SELECT — 0.8.33

## Зачем нужен отдельный контроль

Повторение того же SQL проверяет повторяемость, но не перенос пользы на другие
запросы/значения. Поэтому контрольный набор отделён от генерации кандидатов и
их сравнения. Сначала фиксируется один вариант индексов, затем открывается
ввод новых SELECT. На контроле не выбираются другой индекс, пороги, веса или
лучшее сочетание. Результат не меняет предпочтение подбора и не обучает модель.

## Как попробовать

1. В «Транзакциях» открыть `examples/transactions/university-index-comparison.sql`,
   выполнить разбор, запросить планы и собрать индексных кандидатов.
2. Отметить `enrollments(student_id, registered_at)` и
   `enrollments(offering_id, registered_at)` без INCLUDE. Указать заранее
   подготовленную отдельную копию `pqo_university_index_lab`, подтвердить её.
3. Выполнить сравнение, обычно с двумя сериями. В таблице выбрать строку
   измеренного варианта, где подтверждена польза для чтений. Требуется полное
   сравнение и подтверждённые откаты всех проб, а не частичный результат.
4. Открыть внутреннюю вкладку «Контроль SELECT», нажать
   «Зафиксировать вариант выбранной строки сравнения». До фиксации редактор
   контроля недоступен. После неё переключение строк сравнения не меняет
   зафиксированные индексы. При нехватке ширины вкладки прокручиваются стрелками.
5. Загрузить `examples/transactions/university-index-holdout.sql` либо ввести
   собственные 1–20 новых SELECT с конкретными значениями. Пример предназначен
   только для синтетической копии, не production. Значения отличаются от подбора:
   student_id 19007/19008/19009, offering_id 777, другие LIMIT/условие IN.
6. Нажать «Проверить контроль на копии», прочитать подтверждение. Выполняются
   две серии A/B/A одного и того же зафиксированного набора индексов, три
   замера плюс прогрев в каждой фазе. Другие варианты не испытываются.
7. Слева посмотреть итоги двух серий (таблица ниже редактора; панель при
   необходимости прокручивается), справа — состав индексов, происхождение
   выбора, A1/B/A2 каждого SELECT, причины отказа и подтверждение отката.

Для другой БД имя и пригодность копии подтверждает пользователь. Другое имя
БД не доказывает, что она тестовая или действительно является копией источника.
Подготовка университетской копии: [инструкция](transaction-index-trials.md).

## Два разных вывода

«Контроль пройден» означает: обе контрольные серии прошли пороги, проверки
регрессии/дрейфа/использования индексов, полный набор измерен, откаты подтверждены.

«Подбор + контроль пройдены» дополнительно требует, чтобы зафиксированный
вариант был устойчивым однозначным предпочтением повторных серий подбора.
Если выбрана другая строка или при подборе не было устойчивого предпочтения,
она фиксируется как **ручная гипотеза**. Её можно проверить, но положительный
контроль не исправляет слабое/неустойчивое подтверждение подбора и не назначает
нового победителя. Постоянного применения индексов нет в обоих случаях.

В контрольном наборе у всех SELECT вес 1. Веса подбора (например, 10:1) не
переносятся на другие команды. Измеряется сумма медиан самостоятельных чтений,
не время транзакции, не исполнение цикла/конкурирующей нагрузки. Пара проверяется
вместе против отсутствия пробных индексов; добавочная польза каждого её индекса
на контроле отдельно не измеряется, минимальность состава не доказывается.

## Что проверяется до подключения

Разрешены только 1–20 самостоятельных SELECT/UNION/INTERSECT/EXCEPT, не более
500000 символов. BEGIN/COMMIT/ROLLBACK, SET, DDL, DML, изменяющие CTE и SELECT INTO
в контроле запрещены, а не пропускаются. Нужны схема.таблица, разрешённая схема,
поддержанные безопасные функции; блокировки строк, неизвестные функции и
неразрешённые параметры отклоняются теми же guards, что в индексных пробах.

Контроль пока принимает готовый SQL с явными значениями. Собственный ввод
типов для `$1` в этой вкладке не добавлен: параметры не угадываются, исходные
привязки из «Параметры SQL» к другим контрольным командам не копируются.

После нормализации AST-текста без комментариев отклоняются повторы внутри
контроля и любой SELECT, совпавший с чтением подбора. Частично новый набор,
содержащий хотя бы один такой повтор, также отклоняется. Иные литералы
разрешены, включая ту же структуру запроса с новыми значениями. Это проверка
текстового повтора после разбора, не доказательство семантической независимости,
непересечения строк, равномерности значений или репрезентативности production.
Обязательное наличие чтения таблиц выбранных индексов и применимость ведущих
ключей проверяются прежним механизмом проб; отсутствие применения даёт отказ.

Сравнение связано SHA-256 с точным эффективным SQL подбора и контекстом
подключения/разрешённых схем/тайм-аутов. Пароль не включается в digest.
Нельзя зафиксировать старый результат для другого SQL/подключения. Это связь
контекста, не снимок данных/каталога и не аутентификация внешнего отчёта.

## Одна попытка и границы независимости

Один вариант фиксируется один раз на текущее сравнение. Ошибки локального
ввода и отказ в диалоге не тратят попытку. После запуска она израсходована
даже при отмене, тайм-ауте или ошибке: нельзя подбирать вариант по увиденным
контрольным результатам. Редактор/загрузка/повторный запуск блокируются.

Изменение исходного SQL/привязок параметров/подключения/имени копии/весов/
числа серий/отмеченных кандидатов или новый подбор сбрасывает фиксацию,
контрольный текст и результат. Запоздавший callback не восстанавливает их.
Новые гипотезы после изучения контроля требуют нового, ещё не изученного
контрольного набора: старый набор уже стал частью разработки.

Приложение не может доказать, что пользователь раньше не видел набор или не
использовал его в другом запуске. Ограничение одной попытки — локальная защита
интерфейса в памяти, не глобальный журнал научного эксперимента. Backend API
stateless и сам по себе не запрещает повторные вызовы. Встроенные примеры —
демонстрация механизма, не скрытый бенчмарк после ознакомления с ними.

## Измерения и безопасность

Две контрольные серии имеют один общий бюджет 180 с плюс ограниченное
завершение/проверки отсутствия индексов. Пороги абсолютного/относительного
выигрыша фиксируются из выбранной пробы подбора, текущие поля UI не подменяют их.
Каждая проба остаётся отдельной rollback-only транзакцией и снимком копии,
не одной общей snapshot-транзакцией между сериями. Не допускайте внешнюю
нагрузку и изменение данных во время проверки.

Применяются [ограничения проб](transaction-index-trials.md): только явно
подтверждённая другая БД, временные один/два индекса, READ ONLY в фазах SELECT,
statement_timeout до 30 с/остатка бюджета, lock_timeout 1 с, откат и независимая
проверка отсутствия каждого созданного индекса, проверка общего размера после
создания (порог 64 МиБ, не гарантия расхода диска до создания). Существенная
регрессия отдельного чтения (>2 мс и >10%) или дрейф A1/A2 (>2 мс и >20%)
отклоняют соответствующую серию. Межсерийный размах базовых времён одновременно
>2 мс и >20% минимального значения блокирует общий положительный вывод.
В каждой контрольной серии должны использоваться все индексы сочетания.

Ошибка/отмена/отказ/неподтверждённый откат останавливают следующие пробы.
Полные измерения с отрицательной оценкой пользы сохраняются; вторая заранее
заданная серия всё равно может быть измерена, но положительного вывода при
отказе любой серии не будет. Образцы подбора и контроля не объединяются.

DML и состояние промежуточных записей не воспроизводятся, цена записи не
измеряется. READ ONLY не является песочницей для недоверенных функций,
операторов или расширений. SQL/значения и результаты живут только в текущем
анализе, не попадают автоматически в историю/обучение/настройки. Успешный
smoke-журнал не содержит SQL/значений; диагностические ошибки и экранные
планы могут раскрывать фрагменты, поэтому не используйте чувствительные данные.

## Проверки

```powershell
$env:PQO_UNIVERSITY_TESTS='1'
$env:PQO_TRANSACTION_TRIAL_TESTS='1'
.venv\Scripts\python.exe -B -m unittest discover -s tests -p 'test_transaction*.py' -q
```

Опт-ин сквозной тест приложения:

```powershell
$env:PQO_TRIAL_COPY_CONFIRMED='1'
$env:PQO_TRIAL_COPY_DATABASE='pqo_university_index_lab'
PredictiveQueryOptimization.exe --transaction-holdout-smoke-test
```

Он сначала выполняет реальное сравнение и фиксирует допустимый измеренный
вариант, затем загружает новый контрольный файл. Требует две технически полные
контрольные пробы/откаты и сохранность исходного SQL/сравнения/одноразового
состояния UI, но не положительный вывод контроля: польза зависит от нагрузки.
Если синтетический пример не дал ни одной подтверждённой пробы подбора,
тест завершится с объяснением, а не сфабрикует допуск. Отдельная реальная
проверка backend использует заранее заданную ручную гипотезу пары без
поддельных замеров подбора; проверяет строки и каталог источника/копии до/после.

`PQO_SMOKE_PREVIEW=1` дополнительно сохраняет снимки фактического UI теста
1740×1030 и 1280×800; это только синтетический opt-in сценарий, не обычный режим.

и межсерийный дрейф. GUI проверен с реальным queued worker: блокировка других
анализов, одноразовая попытка, сохранность подбора, очистка при изменении контекста
и отказ для запоздавшего callback. После правки компоновки отдельно повторены
все 20 GUI-тестов транзакционного блока, успешно.

В исходном сквозном прогоне ручной вариант 3 (пара) сохранил пользу на трёх

из-за дрейфа A1/A2 для SELECT 3, несмотря на большое уменьшение суммы.
Это демонстрационные повторные запуски для проверки кода/GUI, не несколько
независимых контрольных наборов и не обещание этих чисел в другой нагрузке.
