# Общие индексные кандидаты транзакции — 0.8.27

## Использование

На вкладке «Транзакции» открыть `examples/transactions/university-shared-index.sql`,
выполнить локальный разбор, получить оценочные планы, затем нажать
«Подобрать общие индексы (без создания)». Нужна тестовая БД `pqo_university_unseen`
с разрешённой схемой university. Прежний пример `university-inspection.sql`
тоже поддерживается.

Внизу появляются две внутренние вкладки: «Команды и планы» и «Индексные
кандидаты». Выбор кандидата показывает DDL, номера потенциально обслуживаемых
команд и связанные операции записи. Кнопки применения здесь намеренно нет:
ни один кандидат не считается проверенным ускорением.

## Как формируются кандидаты

Существующие планы связываются с тем же текстом транзакции и подключением.
Затем в READ ONLY/REPEATABLE READ читаются только системные каталоги:
обычные/секционированные таблицы, столбцы, индексы и счётчики активности.
Команды пользователя не отправляются на выполнение повторно, ANALYZE и DDL нет.

Для каждой области SQL отдельно рассматриваются прямые столбцы в равенствах,
простых диапазонах, ON и ORDER BY. Равенства помещаются перед диапазоном;
проверяются альтернативы порядка фильтр/сортировка. Сохраняются узкие кандидаты
и ограниченные варианты INCLUDE по столбцам проекции: не более трёх ключей и
трёх INCLUDE. Одинаковые кандидаты объединяются между командами; затем
отмечаются другие команды, где ведущий ключ встречается в подходящем условии.
Это структурная возможность поиска, не утверждение, что PostgreSQL выберет индекс.

Используется реальный список столбцов таблицы. Алиасы вложенных запросов не
смешиваются с внешними. Для CTE/подзапросов не угадывается происхождение
вычисленных столбцов, неоднозначные имена пропускаются. OR не превращается
в одно совместное равенство; функции над столбцом не считаются обычным
индексируемым условием. Покрытие вычислений и CTE пока неполное.

Три состояния:

- «к проверке» — подходящего безусловного покрытия ключей в каталоге не найдено;
- «только INCLUDE — спорно» — ключи уже покрыты, новый индекс добавил бы главным
  образом payload; это может быть неоправданным дублированием;
- «уже покрыт» — есть подходящий существующий индекс; новый дубликат не предлагается.

Для покрытия проверяются ведущий префикс ключей и доступность требуемых INCLUDE.
Частичные, выраженческие, невалидные/неготовые, не-B-tree индексы и нестандартные
направления/opclass/collation консервативно не признаются безусловной заменой.
Это может пропускать реально применимые нестандартные индексы — лучше явно
проверить их, чем утверждать покрытие без проверки.

Порядок списка — детерминированная очерёдность просмотра (не обучение и не
численная оценка выигрыша): новые кандидаты, спорные INCLUDE, уже покрытые;
учитываются число связанных команд и ширина варианта. Частоты операций не заданы:
повторение команды в тексте не подменяется частотой рабочей нагрузки.

## Влияние на запись

Для каждой непосредственно изменяемой таблицы учитываются INSERT/UPDATE/DELETE,
в том числе в изменяющих CTE. UPDATE сопоставляет явно присваиваемые столбцы с
ключами и INCLUDE. Если пересечение есть, выдаётся предупреждение о дополнительном
обслуживании и возможной потере HOT. Если пересечения нет, нулевые издержки всё
равно не обещаются. INSERT увеличивает обслуживание индексов, DELETE — нагрузку
обслуживания/очистки версий.

Численный процент замедления записи **не вычисляется**: строки не меняются,
триггеры/каскады/генерируемые столбцы не воспроизводятся, частоты и конкурентная
нагрузка неизвестны. Счётчики pg_stat_user_tables — накопленные значения после
сброса статистики, а не измеренная частота и не число операций этой транзакции.
Размер отношения не равен размеру нового индекса; для секционированного родителя
он также не является суммой всех секций.

Основание правил: [ведущие столбцы B-tree](https://www.postgresql.org/docs/17/indexes-multicolumn.html),
[условия HOT](https://www.postgresql.org/docs/17/storage-hot.html),
[метаданные pg_index](https://www.postgresql.org/docs/17/catalog-pg-index.html).

## Ограничения и проверки

Не более 128 вариантов и 64 таблиц; бюджет чтения метаданных 30 с, отдельные
запросы ограничены тайм-аутом. Неполное покрытие/ошибки метаданных явно отмечаются.
Есть отмена, сброс результатов при смене текста/подключения и блокировка
конфликтующих операций интерфейса. SQL/кандидаты автоматически не сохраняются.

На реальной тестовой БД пример даёт общий ведущий student_id для нескольких
SELECT/UPDATE/DELETE, а варианты с status предупреждают о его изменении UPDATE.
Сравнение строк enrollments студента 17001 и полного списка/DDL индексов схемы
до/после совпадает. Это проверка отсутствия изменений, не доказательство ускорения.

```powershell
$env:PQO_UNIVERSITY_TESTS='1'
.venv\Scripts\python.exe -B -m unittest discover -s tests -p test_transaction_indexes.py -v
```

Следующий этап: отдельно подтвердить пользу кандидатов на тестовой копии,
учитывая всю нагрузку. Последовательный запуск DML-транзакции, измерение её
времени и автоматическое применение индексов этим этапом не реализованы.
