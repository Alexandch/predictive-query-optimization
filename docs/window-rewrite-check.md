# Оконный запрос: что поддержано и что проверяется

Версия 0.8.24 содержала десять правил, их сочетания, сравнение результатов,
парные замеры, применение/возврат SQL и выбор вариантов. Эти механизмы не
пропали. Но правило CTE предлагало NOT MATERIALIZED только для повторно
используемого CTE. В университетском запросе каждый CTE использовался один раз,
а преобразования DENSE_RANK не было. Поэтому генератор возвращал ноль вариантов.

В 0.8.25 результат нажатия показан в отдельной заметной области над редакторами.
Отсутствие вариантов означает, что SQL для проверки не выполнялся. Это не вывод
о невозможности оптимизации. При ошибке/тайм-ауте показывается незавершённая
проверка, а не «оптимизация не требуется». Редактирование исходного SQL очищает
старое сообщение.

Новое правило `materialize-aggregate-before-window` проверяет MATERIALIZED для
одного верхнеуровневого агрегирующего SELECT CTE, используемого один раз прямо
в SELECT с оконной функцией. Не меняются текст оконного выражения, фильтры,
группировка и состав JOIN. Явные MATERIALIZED/NOT MATERIALIZED, рекурсия,
окна внутри исходного CTE и произвольные функции пропускаются. Преобразование
создаёт кандидата, а не автоматически принятую рекомендацию.

Каждый кандидат проходит прежний read-only протокол EXCEPT ALL на снимке и
замеры с проверкой порогов. Материализация может ускорить или замедлить запрос;
само наличие окна не делает её полезной. Универсальная семантическая
эквивалентность на любых данных не утверждается.

Проверка на текущей university 30.10.2026, без обучения и изменения данных:

- результаты исходного и нового SQL совпали;
- медианы трёх прогонов: 707,833 → 727,302 мс;
- ускорение не подтверждено (наблюдаемое замедление около 2,8%);
- кандидат отклонён, применять его нельзя.

Протокол: `artifacts/window-materialization-20261030/report.json`, тестовый
журнал рядом; записи не включаются в обучение. Пакетные замороженные эксперименты
явно отключают новое правило через `include_window_materialization=False`,
чтобы не менять их набор кандидатов задним числом.

Таким образом, этот пример теперь действительно сравнивается с конкретным
вариантом, но рекомендация по-прежнему может быть отрицательной. Это ожидаемый
результат, а не необходимость ослаблять пороги ради кнопки применения.
