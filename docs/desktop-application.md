# Десктопное PyQt6-приложение

Приложение объединяет прогноз XGBoost, селектор стратегии оптимизации, быструю
однократную рекомендацию DQN и измеренный последовательный план индексов.
С версии 0.8.26 отдельная вкладка «Транзакции» позволяет разобрать один блок
BEGIN … COMMIT/ROLLBACK и явно запросить оценочные планы команд без их запуска.
Это пока инвентаризация и планы исходного состояния, а не оптимизация/выполнение
всей транзакции. [Подробности и ограничения](transaction-roadmap.md).
С версии 0.8.27 после получения планов доступна кнопка «Подобрать общие индексы
(без создания)». Список показывает команды потенциального поиска, запись в
таблицу, уже существующие индексы и риск изменения ключа/INCLUDE. Это
[структурные кандидаты](transaction-index-candidates.md), не проверенное ускорение.
С версии 0.8.28 выбранный кандидат можно явно проверить на другой,
подтверждённой тестовой БД. Проба измеряет только SELECT по A/B/A и откатывает
индекс; вся транзакция и операции записи не запускаются.
[Руководство по пробе](transaction-index-trials.md).
С версии 0.8.29 таблица разделяет «SELECT №», «Поиск в DML №» и «Запись №».
Карточка и статус кандидата отражают именно его пробу на выбранной копии;
переключение кандидатов восстанавливает соответствующий результат в разделе
«Проба на копии». Если нет применения в самостоятельном SELECT, кнопка пробы
отключена с объяснением. Это не отрицательный вывод о пользе индекса для DML.
Результаты хранятся только в текущем анализе и сбрасываются при изменении SQL,
подключения, имени копии или повторном сборе кандидатов.
С версии 0.8.30 флажками в таблице можно отметить 1–3 подходящих для SELECT
кандидата. «Повторы SELECT» задаёт положительные целые числа повторений в
условном наборе (по умолчанию 1). Кнопка сравнения выполняет до шести проб:
одиночные кандидаты и пары. Результаты и состав каждой пары находятся в
«Сравнение индексов», не подменяют одиночные карточки/ML-прогноз и не означают
измерение DML. [Правила выбора и ограничения](transaction-index-comparison.md).
С версии 0.8.31 «Параметры SQL» после локального разбора показывает `$1`, `$2`, …
отдельно для каждой команды. Выберите тип, введите значение без SQL-кавычек
или явно отметьте NULL, затем примените параметры локально. Планирование
доступно после заполнения; исходный редактор не меняется. Новые значения
сбрасывают планы, кандидатов и обе разновидности проб. Значения живут только
в памяти текущего анализа, не в настройках/обучении.
[Подробности и поддерживаемые типы](transaction-parameters.md).
С версии 0.8.32 поле «Серий» рядом с кнопкой сравнения задаёт 1–3 серии
(по умолчанию 2). В таблице отдельные колонки «Серия» и «Вариант»: номера
вариантов не меняются при обратном порядке исполнения. Предпочтение выбирается
только при совпадении выбора всех полных серий и отсутствии существенного
межсерийного дрейфа. Одна серия помечается как предварительная. Изменение числа
серий сбрасывает прежнее сравнение; во время операции поле блокируется.
Ограничение 180 с относится ко всем сериям вместе, не к каждой по отдельности.
С версии 0.8.33 «Контроль SELECT» сначала фиксирует вариант выбранной строки
завершённого сравнения, затем открывает ввод новых 1–20 SELECT с конкретными
значениями. Две серии проверяют только зафиксированный набор; попытка в UI
одноразовая. Успешный контроль ручной гипотезы не меняет исходное предпочтение
и не исправляет неустойчивый подбор. [Инструкция](transaction-index-holdout.md).
С версии 0.8.34 «Запись и индексы» позволяет задать повторы/предполагаемые
строки DML и сценарный лимит. Это локальный структурный счётчик, не измерение
времени записи. Показаны ключи/INCLUDE в SET, новые ограничения HOT и неполный
охват триггеров/каскадов/секций. Флажки кандидатов только для DML доступны
для этой оценки, но не включают их в SELECT-пробы. [Инструкция](transaction-write-pressure.md).
С версии 0.8.35 отдельная вкладка «Выполнение на копиях» реально выполняет
ограниченные BEGIN … COMMIT на новых одноразовых БД A1/B/A2 одного закрытого
снимка. Сравниваются исходное состояние, результаты/RETURNING и итоговые данные;
удаление созданных БД проверяется отдельно по имени/OID. Нужны явное согласие,
доверенный лабораторный сервер и отдельный эталон; исходная БД не выполняется.
Общий клиентский прогон, execute+fetch SELECT/DML и построение/размер индексов
показаны отдельно. В 0.8.36 добавлен итог для отмеченного набора по всей
смешанной нагрузке: две серии по умолчанию, пороги до запуска, проверки
общего выигрыша в каждой серии, регрессий отдельных команд и дрейфа.
Размер учитывается до/после записи, построение не смешивается со временем
транзакции. Одна серия диагностическая; смена порогов/контекста сбрасывает
вывод. Это не поиск глобального оптимума и не применение на production.
[Итоговая оценка](transaction-mixed-recommendation.md).
В 0.8.37 «Переписывание SELECT» локально готовит варианты одного SELECT,
показывает исходник/замену рядом и выполняет всю поддерживаемую транзакцию
на новых одноразовых A1/B/A2 копиях. В B меняется только выбранный SELECT;
порядок и остальные команды сохраняются. Проверяются каждый результат,
RETURNING, затронутые строки и итоговые данные; ошибка, несовпадение,
отмена/неподтверждённая очистка блокируют рекомендацию. Ускорение проверяется
отдельно от эквивалентности. [Инструкция](transaction-select-rewrite.md).
[Инструкция и узкий контракт](transaction-disposable-replay.md).
Кнопка «Быстрый ML-прогноз» не выполняет пользовательский SQL. Она получает
оценочный `EXPLAIN`-план, собирает признаки SQL и текущей БД и передаёт их в XGBoost.
Ранее собранный профиль калибровки применяется без новых замеров.

Карточка времени показывает только прогноз и его источник: ML-модель или ML с профилем БД.
Оценочный диапазон ошибки доступен в подсказке, чтобы не перегружать основной экран. Индекс, переписывание или
структурное изменение подтверждается только при
прохождении порога исходного времени, минимального абсолютного выигрыша и
минимального относительного выигрыша.

Базовый прогноз «до калибровки» в интерфейсе не показывается. Блок рекомендаций
разделяет предварительную ML-навигацию, индексных кандидатов, фактически
проверенные решения и структурные гипотезы. Класс `NOOP` не является запретом на
изменения: если глубокая проверка доказала ускорение, её фактический результат
имеет приоритет.

Кнопка «Предварительно калибровать по файлу SQL» принимает UTF-8 файл с 1–30 запросами,
разделёнными точкой с запятой. Допускаются только `SELECT` и `WITH`. Приложение
последовательно выполняет их через `EXPLAIN ANALYZE`, сохраняет профиль после
каждого успешного измерения и показывает MAE до/после. Для каждого SQL выполняется
один прогрев и пять замеров; сохраняются медиана и диапазон. Это необязательный
способ заранее заполнить общий профиль. Пример нагрузки находится в
`examples/manual-check-queries.sql`.

## Запуск

Если Windows-установщик уже выполнен, используйте ярлык
«Predictive Query Optimization» на рабочем столе или в меню «Пуск».
Установленная программа находится в
`%LOCALAPPDATA%\Programs\PredictiveQueryOptimization` и не требует отдельной
установки Python. PostgreSQL можно запустить из каталога проекта:

```powershell
docker compose up -d --wait
```

Запуск непосредственно из исходного кода нужен только для разработки:

```powershell
docker compose up -d --wait
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[desktop]"
.\.venv\Scripts\pqo-desktop.exe
```

По умолчанию используются PostgreSQL на `localhost:55432` и выбранные модели
из каталога `models`. Параметры можно изменить на вкладке «Настройки».
Пароль PostgreSQL не записывается в `QSettings` и существует только в памяти
текущего процесса.

Для подключения другой PostgreSQL укажите её хост, порт, имя БД, пользователя,
пароль и список разрешённых схем. Запросы лучше задавать с именем схемы,
например `sales.orders`; для таблиц без явной схемы анализатор использует
`public`. Пользователю БД нужны `CONNECT`, `USAGE` на схемы и `SELECT` на
анализируемые таблицы. Для обычного анализа право `CREATE` не требуется.

Кнопка «Глубокий анализ индексов» работает иначе и всегда показывает отдельное
подтверждение. Она реально выполняет SELECT через `EXPLAIN ANALYZE`, временно
создаёт до двух выбранных индексов и измеряет результат. Исходное время — медиана
пяти замеров после отдельного прогрева; интерфейс также показывает минимум и
максимум. Для неё пользователь
должен иметь право `CREATE` в целевой схеме. Весь эпизод выполняется в одной
транзакции и безусловно откатывается: приложение выводит проверенные DDL, но не
оставляет индексы в БД. Кандидат показывается только если PostgreSQL использовал
его в плане, измеренная награда положительна, а абсолютная экономия составляет
не менее 5 мс. Если фактическое исходное время ниже установленного порога
рекомендации, индекс не предлагается. Лимит пробных индексов — 64 МиБ.

В Windows-сборке последовательная DQN выполняет инференс через экспортированный
NumPy-артефакт с теми же весами. PyTorch остаётся доступным для обучения, но не
загружается путём глубокого анализа; это исключает нативное завершение процесса
`BEX64` при работе упакованного приложения.

После успешного глубокого анализа кнопка «Применить проверенные индексы и
измерить» создаёт предложенные индексы постоянно только после подтверждения
пользователя. Приложение трижды измеряет исходный запрос, показывает медиану до
и после и сохраняет точные имена созданных индексов в локальном журнале. Кнопка
«Откатить применённые индексы» доступна и после перезапуска: она удаляет только
индексы с безопасными именами из этого журнала и повторяет замер без них.
Для каждого проверенного индекса интерфейс показывает размер, долю от полного
размера целевой таблицы, время тестового построения и накопленные счётчики
`INSERT/UPDATE/DELETE` из статистики PostgreSQL. Отдельно указывается, что индекс
увеличивает стоимость записи, занимает диск и кэш, а ускорение доказано только
для текущего SQL. Перед постоянным применением пользователь повторно видит эти
ограничения; для production рекомендуется проверка репрезентативной нагрузки и
`CREATE INDEX CONCURRENTLY` либо окно обслуживания.

Вкладка «Анализ» прокручивается целиком. Нижние поля «Принять», «Отклонить» и
«Фактический замер» относятся к обратной связи по структурным рекомендациям, а
не к применению индексов. Они активируются только для анализа, сохранённого в
служебной схеме `pqo`.

Кнопка «Проверить переписывание SQL» формирует консервативные варианты без
изменения схемы: заменяет положительную проверку `COUNT(*)` на `EXISTS`, цепочку
равенств `OR` по одному столбцу на `IN`, две включительные границы на `BETWEEN`,
удаляет не влияющий на результат `ORDER BY` из подзапроса без `LIMIT` и переносит
безопасные неагрегатные условия из `HAVING` в `WHERE`. Исходный и новый запросы
выполняются в транзакции `READ ONLY`.
Приложение сначала доказывает совпадение мультимножеств строк в обе стороны
через `EXCEPT ALL`, затем чередует измерения `EXPLAIN ANALYZE`. Новый SQL
показывается только при достижении настроенных порогов. После успешной проверки
кнопка «Применить проверенный SQL и измерить» заменяет текст в редакторе и
повторяет обычный фактический анализ. «Вернуть исходный SQL и измерить» восстанавливает
сохранённый исходный текст. Эти действия не изменяют схему или данные PostgreSQL:
для переписывания откат означает возврат текста запроса, а не `ROLLBACK` DDL.
Результат проверки содержит нормализованный diff с удалёнными (`-`) и добавленными
(`+`) строками. Специализированные экраны переписывания и глубокого индексного
анализа не дополняются структурными гипотезами: они показываются только в
результате обычного анализа и управляются в отдельном блоке.

После обычного анализа селектор показывает один из трёх предварительных классов:
`NOOP`, проверить индекс или проверить переписывание SQL. Рядом выводятся
вероятности всех классов. Это навигационная ML-подсказка, а не итоговая
рекомендация: она не создаёт индекс и не подменяет SQL. Пользователь проверяет
кандидата одной из двух кнопок глубокого
анализа, после чего PostgreSQL проверяет фактический выигрыш с полным откатом.
Ниже приложение выводит отдельный блок структурных рекомендаций по агрегациям,
JOIN, сортировкам и материализованным представлениям. Для каждого пункта указаны
основание, приоритет, действие и способ фактической проверки. Эти рекомендации
не изменяют SQL или схему автоматически.
При сохранении анализа ниже становятся доступны кнопки «Принять» и «Отклонить».
Для принятого пункта можно записать независимый замер времени до и после
оптимизации. Решение и результат сохраняются в служебной схеме `pqo`, видны в
истории и попадают в её CSV/JSON-экспорт.
Для поддерживаемых правил после принятия доступна кнопка «Проверить
автоматически». Она выполняет фактические замеры в откатываемой транзакции,
сохраняет отдельный протокол проверки и заполняет поля времени до/после.

Флажок «Сохранять в историю pqo» распространяется и на обычный, и на глубокий
анализ. Для глубокого анализа сохраняются фактические времена до/после,
измеренный выигрыш, причина остановки и каждый проверенный DDL с Q-оценкой и
reward. Если перед ним уже был сохранён обычный анализ того же SQL, результаты
связываются с одной записью запроса; иначе создаётся отдельная запись. Флажок по
умолчанию выключен, поэтому анализ чужой БД не требует служебных таблиц проекта.
Его следует включать только для БД, в которой установлена схема `pqo` из
`database/init`.

Для новой БД профиль создаётся явной пакетной калибровкой по файлу SQL. Контрольные
замеры после явного применения/отката переписанного SQL также могут пополнять профиль. После десяти разных SQL становятся доступны и
общие групповые поправки для уже знакомых шаблонов. Ручного флажка включения нет;
под адаптивной оценкой при необходимости показывается исходный прогноз модели.
Подробности и команды CLI приведены в
[руководстве по калибровке](database-calibration.md).

В установленной версии результаты обучения и экспорта записываются в
`%LOCALAPPDATA%\PredictiveQueryOptimization\artifacts`, поэтому программа не
пытается изменять защищённые файлы внутри своего каталога установки.

## Вкладки

- **Анализ** — ввод `SELECT`/`WITH`, быстрый ML-прогноз без запуска SQL и
  отдельные глубокие режимы с проверенным планом до двух индексов и измеренным
  переписыванием SQL. Проверенный SQL применяется в редактор только отдельной
  кнопкой пользователя и может быть возвращён; DDL без подтверждения не применяется.
- **История** — последние 200 обычных и глубоких анализов из схемы `pqo`,
  включая фактическое время, измеренный выигрыш и проверенные индексы.
- **Эксперименты** — карточки parameter/stress-метрик, включая независимый
  logistics-контроль DQN, график
  «факт → прогноз» XGBoost и сравнение DQN с Random/NOOP. При пересчёте
  модель применяется к 3 398 агрегированным точкам текущего датасета.
- **Настройки** — подключение к PostgreSQL, разрешённые схемы, пути к XGBoost,
  однократной и последовательной DQN, селектору стратегии и проверка связи.
- **Обучение** — повторное обучение XGBoost или DQN на указанном датасете с
  выводом итоговых метрик. Для DQN доступны parameter и unseen-template
  stress-режимы. Во время работы отображается индикатор прогресса.

## Контроль качества модели

Обученный артефакт сначала сохраняется как кандидат в `artifacts/models`.
Кнопка назначения основной моделью активируется только если:

- у XGBoost не ухудшились `R²` и `MAE` в parameter- и stress-оценках;
- у DQN не снизилась accuracy и не вырос regret в parameter-оценке;
- DQN-кандид был обучен в parameter-режиме, а не тольо stress.

Перед заменой текущие файлы копируются в подкаталог `previous`.

## Экспорт

Историю анализа и экспериментальные результаты можно сохранить в UTF-8
JSON или в CSV с BOM для корректного открытия в Excel. JSON истории содержит
структурированные шаги глубокого анализа, а в CSV они записываются одной JSON-
ячейкой. CSV-экспорт эксперимента создаёт файл точек и соседний
`*_summary.csv` со сводными метриками.

Анализ, доступ к истории, проверка связи и обучение выполняются в фоновых
потоках, поэтому окно не зависает во время долгих операций.

Те же проверки переписывания доступны из командной строки:

```powershell
.\.venv\Scripts\pqo-rewrite.exe `
  "SELECT ... WHERE (SELECT COUNT(*) FROM ...) > 0"
```

Для просмотра синтаксических кандидатов без подключения к PostgreSQL добавьте
`--generate-only`.
