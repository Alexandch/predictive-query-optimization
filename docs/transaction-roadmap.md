# Переход к анализу транзакций

## Этап 1: инвентаризация, без выполнения

Добавлен `pqo.transaction_inspection`. Он принимает один простой блок
BEGIN ... COMMIT/ROLLBACK, сохраняет порядок SELECT/INSERT/UPDATE/DELETE,
показывает имена отношений и отмечает запись, неизвестные функции,
блокировки строк и неподдержанные команды. Существующая защита одиночного
SELECT не ослабляется. `execution_permitted` всегда false.

```powershell
.venv\Scripts\python.exe -m pqo.transaction_inspection examples/transactions/university-inspection.sql
```

Это только локальный структурный разбор, не подключение к БД и не запуск SQL.
JSON содержит SQL с литералами; перед передачей наружу проверить чувствительные
данные. Число команд ограничено 100, текст — 500 тысячами символов. Явные режимы
BEGIN, savepoints, подготовленные транзакции и несколько транзакций в одном
тексте пока не поддерживаются для дальнейшего планирования. Неквалифицированные
имена требуют будущего разрешения search_path. Операции, распознанные парсером,
не становятся от этого безопасными для исполнения.

В 0.8.26 добавлена отдельная вкладка «Транзакции». Нельзя вставлять BEGIN ...
COMMIT в прежний одиночный анализатор: его защита по-прежнему допускает только
один SELECT/WITH.

## Этап 2: интерфейс и оценочные планы

1. На вкладке «Транзакции» вставить текст или открыть UTF-8 SQL-файл.
2. Нажать «Разобрать без подключения к БД». В таблице видны порядок команд,
   операции записи и отношения; справа — SQL и предупреждения выбранной команды.
3. Проверить подключение на вкладке «Настройки», затем нажать «Получить оценочные
   планы» и подтвердить подключение. Пример для тестовой университетской БД:
   `examples/transactions/university-inspection.sql`.
4. Прочитать статус каждой команды и JSON плана справа. Ошибка/тайм-аут отдельного
   плана не останавливает следующие команды. Есть отмена; общий бюджет 90 с,
   отдельный statement_timeout не больше 30 с, lock_timeout не больше 1 с.

`pqo.transaction_planning.collect_transaction_plans` повторно проверяет исходный
текст и запрашивает только `EXPLAIN (FORMAT JSON)`, без ANALYZE. Исходные
BEGIN/COMMIT и команды записи не исполняются. Соединение работает в REPEATABLE
READ, READ ONLY, с принудительным откатом; у каждого плана отдельный savepoint.
Для физических отношений нужны явные имена разрешённая_схема.таблица. Параметры
$1/:name/?, неизвестные функции, SELECT INTO, FOR UPDATE, DDL/SET пока блокируются.
Допустимые CTE разрешаются по областям видимости, а не глобальному совпадению имён.

Важно: это **не последовательное выполнение транзакции**. Все команды
планируются относительно исходного состояния, без результатов предыдущих записей.
Стоимость PostgreSQL не является миллисекундами; сумма стоимости/прогнозов
одиночных SELECT не показывается как время транзакции. Фактическая общая
проверка индексов, численная цена записи и применение переписываний транзакции
ещё не реализованы.

Даже EXPLAIN без ANALYZE берёт блокировки и использует ресурсы планировщика;
БД может содержать пользовательские функции/операторы/расширения, вызываемые
при планировании. READ ONLY и консервативная проверка SQL — не песочница для
недоверенной БД. Использовать тестовую копию и минимальные права.
[Поведение EXPLAIN в PostgreSQL](https://www.postgresql.org/docs/17/sql-explain.html).

Текст транзакции/планы автоматически не сохраняются и не включаются в обучение.
Как и раньше, диагностический журнал ошибок GUI может содержать фрагменты SQL;
перед передачей журналов проверьте чувствительные данные. Изменение текста
сбрасывает разбор и планы, изменение подключения — планы; устаревшие ответы
фоновой операции не принимаются.

Проверка на `pqo_university_unseen`: SELECT/UPDATE/INSERT/DELETE получают планы,
ошибка отсутствующей таблицы не мешает последующему SELECT, строка студента
17001 до/после полностью совпадает. INSERT с дублирующим PK также только
планируется: именно выполнение, которое нарушило бы уникальность, не происходит.

```powershell
$env:PQO_UNIVERSITY_TESTS='1'
.venv\Scripts\python.exe -B -m unittest discover -s tests -p test_transaction_planning.py -v
```

## Этап 3: общие индексные кандидаты

В 0.8.27 после получения планов можно сгруппировать структурные индексные
кандидаты для всех допустимых команд, проверить существующее покрытие и
посмотреть качественное влияние на запись. [Алгоритм, пример и ограничения](transaction-index-candidates.md).
Версия 0.8.27 собрана, установлена и проверена; снимки настроек до/после совпали.
Индексы не создаются, время/замедление не измеряются; это не фактическая
оптимизация транзакции и не обучение новой модели.

## Этап 4: проба одного общего индекса на копии

В 0.8.28 выполняется сравнение A/B/A всех допустимых самостоятельных SELECT
из текста транзакции на отдельной подтверждённой копии. Индекс временный,
откат проверяется отдельно; существенные регрессии и дрейф блокируют подтверждение.
Версия собрана, установлена и проверена, настройки подключения/моделей сохранены.
Команды записи и изменяющие CTE пропускаются. Это не выполнение транзакции.
[Алгоритм и инструкция](transaction-index-trials.md).

В 0.8.29 проба привязана к конкретному кандидату и копии, её результат виден
в исходной карточке/строке. Применения в SELECT и поиск в DML разделены;
кандидат только для команды записи не запускает пробу ускорения чтений.
Это уточнение области доказательства, не добавление выполнения DML.

## Этап 5: сравнение кандидатов и пар, явные повторы SELECT

В 0.8.30 можно отметить до трёх кандидатов и сравнить одиночные варианты и
пары — максимум шесть A/B/A проб. Числа повторений задаёт пользователь;
взвешенная сумма не называется временем транзакции. У каждой пробы свой
снимок/базовые замеры; межвариантный дрейф блокирует предпочтение. Неиспользуемый
индекс пары и отсутствие добавочной пользы не обосновывают лишний индекс.
[Инструкция и границы](transaction-index-comparison.md).

## Этап 6: явные типизированные значения параметров

В 0.8.31 `$1`, `$2`, … задаются отдельно для каждой команды. Локальная привязка
скалярных значений сохраняет исходный редактор, используется в планах,
кандидатах и SELECT-пробах, а изменение значения сбрасывает прежние результаты.
Это конкретный сценарий значений, не PREPARE/generic-plan production.
Сессионные SET, режимы BEGIN, savepoint/replay и другие сложные контексты
по-прежнему не поддерживаются. [Инструкция](transaction-parameters.md).

## Этап 7: повторные серии сравнения

В 0.8.32 доступны 1–3 серии с прямым, обратным и сдвинутым порядком вариантов.
По умолчанию 2 серии; предпочтение должно независимо совпасть в каждой,
существенный дрейф между сериями также блокирует выбор. Отмена, ошибка,
исчерпание общего бюджета или неподтверждённый откат не дают общего выбора.
Результаты всех проб сохраняются в текущем анализе, без автоматического
сохранения SQL или обучения. Это ещё не независимый контрольный набор и не
последовательное выполнение DML. [Правила](transaction-index-comparison.md#повторные-серии-в-0832).

## Этап 8: отдельный контроль SELECT

В 0.8.33 вариант фиксируется до открытия контроля, затем две серии проверяют
его на новых конкретных SELECT/значениях, не использованных в сравнении.
Выбор индекса/порогов на контроле не выполняется, исходное предпочтение не
меняется. Проверка ручной гипотезы отделена от прохождения подбора + контроля.
UI допускает одну фактическую попытку на сравнение, но не может доказать
историческую независимость пользовательских данных между запусками.
[Инструкция и границы](transaction-index-holdout.md).

## Этап 9: структурный сценарий записи

В 0.8.34 пользователь задаёт повторы и предполагаемые затронутые строки
простых DML, сравнивает экспозицию «строка × новый индекс» с собственным
лимитом и отдельно видит измерения чтений того же набора. Добавлены сведения
каталогов о генерируемых столбцах/триггерах/правилах/потомках/FK-действиях,
разделены риски ключей/INCLUDE и уже существующих ограничений HOT.
Неизвестное/побочные операции не превращаются в нулевую цену. Это не прогноз
миллисекунд и не фактическая запись; чистый выигрыш не объявляется.
[Инструкция](transaction-write-pressure.md).

## Следующие этапы

Согласованная последовательность 01.11.2026:

1. Реальная запись на одноразовых копиях — первый ограниченный режим добавлен
   в 0.8.35: закрытый снимок, новые A1/B/A2, последовательный COMMIT, сравнение
   исходных состояний/выводов/итоговых данных, отслеживание и отдельное подтверждение
   удаления созданных БД. [Инструкция](transaction-disposable-replay.md).
2. В 0.8.36 добавлена итоговая оценка отмеченного набора по смешанной нагрузке:
   общий выигрыш каждой серии, SELECT/DML и отдельные команды, размер до/после
   записи, построение, дрейф внутри/между сериями; неполная корректность/очистка
   блокирует рекомендацию. Без глобального поиска/production-применения.
   [Политика и границы](transaction-mixed-recommendation.md).
3. В 0.8.37 добавлена замена одного SELECT внутри ограниченной транзакции:
   локальные правила/ручной вариант рядом с исходником, неизменный порядок
   остальных команд, полная A1/B/A2 проверка с предыдущими DML, все результаты
   и итоговые данные, очистка и проверка общего измеренного эффекта.
   Новых индексов и применения к источнику нет. [Инструкция](transaction-select-rewrite.md).
4. Следующий этап: сквозная проверка MVP на нескольких БД, положительных и отрицательных случаях,
   отмене/ошибках; установка согласованной версии и обновление записки по факту.

Для полезного курсового MVP предварительный инженерный ориентир — 5–10
рабочих дней разработки и проверок, с уточнением после первых интеграций.
Это не обещание календарной даты или фоновой работы без взаимодействия.
Безопасная работа с произвольными production-транзакциями — более широкий
проект: изолированная копия, права, побочные эффекты функций, триггеры,
блокировки и конкурентная нагрузка требуют отдельной проверки.
