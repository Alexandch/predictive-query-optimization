# Проверка индексов и переписывания SQL

Быстрый анализ формирует кандидатов. Итоговое решение появляется после отдельной
фактической проверки: предварительная ML-оценка и структурная гипотеза не дают
разрешения на применение.

## Индексные кандидаты

Генератор учитывает условия фильтра и соединений, сортировку, ключи и INCLUDE.
Покрытие проверяется по существующим индексам; частичный или выраженческий
индекс не считается безусловной заменой обычного кандидата.

Глубокий анализ создаёт пробные индексы, получает фактические планы и измеряет
время. Кандидат принимается только при использовании индекса PostgreSQL,
прохождении порога исходного времени, абсолютного и относительного выигрыша.
Стандартные минимальные выигрыши — 5 мс и 5%; значения настраиваются в интерфейсе.
Последовательная проверка ограничена двумя шагами и бюджетом новых индексов.

Пробные изменения откатываются. Постоянное создание проверенного набора —
отдельная подтверждаемая операция. Локальный журнал хранит точные имена созданных
приложением индексов и используется при их откате. Построение, размер и влияние
на запись показываются отдельно; измеренный эффект относится к текущему SQL.

Список действий и проба из CLI:

```powershell
.\.venv\Scripts\pqo-index.exe "SELECT flight_id FROM aviation.flights WHERE departure_airport = 'MSQ'"
.\.venv\Scripts\pqo-index.exe --action-index 1 --repetitions 3 "SELECT flight_id FROM aviation.flights WHERE departure_airport = 'MSQ'"
```

Вторая команда реально выполняет запрос и создаёт пробный индекс с откатом.

## Два редактора SQL

Слева остаётся исходный запрос, справа — автоматический или ручной вариант.
Подготовка варианта не заменяет исходник. Изменённые строки подсвечиваются,
при наведении виден старый текст; отдельного дублирующего текстового diff нет.

«Проверить вариант и измерить оба SQL» выполняет:

1. проверку допустимости обоих read-only запросов;
2. сравнение мультимножеств через `EXCEPT ALL` в двух направлениях;
3. прогрев и чередующиеся замеры исходного и нового SQL в одном
   `READ ONLY REPEATABLE READ` снимке;
4. сравнение медиан с настроенными порогами выигрыша.

Направления `EXCEPT ALL` выполняются последовательно. Несовпадение,
тайм-аут или ошибка не считаются подтверждением. Редактирование варианта
сбрасывает прежнюю проверку. Применить можно только подтверждённый текст;
кнопка возврата восстанавливает исходник.

Совпадение на одном снимке не доказывает равенство для любых данных и не
подтверждает порядок строк. Отдельного внимания требуют дубликаты, NULL,
недетерминированные выражения и LIMIT с неуникальной сортировкой.

## Автоматические правила

Генератор основан на ограниченных правилах:

- положительный `COUNT(*)` → `EXISTS`, нулевой → `NOT EXISTS`;
- равенства одного столбца через OR → IN;
- включительные границы диапазона → BETWEEN;
- удаление внутреннего ORDER BY без влияющих на результат ограничений;
- пробные NOT MATERIALIZED для повторного CTE и MATERIALIZED для агрегата
  перед оконной функцией;
- перенос допустимого неагрегатного HAVING в WHERE;
- коррелированный скалярный агрегат → группировка с LEFT JOIN;
- объединение совместимых коррелированных агрегатов в одну группировку;
- фильтрующая цепочка INNER JOIN под DISTINCT → EXISTS с сохранением DISTINCT.

Некоторые правила можно объединить в ограниченный двухшаговый вариант.
У каждого правила свои проверки допустимости; реестр находится в
[sql_rewrite.py](../src/pqo/sql_rewrite.py). Составные ключи не отбрасываются,
COUNT при отсутствии дочерних строк сохраняет нулевой результат. Генератор
не исправляет произвольную бизнес-семантику SUM после размножающего JOIN.

Любое преобразование может замедлить SQL. Отсутствие кандидатов означает,
что поддерживаемое правило не подошло, а не что запрос оптимален.

## CLI и примеры

```powershell
.\.venv\Scripts\pqo-rewrite.exe --generate-only "SELECT flight_id FROM aviation.flights WHERE departure_airport = 'MSQ' OR departure_airport = 'SVO'"
.\.venv\Scripts\pqo-rewrite.exe "SELECT flight_id FROM aviation.flights WHERE departure_airport = 'MSQ' OR departure_airport = 'SVO'"
```

Первый вызов только генерирует варианты, второй запускает фактическую проверку.
Примеры: [коррелированные агрегаты](../examples/aviation-shared-aggregates-rewrite.sql),
[фильтрующие JOIN](../examples/retail-customer-join-chain-rewrite.sql),
[индекс](../examples/logistics-index-check.sql).
Требуются соответствующие схемы и данные.

Локальный журнал проверок просматривается через `pqo-rewrite-journal`.
Обучаемое ранжирование вариантов пока работает офлайн и не меняет рабочий
генератор; см. [experiments.md](experiments.md).
Для SELECT внутри транзакции действует более узкий [контракт](transactions.md).
