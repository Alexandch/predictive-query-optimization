# Два редактора и проверка переписывания SQL

Обновлено для версии 0.8.23, 27.10.2026. В этапе переписывания модели XGBoost и DQN не заменялись.

Слева остаётся исходный/текущий запрос. Справа — отдельный редактируемый вариант.
Автоматическая проверка заполняет правое поле, но не меняет левое. При отсутствии
автоматического преобразования можно предложить свой SELECT справа.

Кнопка «Проверить вариант и измерить оба SQL» спрашивает подтверждение фактического
выполнения, проверяет read-only SQL и совпадение мультимножеств через EXCEPT ALL,
после прогрева чередует три замера исходного и три замера варианта. Результат —
две медианы. Используется единый REPEATABLE READ-снимок БД. Исходный редактор
не меняется. Во время операции редакторы и конкурирующие действия блокируются.

Два направления EXCEPT ALL выполняются последовательно в этом же снимке,
а не внутри одного UNION ALL с четырьмя копиями запросов. Это уменьшает
пиковое число одновременно исполняемых планов и hash-таблиц. Если первое
направление уже нашло различие, второе не выполняется. Тайм-аут или нехватка
ресурсов всё равно означают отказ в подтверждении, а не эквивалентность.

Совпадение на текущем снимке не доказывает совпадение на всех возможных данных,
не подтверждает порядок строк и не заменяет проверку бизнес-семантики. Особенно
важны дубликаты, NULL, недетерминированные функции и LIMIT с неуникальной сортировкой.
Несовпадение результатов запрещает применение. Редактирование правого поля
отключает применение старого проверенного текста до новой проверки.

«Применить проверенный SQL и измерить» по-прежнему переносит подтверждённый
вариант в основной редактор с повторным замером; исходный текст сохраняется
для кнопки возврата. Это изменение текста, не постоянное изменение таблиц БД.

## Что умеет автоматический генератор

Одиннадцать ограниченных правил, а не произвольное нейросетевое переписывание:

1. COUNT(*) > 0 / >= 1 → EXISTS.
2. COUNT(*) = 0 → NOT EXISTS.
3. OR-равенства одного столбца → IN.
4. Две включительные границы → BETWEEN.
5. Удаление внутреннего ORDER BY без LIMIT, OFFSET и DISTINCT ON.
6. Пробное NOT MATERIALIZED для повторно используемых SELECT CTE без рекурсии.
7. Перенос неагрегатного HAVING-фильтра в WHERE при наличии обычного GROUP BY
   (не ROLLUP, CUBE и GROUPING SETS).
8. Коррелированный скалярный агрегат → сгруппированный подзапрос с LEFT JOIN.
9. DISTINCT над цепочкой фильтрующих INNER JOIN → один EXISTS; внешний DISTINCT сохраняется.
10. Несколько коррелированных агрегатов над одним потоком → одна общая
    группировка и LEFT JOIN вместо отдельных группировок.
11. Пробное MATERIALIZED для однократно используемого агрегирующего CTE
    перед оконной функцией. [Ограничения и результат проверки](window-rewrite-check.md).

### Новые правила для агрегаций и JOIN

Правило 8 обрабатывает явно названные выходные столбцы с SUM/AVG/MIN/MAX
одного столбца, COUNT(*), COUNT(column) и COUNT(DISTINCT column). Подзапрос
должен читать один источник с явным алиасом и иметь одно или несколько
равенств ключей дочерней таблицы ключам родителя. Все компоненты составного
ключа сохраняются в GROUP BY и ON. Допускаются простые локальные фильтры дочерней таблицы. Другие
выходные столбцы родителя должны быть явно квалифицированы; SELECT * запрещён.
COUNT заменяется COALESCE(агрегат, 0), поскольку LEFT JOIN без совпадений даёт
NULL, а исходный скалярный COUNT — ноль. SUM/AVG/MIN/MAX оставляют NULL.
Несколько независимых скалярных агрегатов создают отдельные сгруппированные
источники с уникальными алиасами. Это по-прежнему отдельный кандидат;
дополнительно правило 10 предлагает общую группировку при совпадении
источника, всех ключей корреляции и локального фильтра. COUNT DISTINCT
по кортежу/нескольким столбцам, DISTINCT у других агрегатов, FILTER,
оконные функции, вложенные источники, LIMIT/ORDER/GROUP BY внутри агрегата и
произвольные функции не поддерживаются этим правилом.

Правило 9 допускает один или несколько INNER JOIN с ON, уникальными явными
алиасами и выводом только столбцов родителя. ON/WHERE допускают простые сравнения квалифицированных
столбцов и констант. LEFT/RIGHT/FULL, NATURAL/USING, вывод дочерних столбцов,
DISTINCT ON, GROUP BY, LIMIT/OFFSET, окна и функции не переписываются.
DISTINCT сохраняется: без знания ключей проекции его удаление было бы ошибкой.

Вся цепочка переносится в один EXISTS: дочерние таблицы по-прежнему должны
совпасть друг с другом, а не просто независимо содержать подходящую строку.
Условия с внешним алиасом из последующих ON поднимаются в WHERE этого
EXISTS; дочерние условия остаются в JOIN. Если все условия ON оказались
внешними, внутри EXISTS используется CROSS JOIN с сохранёнными условиями
в WHERE. Это допустимо только для исходной цепочки INNER JOIN и помогает
PostgreSQL развернуть корреляцию в полусоединение. OR переносится целиком,
его ветви не разрываются. Табличные функции и подзапросы-источники не
считаются обычными таблицами. Это кандидат, а не обещание ускорения.

Локальные проверки 27.10.2026:

- `examples/retail-customer-join-chain-rewrite.sql`: 599,99 → 230,29 мс,
  экономия 61,6%; вариант подтверждён;
- `examples/retail-join-chain-rewrite.sql`: 267,03 → 342,20 мс,
  замедление; применение не предлагается;
- `examples/aviation-join-chain-rewrite.sql`: 224,56 → 406,71 мс,
  замедление; применение не предлагается.

Первые диагностические варианты сохранены отдельно: без переноса внешних
ON-условий проверка первого retail SQL остановилась по тайм-ауту; при
едином четырёхплановом EXCEPT ALL возникла нехватка shared memory. В обоих
случаях вариант не был признан эквивалентным или рекомендованным.
После исправлений тот же SQL проверяется, но честно отклоняется по времени.
Отчёты: `artifacts/join-chain-check*`, `artifacts/join-chain-customer-check`,
`artifacts/join-chain-aviation-check`. Это локальная диагностика, не
независимый бенчмарк и не гарантия для другой нагрузки или других индексов.

Правило 10 использует те же ограничения допустимости, что правило 8.
Алиасы дочерних таблиц могут различаться; перед сравнением нормализуются
только их имена. Схема/таблица, ключ дочерней и родительской таблиц,
фильтр и списки переименования столбцов должны совпадать структурно.
Разные фильтры и источники остаются отдельными потоками. COUNT(*) и
COUNT(column) сохраняют COALESCE(..., 0), остальные агрегаты – NULL при
отсутствии совпадений. Повторяющиеся родительские строки не удаляются.
Идентификаторы с кавычками сохраняются.

Новый кандидат не вытесняет старый: оба проходят EXCEPT ALL и чередующиеся
замеры. Объединение может не помочь при селективном фильтре родителя и
хорошем индексе дочерней таблицы. Результат без выигрыша не предлагается
к применению. Пример: `examples/aviation-shared-aggregates-rewrite.sql`.
Проверка: `scripts/check_shared_aggregates.py`; она не создаёт индексов,
не меняет данные, модель прогноза, калибровку или историю приложения.

Локальная проверка 27.10.2026 на этом примере (20 рейсов, три агрегата):
отдельные группировки – 1728,40 → 621,46 мс; общая группировка –
1690,35 → 222,29 мс, сокращение времени на 86,8% (примерно в 7,6 раза).
Оба варианта совпали по EXCEPT ALL. Приведены отдельные парные медианы
каждого сравнения, поэтому исходные времена отличаются. Результат зависит
от оборудования, кэша, данных и индексов; это демонстрация, не гарантия.
Журнал и отчёт: `artifacts/shared-aggregates-check/`.

Сообщение об отсутствии кандидатов теперь перечисляет правила из того же
реестра, что используется генератором, а не из устаревшего списка из семи
преобразований. Отсутствие кандидатов не означает, что SQL оптимален.

Оба преобразования могут замедлить SQL. Предварительная агрегация может прочитать
всю дочернюю таблицу вместо нескольких быстрых индексных обращений; EXISTS
может получить другой, не лучший план. Поэтому генерация не означает рекомендацию
к применению. Проверяются снимок результатов, фактическое время и заданные пороги.
Проверки на VALUES-фикстурах включают NULL-ключи/значения, отсутствие дочерних
строк, дубликаты родителей, COUNT(*) и COUNT(column).

Новые примеры для правого редактора и автоматической проверки:
`examples/retail-scalar-aggregate-rewrite.sql` и
`examples/logistics-distinct-join-rewrite.sql`. SQL с несколькими широкими
JOIN и произвольными SUM не переписывается вслепую: это может изменить бизнес-итоги.

NOT MATERIALIZED может как улучшить, так и ухудшить план из-за повторных
вычислений; поэтому он только кандидат. PostgreSQL описывает этот компромисс
в [документации о CTE](https://www.postgresql.org/docs/17/queries-with.html#QUERIES-WITH-CTE-MATERIALIZATION).
На авиационном запросе пользователя с route_monthly/airport_monthly/route_dynamics
кандидат прошёл проверку строк, но не ускорил выполнение: медианы около
3138 → 3349 мс при текущей нагрузке во время сборки. Он отклонён, а не выдан
как рекомендация. Это локальный замер, не сравнение с временем со скриншота.
Результат: `artifacts/rewrite-preview-verification/route-cte.json`.
Отсутствие кандидатов означает, что фактическая проверка не запускалась, а не
что SQL оптимален. Синтаксически красивое преобразование OR/BETWEEN может
ничего не ускорить — решение принимается по замерам.

### Составные ключи и COUNT DISTINCT

Пример `examples/aviation-composite-distinct-rewrite.sql` рассчитывает
статистику по паре `(flight_id, fare_conditions)`. Порядок равенств в
подзапросах может различаться: генератор выстраивает одинаковый порядок
ключей, но не удаляет ни одного условия. NULL в любом компоненте ключа
не начинает совпадать с NULL на другой стороне: сохраняется обычное `=`.
COUNT DISTINCT учитывает только уникальные ненулевые значения одного
столбца и возвращает 0 при отсутствии совпавших строк.

Проверка на локальной БД 27.10.2026: отдельные группировки –
2129,11 → 93,27 мс; общая – 2099,19 → 44,14 мс. Все варианты совпали
по EXCEPT ALL. Это примерно 47,6-кратное ускорение второго сравнения,
не гарантия для других запросов и окружений. Протокол сохранён в
`artifacts/composite-distinct-check/`.

```powershell
.venv\Scripts\python.exe scripts/check_shared_aggregates.py --example examples/aviation-composite-distinct-rewrite.sql --output artifacts/composite-distinct-check
```

## Проверенные примеры logistics

Это интерактивная диагностика, не обучение и не подбор по запечатанным метрикам.
Таблицы/данные не изменялись; пробный индекс удалён откатом.
Исторический локальный результат (одноразовый скрипт заменён общим
`python -m pqo.optimization_control`; прежняя версия доступна в истории Git):
`artifacts/rewrite-preview-verification/examples.json`.

- `examples/logistics-index-check.sql`: фильтр facility_id=17, event_type=exception,
  ORDER BY event_time DESC LIMIT 200. Подтверждён индекс
  `(facility_id, event_type, event_time)`, медиана 30,20 → 0,041 мс,
  размер около 5,14 МиБ, построение около 1,07 с. Проверка доказывает ускорение
  только текущего чтения, не отсутствие цены записи. Для приложения установите
  порог рекомендации 5 мс вместо 50 мс; стандартная минимальная экономия 5 мс
  и 5% этому примеру не мешает.
- `examples/logistics-rewrite-check.sql`: коррелированная проверка количества
  tracking_events у 50 shipments. COUNT(*) > 0 → EXISTS, медианы
  2250,91 → 263,46 мс, совпадение мультимножеств подтверждено.

Время зависит от оборудования, кэша, нагрузки и уже имеющихся индексов.
Если индекс уже применён пользователем, повторное предложение не ожидается.
Демонстрация использовала существующие таблицы на 750 000 событий и 150 000 отправлений.

## Перспектива обучаемого переписывания

XGBoost остаётся моделью времени; одиночная и последовательная DQN — модели
индексных действий. Генератор переписываний сейчас основан на правилах.
Следующее расширение может ранжировать кандидатов по обученным оценкам или
использовать нейросеть для предложения SQL, но не обходить проверку результатов
и фактического выигрыша. Нужны отдельные обучающие пары и отложенные семейства:
SQL, схема/план, вариант, результат проверки и реальные времена.

Работа [E3-Rewrite](https://arxiv.org/abs/2508.09023) исследует LLM-генерацию
с проверками исполнимости, эквивалентности и эффективности; она также отмечает
риск неэквивалентных и замедляющих переписываний. Такой генератор в этой версии
не подключён; SQL пользователя никуда не отправляется.

Проверка готового приложения: `--rewrite-smoke-test` проходит сравнение равных
результатов и отказ при изменении числа дубликатов через настоящие фоновые
задачи и обновления интерфейса.
