# Типизированные параметры транзакций — 0.8.31

## Область поддержки

Параметры PostgreSQL `$1`, `$2`, … принимаются только как значения выражений.
Привязка отдельна для каждой команды: `$1` в SELECT №1 и `$1` в UPDATE №3
не обязаны иметь одинаковый тип/значение. Повторное использование `$1`
внутри одной команды получает одно и то же значение. Нумерация в каждой
команде начинается с 1 без пропусков, максимум `$64`, суммарно до 128 строк
параметров. Имена таблиц/столбцов параметризовать нельзя.

Поддерживаемые типы: integer, bigint, numeric, double precision, boolean,
text, date, timestamp, timestamptz, uuid. Тип всегда выбирает пользователь,
в том числе при явном `::тип` в исходном SQL. Неизвестные типы, типовые
параметры precision/scale, массивы, `:name`, `?` и передачу сериализованного
SQL эта версия не принимает.

Результат — один локально материализованный сценарий значений, не серверный
PREPARE и не воспроизведение плана приложения с production. PostgreSQL
различает generic-планы и custom-планы конкретных параметров; literal-сценарий
не доказывает, какой план выберет prepared-запрос другой сессии.
[Документация PostgreSQL PREPARE](https://www.postgresql.org/docs/17/sql-prepare.html).

## Интерфейс и пример

1. Основное подключение: `pqo_university_unseen`, разрешённая схема `university`.
2. На вкладке «Транзакции» открыть `examples/transactions/university-parameters.sql`
   и выполнить локальный разбор. Запроса к БД на этом шаге нет.
3. Открыть «Параметры SQL» и явно заполнить строки:

| Команда | Параметр | Тип | Значение |
| --- | --- | --- | --- |
| 1 | $1 | integer | 17001 |
| 1 | $2 | integer | 50 |
| 2 | $1 | integer | 350 |
| 2 | $2 | integer | 200 |
| 3 | $1 | text | completed |
| 3 | $2 | integer | 17001 |
| 3 | $3 | integer | 350 |

4. Нажать «Применить параметры локально». Справа появится отдельный SQL со
   значениями/явными типами, слева останется исходник с `$1`, `$2`, ….
   Планы/кандидаты/индексы на этом шаге не запрашиваются и не создаются.
5. Получить оценочные планы, затем собрать кандидатов. Для пробы пары отметить
   `enrollments(student_id, registered_at)` и `enrollments(offering_id, registered_at)`
   без INCLUDE, указать `pqo_university_index_lab` и подтвердить отдельную копию.
6. Выполнить одиночную пробу либо сравнение. В них измеряется только SELECT
   со значениями; UPDATE №3 по-прежнему не выполняется.

Кнопка планирования недоступна до явного заполнения/применения параметров.
Пустое значение **text** означает пустую строку, не NULL. Для NULL нужно
отметить отдельный флажок; поле значения очищается и отключается, тип остаётся
обязательным. SQL-кавычки вокруг текста вводить не нужно: они стали бы частью
самого значения.

Изменение типа, значения или NULL сбрасывает привязку, планы, кандидатов и
результаты одиночных/групповых проб. Даже запоздалый ответ фонового потока для
прежнего значения не восстанавливает результат. Исходный SQL остаётся тем же,
но снимок явных значений уже другой. При редактировании исходника вся таблица
параметров очищается. Смена подключения сбрасывает планы/пробы; явно введённые
значения можно повторно использовать после проверки пользователем.

## Форматы и пределы значений

- integer/bigint: целые десятичные числа в диапазоне выбранного типа;
- numeric: конечное число с точкой/десятичной экспонентой, до 1000 значащих
  цифр и модуля экспоненты 1000, без разделителей разрядов;
- double precision: конечное представимое число, без переполнения и
  округления ненулевого ввода до нуля из-за экстремального underflow;
- boolean: `true` или `false`;
- text: исходный текст, включая пробелы/кавычки/Unicode;
- date: `YYYY-MM-DD`, корректная календарная дата;
- timestamp: `YYYY-MM-DD HH:MM:SS` (или `T`), необязательные 1–6 знаков
  дробных секунд, без часового пояса;
- timestamptz: тот же формат с обязательным `Z` или `±HH:MM`, поддерживаемый
  сдвиг не более 14 часов; часовой пояс компьютера не подставляется;
- uuid: корректный UUID, нормализуемый в стандартную запись.

В одном значении не более 4000 символов, NUL и некорректный Unicode запрещены.
Материализованный SQL также ограничен общим лимитом 500000 символов.
Ошибки локальной валидации указывают номер команды/параметра, но не повторяют
само введённое значение. Параметр в комментарии или строковом/dollar-quoted
литерале не подменяется.

## Способ привязки и безопасность

Параметры заменяются только в AST. Значение становится литералом с явным
CAST в закрытый набор типов `pg_catalog`, тип не принимается как произвольный
SQL. После генерации текст повторно разбирается: количество/вид команд,
признаки записи и физические отношения должны остаться прежними, неразрешённых
параметров остаться не должно. CAST сохраняется даже для integer в ORDER BY,
чтобы значение `$1` не превратилось в позиционный номер выходного столбца.

Все пути получения планов/проб фиксируют `standard_conforming_strings=on`.
Текст с кавычками/обратными слешами остаётся одним значением; содержимое
параметров не рассматривается как дополнительная SQL-команда. Это не разрешение
на запуск недоверенного исходного SQL или функций/операторов/расширений БД.
Ограничения [получения планов](transaction-roadmap.md),
[проб на копии](transaction-index-trials.md) и [сравнения пар](transaction-index-comparison.md)
сохраняются. DML, исходные BEGIN/COMMIT и сессионные команды не воспроизводятся.

Значения/материализованный SQL живут только в памяти текущего анализа,
не сохраняются в настройки, историю или обучающие данные. Просмотр справа
может содержать чувствительные значения; не публикуйте его без проверки.
Диагностические журналы ошибок GUI/СУБД могут содержать фрагменты SQL: перед
передачей проверяйте их вручную. Успешный opt-in параметрический smoke-тест
не записывает сами параметры и текст исходника.

## Проверка

```powershell
$env:PQO_UNIVERSITY_TESTS='1'
$env:PQO_TRANSACTION_TRIAL_TESTS='1'
.venv\Scripts\python.exe -B -m unittest discover -s tests -p 'test_transaction*.py' -q
```

Проверяются отдельность `$1` разных команд, повторения, все типы и NULL,
отсутствующие/лишние/дублирующие параметры, пропуски, границы, injection-подобный
текст, кавычки, обратные слеши, Unicode, ORDER BY, привязка кандидатов, передача
сценария во все фоновые операции, сброс и отклонение устаревших ответов.
Реальный PostgreSQL возвращает текстовые значения без изменений; оценочные
планы и проба двух индексов не меняют строки/каталог индексов учебной копии.

Опт-ин проверка установленного приложения:

```powershell
$env:PQO_TRIAL_COPY_CONFIRMED='1'
$env:PQO_TRIAL_COPY_DATABASE='pqo_university_index_lab'
PredictiveQueryOptimization.exe --transaction-parameters-smoke-test
```

Тест заполняет семь значений **заданного учебного примера**, получает три
оценочных плана, реально измеряет два SELECT с двумя временными индексами на
копии и проверяет откат/сброс устаревших значений. Это отдельный тестовый режим,
не автоматические значения для запросов пользователя. Наличие ускорения не
обязательно: оно зависит от текущей нагрузки. UPDATE не выполняется.

## Протокол проверки 31.10.2026

Общий набор: 521 тест, 471 пройден, 50 opt-in проверок пропущены. После
последнего уточнения сообщений интерфейса повторно пройдены все 89 проверок
транзакционного блока с обеими переменными окружения, включая десять реальных
проверок PostgreSQL. Отдельная проверка значений также сравнивает результат
всех поддержанных типов с ожидаемыми Python-значениями, включая временной сдвиг.

Установлена 0.8.31, установщик завершился с exit 0, установленный EXE совпал
со сборкой. Установленный EXE прошёл шесть проверок, везде exit 0:
`--smoke-test`, `--transaction-smoke-test`, `--transaction-trial-smoke-test`,
`--transaction-comparison-smoke-test`, `--transaction-parameters-smoke-test`,
`--rewrite-smoke-test`.

Параметрический сценарий применил семь явно заданных значений учебного примера,
получил три оценочных плана, использовал оба временных индекса в SELECT-пробе
на копии и подтвердил их отсутствие после отката. UPDATE был пропущен.
Изменение первого значения сбросило результаты; запоздалый план прежнего
сценария не восстановился. Исходный редактор сохранил `$1`, `$2`, ….

В исходной БД и копии после проверок: 40000 students, 400 courses, 2000
offerings, 240000 enrollments, 720000 submissions. Пробных `pqo_tx_trial_*`
не осталось. Интеграционные тесты сравнивают также строки и DDL индексов.
Настройки подключения, моделей и порогов до/после совпали, пароли в снимки
не включались. Рабочая история и калибровка не пополнялись: тестовые запуски
использовали отдельные `PQO_APP_DATA_ROOT`.
