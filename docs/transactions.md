# Анализ и проверка транзакций

Вкладка «Транзакции» разделяет локальный разбор, оценочные планы, структурные
кандидаты и фактические проверки. Эти действия имеют разные границы: полученный
план или ускорение SELECT сами по себе не подтверждают пользу для всей транзакции.

## Разбор, планы и параметры

1. Откройте SQL-файл или вставьте один блок BEGIN … COMMIT/ROLLBACK.
2. Выполните локальный разбор: он не подключается к БД и не запускает команды.
3. Для `$1`, `$2`, … заполните «Параметры SQL» и примените их локально.
4. Отдельно запросите оценочные планы и соберите общие индексные кандидаты.

Планы получаются через EXPLAIN без ANALYZE и относятся к исходному состоянию БД:
последующий SELECT на этом этапе не видит UPDATE из текста транзакции.
Стоимость плана не является временем в миллисекундах.

Параметры задаются отдельно для каждой команды, начиная с `$1` без пропусков,
до `$64`; всего до 128 строк параметров. Поддерживаются integer, bigint, numeric,
double precision, boolean, text, date, timestamp, timestamptz и uuid. NULL задаётся
отдельным флажком, пустая строка text остаётся пустой строкой. Имена объектов
параметризовать нельзя. Значения материализуются как типизированные литералы;
это не серверный PREPARE и не проверка generic-плана другой сессии.

Изменение SQL, параметров или подключения сбрасывает устаревшие результаты.
Значения параметров и текст транзакции автоматически не сохраняются в обучение.

## Проверка чтений на отдельной копии

Пользователь указывает заранее подготовленную тестовую БД на том же сервере.
Проба выполняет только допустимые самостоятельные SELECT; DML и изменяющие CTE
пропускаются. Перед B создаётся индекс, сравниваются A1/B/A2, затем индекс
откатывается и его отсутствие проверяется отдельным подключением.

Можно проверить один индекс или отметить до трёх кандидатов для сравнения
одиночных вариантов и пар. Все индексы пары должны использоваться; проверенная
пара не выбирается вместо одиночного без дополнительного выигрыша.

«Повторы SELECT» — заданные пользователем веса 1–10000, а не измеренная частота.
Результат — взвешенная сумма медиан чтений, не время транзакции. Контроль нового
набора SELECT проверяет уже зафиксированный вариант, не подбирает победителя
заново. Положительный ручной контроль не исправляет неустойчивый исходный подбор.

«Запись и индексы» отдельно оценивает пересечения ключей/INCLUDE с командами
записи. Показатель `повторы × предполагаемые строки × число новых индексов`
измеряется в «строка × индекс», а не в миллисекундах или байтах WAL. Пустое число
строк означает неизвестность; триггеры и каскады не превращаются в нулевую цену.

## Последовательное выполнение с записью

Для измерения всей нагрузки нужен отдельный лабораторный эталон и явное
разрешение на DML/COMMIT, создание и удаление одноразовых БД. Требуются CREATEDB
и право клонировать эталон. Источник и эталон не получают пользовательские DML.

Сначала создаётся закрытая копия эталона. Из неё для каждой серии создаются
свежие A1, B и A2. В A1/A2 выполняется исходная транзакция; в B — та же
транзакция с выбранными 1–2 индексами. Команды выполняются один раз в исходном
порядке, поэтому чтение видит предыдущую запись. После COMMIT сверяются данные.
Две серии требуют закрытого снимка и шести рабочих копий.

Проверяются одинаковые начальные состояния, каждый результат SELECT/RETURNING,
число затронутых строк и итоговые данные всех разрешённых таблиц. ORDER BY
сравнивается как последовательность, остальные результаты — как мультимножества
с сохранением NULL, типов и дубликатов. Это проверка конкретного состояния БД,
не доказательство для всех возможных данных.

Время BEGIN–COMMIT включает выполнение, получение результатов и контрольные
операции. Клонирование, полные снимки таблиц и построение индексов учитываются
отдельно. Одинаковые данные не означают одинаковый физический кэш или конкуренцию.

## Поддерживаемый контракт выполнения

| Ограничение | Значение |
| --- | --- |
| SQL | bare BEGIN … COMMIT, 2–20 команд, до 50000 символов |
| Состав | хотя бы один SELECT и одна команда INSERT/UPDATE/DELETE |
| Таблицы | одна физическая таблица в команде, явная разрешённая схема |
| Запись | INSERT VALUES с явными столбцами, до 100 строк; UPDATE/DELETE с WHERE |
| Каталоги | 1–8 постоянных heap-таблиц с PK и поддерживаемыми встроенными типами |
| Размер | эталон до 256 МиБ; снимок до 2 млн строк и 256 МиБ |
| Результат команды | до 10000 строк и 8 МиБ контрольного представления |
| Проверка | 1–3 серии; общий бюджет 300 с, statement до 30 с, lock timeout 1 с |
| Новые индексы | до двух, суммарно до 64 МиБ |

Не исполняются произвольные JOIN/CTE/подзапросы, неизвестные функции,
недетерминированные выражения, DEFAULT/ON CONFLICT, MERGE, SELECT INTO,
блокировки, SET, savepoint и ROLLBACK-сценарии. ROLLBACK не превращается в COMMIT.

В проверяемых схемах исключены identity/последовательности, DEFAULT и
генерируемые столбцы, пользовательские типы/collation, RLS, секции/наследование,
правила, активные пользовательские триггеры, CHECK/исключения, каскадные/внешние
FK и нестандартные индексы. Допускаются обычные PK/UNIQUE и внутренние FK
NO ACTION/RESTRICT. Расширения кроме plpgsql, event triggers и подписки блокируют
режим. Полные проверки заданы в [transaction_replay_guard.py](../src/pqo/transaction_replay_guard.py).
Это ограниченный исполнитель для доверенной тестовой БД, не SQL-песочница.

## Итог для всей нагрузки

По умолчанию нужны две полные серии. В каждой серии общий выигрыш должен
достигать одновременно 5 мс и 5%; пороги фиксируются до запуска. Дополнительно:

- регрессия SELECT, DML или любой команды более 2 мс и 10% блокирует рекомендацию;
- дрейф A1/A2 или между сериями более 2 мс и 20% означает недостаточную надёжность;
- размер индексов до и после записи должен укладываться в заданный бюджет;
- результаты, состояния и очистка должны быть полностью подтверждены.

`recommended` означает прохождение всех условий для измеренного сценария;
`not_recommended` — измеренный отказ по эффекту или размеру; `inconclusive` —
недостаточные/нестабильные данные, ошибка, отмена либо неподтверждённая очистка.
Одна серия диагностическая. Успешный код завершения CLI не обязательно означает
положительную рекомендацию. Постоянного применения к исходной БД в этом режиме нет.

## Замена отдельного SELECT

В разделе «Переписывание SELECT» подготовьте варианты без подключения, выберите
команду и отредактируйте замену справа. «Показать замену и порядок команд»
показывает транзакцию с единственной заменой, не выполняя её.

Допускаются одиночные OR→IN, диапазон→BETWEEN, удаление внутреннего ORDER BY
без LIMIT/OFFSET и перенос допустимого HAVING. Только этот режим дополнительно
разрешает один SELECT в FROM под внешней агрегацией, с двумя уровнями SELECT
и одной физической таблицей. JOIN, CTE, произвольные подзапросы и изменения DML
не становятся допустимыми.

Ручной вариант должен быть одним SELECT, сохранять физическую таблицу, внешние
ORDER BY и LIMIT. Остальные команды и их порядок остаются прежними. В A1/A2
исполняется оригинал, в B — транзакция с заменой; новых индексов не создаётся.
Сверяются все промежуточные результаты и конечные данные, затем общий эффект
по той же политике. Проверка SELECT до записей не заменяет эту проверку контекста.

## Отмена и очистка

Удаляются только копии, созданные текущим вызовом, с подтверждёнными именем,
OID и владельцем. Принудительное завершение чужих подключений, FORCE и удаление
по маске не используются. Обычная отмена дожидается очистки; CREATE может ждать
своего тайм-аута до 30 с.

Журнал `artifacts/disposable-recovery` хранит владение копиями без SQL и строк.
После аварийного завершения оставшиеся БД сверяются с журналом вручную:
автоматического удаления по старому журналу нет. Неподтверждённая очистка
блокирует положительный итог.

Примеры находятся в [examples/transactions](../examples/transactions).
Подготовка стенда и повторяемая приёмка — в [testing.md](testing.md).
