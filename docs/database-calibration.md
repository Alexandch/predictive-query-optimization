# Калибровка прогноза для пользовательской базы данных

## Назначение

Основная XGBoost-модель переносит закономерности между разными структурами SQL,
но абсолютное время зависит от оборудования, объёма данных, настроек PostgreSQL и
состояния кэша. Калибровочный профиль корректирует масштаб прогноза для конкретной
БД без изменения и дообучения основной модели.

Профиль привязан к двум идентификаторам:

- адресу `host:port/database` без имени пользователя и пароля;
- SHA-256 файла XGBoost-модели.

Поэтому профиль нельзя случайно применить к другой БД или новой версии модели.
Он хранится локально в каталоге данных приложения и не загружается в PostgreSQL.

## Калибровка в приложении

1. На вкладке «Настройки» подключите пользовательскую PostgreSQL и укажите
   разрешённые схемы.
2. На вкладке «Анализ» вставьте характерный для этой БД `SELECT` или `WITH`.
3. Нажмите «Добавить текущий SQL в калибровку» и подтвердите выполнение.
4. Повторите минимум для десяти разных запросов. Практически рекомендуется 10–30
   запросов разной длительности и структуры.
5. После проверки выборки включите флажок «Использовать калибровку этой БД».

Кнопка калибровки выполняет `EXPLAIN ANALYZE`, то есть запрос реально запускается.
Допускается только один read-only `SELECT`/`WITH`; транзакция переводится в режим
read-only, а время ограничивается `statement_timeout` из настроек подключения.
Не используйте для калибровки намеренно тяжёлые запросы без подходящего таймаута.

Обычная кнопка «Анализировать» выполняет только `EXPLAIN` без `ANALYZE` и поэтому
не запускает пользовательский запрос. После активации профиль меняет только
числовой прогноз времени; DQN-рекомендация по индексу продолжает анализировать
оценочный план и структуру SQL.

## Алгоритм

Для каждого SQL сохраняются базовый прогноз и фактическое `Actual Total Time`.
Поправочный коэффициент вычисляется как взвешенная медиана отношений
`(факт + 1) / (прогноз + 1)`. Повторы одного SQL сначала агрегируются медианой,
а вес запроса пропорционален его базовому прогнозу. Поэтому короткие запросы не
могут подавить более существенную ошибку в миллисекундах на долгих запросах.
Коэффициент ограничен диапазоном от `0,05` до `20`, а профиль применяется только
после десяти разных SQL и явного включения пользователем в приложении.

Отображаемые в профиле MAE рассчитаны на самих калибровочных наблюдениях и не
являются независимой оценкой качества. Для отчёта о качестве следует отдельно
проверить профиль на запросах, которые не участвовали в калибровке.

## Командная строка

Добавить измерение:

```powershell
.\.venv\Scripts\pqo-calibrate.exe add `
  models\xgboost\xgboost_query_time.joblib `
  artifacts\calibration\my_database.json `
  "SELECT * FROM public.orders WHERE customer_id = 100"
```

Посмотреть профиль:

```powershell
.\.venv\Scripts\pqo-calibrate.exe status `
  artifacts\calibration\my_database.json
```

Применить его при безопасном прогнозе или полном анализе:

```powershell
.\.venv\Scripts\pqo-predict.exe `
  models\xgboost\xgboost_query_time.joblib `
  "SELECT * FROM public.orders WHERE customer_id = 200" `
  --calibration artifacts\calibration\my_database.json

.\.venv\Scripts\pqo-analyze.exe `
  models\xgboost\xgboost_query_time.joblib `
  models\dqn\dqn_index_advisor.pt `
  "SELECT * FROM public.orders WHERE customer_id = 200" `
  --calibration artifacts\calibration\my_database.json --no-persist
```

Для CLI параметры подключения задаются переменными `POSTGRES_HOST`,
`POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и
`PQO_ALLOWED_SCHEMAS`.

## Раздельная оценка

Для CSV, ранее собранного через `pqo-collect`, можно автоматически отделить
калибровочные SQL от проверочных и сформировать JSON/CSV-отчёт:

```powershell
.\.venv\Scripts\pqo-calibrate.exe experiment `
  dataset\postgresql\production_control.csv `
  models\xgboost\xgboost_query_time.joblib `
  artifacts\calibration\evaluation `
  --calibration-fraction 0.20 --seed 1701 --split-mode parameter
```

Режим `parameter` оставляет разные SQL каждого структурного шаблона в обеих
частях и проверяет типичный сценарий репрезентативной калибровки. Более строгий
`unseen-template` целиком удерживает новые структуры в holdout и показывает,
можно ли переносить один глобальный коэффициент на неизвестные классы запросов.
В обоих случаях пересечение точных SQL запрещено.
