# Калибровка прогноза для пользовательской базы данных

## Назначение

Основная XGBoost-модель переносит закономерности между разными структурами SQL,
но абсолютное время зависит от оборудования, объёма данных, настроек PostgreSQL и
состояния кэша. Калибровочный профиль корректирует масштаб прогноза для конкретной
БД без изменения и дообучения основной модели.

Профиль привязан к двум идентификаторам:

- адресу `host:port/database` без имени пользователя и пароля;
- SHA-256 файла XGBoost-модели.

Поэтому профиль нельзя случайно применить к другой БД или новой версии модели.
Он хранится локально в каталоге данных приложения и не загружается в PostgreSQL.

## Калибровка в приложении

1. На вкладке «Настройки» подключите пользовательскую PostgreSQL и укажите
   разрешённые схемы.
2. На вкладке «Анализ» вставьте характерный для этой БД `SELECT` или `WITH`.
3. Нажмите «Анализировать и измерить». Профиль создастся и применится сам.
4. Для точного SQL достаточно первого устойчивого набора из пяти замеров. Чтобы
   улучшать перенос на похожие запросы, проанализируйте 10–30 разных характерных
   запросов или используйте предварительную калибровку по файлу.

Обычный анализ выполняет `EXPLAIN ANALYZE`, то есть запрос реально запускается.
Сначала выполняется один прогревочный запуск, который отбрасывается, затем пять
измерений. В профиль записываются их медиана, минимум и максимум. Допускается
только один read-only `SELECT`/`WITH`; транзакция переводится в режим read-only,
а каждый запуск ограничивается `statement_timeout` из настроек подключения.
Не используйте для калибровки намеренно тяжёлые запросы без подходящего таймаута.

Ручного переключателя калибровки нет. DQN-рекомендация по индексу продолжает
анализировать оценочный план и структуру SQL, а порог её запуска проверяется по
адаптивному времени текущей БД.

## Алгоритм

Для каждого SQL сохраняются базовый прогноз, фактическое `Actual Total Time`,
диапазон пяти измерений, группа запроса и отпечаток структуры SQL без конкретных
значений литералов.
Группа учитывает число `JOIN`, наличие подзапросов, агрегации, сортировки и
диапазон базового прогноза: менее 100 мс, 100–999 мс или от 1000 мс.

Если точный SQL имеет устойчивую сессию из пяти замеров, она применяется сразу.
При накоплении сессий используется медиана до трёх последних. Это позволяет учитывать текущее прогретое состояние
конкретной БД без переноса поправки на остальные запросы. Внутри группы поправка
вычисляется как взвешенная медиана отношений
`(факт + 1) / (прогноз + 1)`. Повторы одного SQL сначала агрегируются медианой,
а вес запроса пропорционален его базовому прогнозу. Группа активируется после
трёх разных SQL, причём её коэффициент стягивается к `1,0` при малом числе
наблюдений. Поправка применяется только тогда, когда нормализованный шаблон SQL
уже встречался в профиле. Если шаблон новый или подходящая группа ещё не набрала
три SQL, прогноз остаётся без поправки: потенциально опасный перенос коэффициента
на незнакомую структуру не выполняется.

Общая групповая часть профиля становится готова после десяти разных SQL и
применяется только при значимом улучшении. Точечная часть для уже измеренного SQL
активна сразу. Уменьшение общей MAE считается значимым,
только если выигрыш составляет не менее 0,5 мс и 2%. Старые профили читаются, но наблюдения без
сохранённой группы и отпечатка структуры не активируют условную поправку; их
можно постепенно дополнить.

Отображаемые в профиле MAE рассчитаны на самих калибровочных наблюдениях и не
являются независимой оценкой качества. Для отчёта о качестве следует отдельно
проверить профиль на запросах, которые не участвовали в калибровке.

## Командная строка

Добавить измерение:

```powershell
.\.venv\Scripts\pqo-calibrate.exe add `
  models\xgboost\xgboost_query_time.joblib `
  artifacts\calibration\my_database.json `
  "SELECT * FROM public.orders WHERE customer_id = 100"
```

Посмотреть профиль:

```powershell
.\.venv\Scripts\pqo-calibrate.exe status `
  artifacts\calibration\my_database.json
```

Применить его при безопасном прогнозе или полном анализе:

```powershell
.\.venv\Scripts\pqo-predict.exe `
  models\xgboost\xgboost_query_time.joblib `
  "SELECT * FROM public.orders WHERE customer_id = 200" `
  --calibration artifacts\calibration\my_database.json

.\.venv\Scripts\pqo-analyze.exe `
  models\xgboost\xgboost_query_time.joblib `
  models\dqn\dqn_index_advisor.pt `
  "SELECT * FROM public.orders WHERE customer_id = 200" `
  --calibration artifacts\calibration\my_database.json --no-persist
```

Для CLI параметры подключения задаются переменными `POSTGRES_HOST`,
`POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и
`PQO_ALLOWED_SCHEMAS`.

## Раздельная оценка

Для CSV, ранее собранного через `pqo-collect`, можно автоматически отделить
калибровочные SQL от проверочных и сформировать JSON/CSV-отчёт:

```powershell
.\.venv\Scripts\pqo-calibrate.exe experiment `
  dataset\postgresql\production_control.csv `
  models\xgboost\xgboost_query_time.joblib `
  artifacts\calibration\evaluation `
  --calibration-fraction 0.20 --seed 1701 --split-mode parameter
```

Режим `parameter` оставляет разные SQL каждого структурного шаблона в обеих
частях и проверяет типичный сценарий репрезентативной калибровки. Более строгий
`unseen-template` целиком удерживает новые структуры в holdout и проверяет
перенос условных коэффициентов на неизвестные шаблоны. В обоих случаях
пересечение точных SQL запрещено.

Для устойчивой оценки по нескольким разбиениям:

```powershell
.\.venv\Scripts\pqo-calibrate.exe cross-validate `
  dataset\postgresql\production_control.csv `
  models\xgboost\xgboost_query_time.joblib `
  artifacts\calibration\cross_validation `
  --runs 20 --seed-start 1 --split-mode both
```

Команда отдельно сообщает среднее, стандартное отклонение, минимум, максимум и
долю улучшившихся разбиений. Режим проходит критерий устойчивости, если средние
MAE и RMSE улучшились и каждая метрика выиграла минимум в 70% запусков.
