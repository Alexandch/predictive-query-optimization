# Контроль выбора между несколькими переписываниями

23.10.2026. Результат: **ранжировщик не допущен к активации**.
Установленная версия 0.8.23 и модель прогноза времени не менялись.

## Зачем отдельная проверка

Первый XGBoost-кандидат уменьшил MAE оценки относительного ускорения отдельных
переписываний. Это не доказывало, что он выберет лучший вариант одного SQL.
В этой проверке модель заморожена: без дообучения и подбора параметров.

SHA-256 модели:
`ccc874b3f7d2810bf2b39de17a6c4aa650f70721723a2a9847b251892859e351`.
Хэш обучающей выборки:
`8340ff567f507d92a5083f101a91156b122f897bff41ff80d09fe1bea96ec16f`.

Перед выполнением пересоздаётся аудит исходного журнала и проверяется совпадение
хэша выборки с артефактом. Используются только 19 ранее отложенных FK-семейств,
не участвовавших в fit. Проверяются отсутствие пересечения семейств и точных
нормализованных форм исходных/переписанных SQL с development-данными.

Это новые составные формы на прежних контрольных связях, не новая БД и не
полностью независимый новый контроль: эти связи уже использовались в проверке
точечной ошибки. После просмотра данного результата он остаётся диагностическим;
его нельзя незаметно превратить в обучающую выборку или снова назвать свежим
финальным контролем после настройки модели.

## Сценарии

По три SQL на каждое семейство, всего 57 запросов и 152 кандидата:

1. Коррелированный COUNT в проекции и включительный диапазон: два кандидата.
2. DISTINCT над INNER JOIN, OR-равенства и диапазон: три кандидата.
3. Внутренний ORDER BY перед группировкой, диапазон и HAVING: три кандидата.

Полный список фиксируется перед измерениями. Каждый кандидат проверен через
EXCEPT ALL на read-only REPEATABLE READ-снимке, затем измерены три пары после
прогрева с чередованием порядка. Порог принятия — 2 мс и 5% выигрыша;
statement timeout — 1500 мс. В итоговом наборе нет неполных запросов: все
57 получили полные измерения всех своих кандидатов. Если один кандидат
не проверен/не измерен, весь запрос исключается из сравнения oracle, а не
получает вымышленное нулевое время для неудачного варианта.

Интеграционные тесты БД запускаются после завершения сбора. Последующие
`--resume` только пересчитывали отчёт из сохранённых записей, без новых замеров
и без изменения модели.

## Политики при бюджете одной проверки кандидата

- Модель: максимальный предсказанный log-speedup, если он больше log(1,05),
  иначе ничего не менять.
- Порядок генератора: проверить первый сгенерированный вариант.
- Стоимость плана: максимум log(cost исходного / cost варианта), если он
  положителен, иначе ничего не менять.
- NOOP: исходный SQL без попытки переписывания.

Решения модели и стоимости используют только AST и оценочный EXPLAIN.
Фактические времена не участвуют в вычислении баллов.
После выбора каждой политике разрешена одна проверка кандидата, а не один
SQL-вызов: проверка включает сравнение результатов и повторные измерения.
Если выбранный кандидат не проходит пороги, остаётся исходный SQL.
Флаг accepted перепроверяется по сырым временам и фиксированным порогам.

В эксперименте измерялись **все** кандидаты, чтобы построить oracle; бюджет
одной проверки оценивается офлайн по этим результатам, не живым запуском
разных политик. Новый порядок выполнения и его влияние на кэш не измерялись.

Oracle — лучший из фактически принятых кандидатов или исходный SQL. Полезный
вариант нашёлся у 11 из 57 запросов. Log-regret — разность между log-speedup
oracle и выбранного применимого варианта; меньше лучше. Это не миллисекунды.
Суммарный вес каждого из 19 семейств равен единице.

## Результат

| Политика | Средний log-regret | Найдено полезных вариантов |
| --- | ---: | ---: |
| XGBoost-кандидат | 0,17560 | 3 |
| Первый вариант генератора | 0,39975 | 0 |
| Оценочная стоимость плана | 0,13815 | 9 |
| Ничего не менять | 0,39975 | 0 |

Модель номинально лучше первого варианта, но по среднему regret не обошла
простую стоимость плана. 95%-й bootstrap-интервал разности regret модели
и стоимости по целым семействам: [-0,23781; 0,29382], то есть включает ноль.
Превосходство модели не подтверждено. По сравнению с генератором и NOOP
интервал [-0,55548; 0,0] также не проходит строгую проверку верхней границы.

Метрика совпадения полезности с oracle для модели — 85,96%, но её нельзя
выдавать за «точность выбора лучшего SQL»: 46 запросов не имели принятого
варианта, и у них исходный SQL — правильный выбор для всех политик. Число
действительно найденных ускорений (3 против 9) здесь информативнее.

Gate требует не менее 10 семейств, уменьшения среднего regret минимум на 5%
относительно каждой из трёх базовых политик и отрицательной верхней границы
bootstrap-интервала разности. Итог: `passes_ranking_gate=false`,
`automatic_activation=false`. Замедляющие и непроверенные варианты не применяются.

## Инструмент и артефакты

`python -m pqo.rewrite_ranking` принимает только доверенный локальный joblib:
загрузка стороннего joblib небезопасна. Он не вызывает fit и не меняет файлы
из `models/`. Для воспроизведения используйте новый выходной каталог:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pqo.rewrite_ranking --model artifacts/rewrite-learning/expanded-experiment-20261023/candidate.joblib --training-journal artifacts/rewrite-batches/expanded-clean-20261023/journal --training-batch artifacts/rewrite-batches/expanded-clean-20261023/batch.json --output artifacts/rewrite-ranking/new-control
```

Для продолжения прежнего пакета добавьте `--resume`; SHA модели и выборки
должны совпадать. Сохранение и блокировка измерений используют общий сборщик.
При незавершённом пакете положительный итоговый gate запрещён.

Текущие артефакты находятся в `artifacts/rewrite-ranking/control-20261023`:

- `ranking-identity.json`: замороженная модель и выборка;
- `measurements/batch.json` и `measurements/journal`: SQL, протокол, все планы и времена;
- `ranking-report.json`: баллы, выбор каждого метода, полезность и итоговый gate.

Журналы содержат полный SQL, остаются локальными и не публикуются в Git.
Файлы установленного приложения не обновлялись на этом офлайн-этапе.

## Следующее развитие

Для нового кандидата нужны development-запросы с несколькими вариантами на
каждый SQL, обучение предпочтения внутри запроса и отдельная внутренняя
валидация по семействам. Возможен pairwise/listwise objective вместо одной
регрессии времени/ускорения. Сначала проверяется development-валидация, затем
заранее фиксируется новый финальный контроль. Подгонка по текущим 57 запросам
и повторное объявление их независимым контролем недопустимы.
