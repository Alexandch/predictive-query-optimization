# Обучение предпочтения вариантов внутри одного SQL

25.10.2026. Реализован отдельный XGBRanker с objective `rank:pairwise`.
Он не заменяет прогноз времени, не генерирует произвольный SQL и пока не
подключён к установленному приложению 0.8.23.

## Отличие от предыдущего кандидата

Ранее регрессор оценивал log-speedup каждого варианта отдельно. Новый кандидат
обучается на группах: исходный SQL (NOOP) и все его переписывания образуют одну
группу. Целевая релевантность — порядковое предпочтение фактически полезных
вариантов внутри группы, а не абсолютное время. Не принятые по факту варианты
и NOOP имеют одинаковую нулевую полезность; наиболее полезный принятый вариант
получает наивысший ранг. При равных модельных баллах предпочтение отдано NOOP.
Баллы ranker не являются миллисекундами или прогнозируемым процентом ускорения.

Признаки: разрешённые оценочные планы и AST обеих версий, правило, флаг NOOP
и разности численных структурных/оценочных признаков. Фактические времена,
метки принятия, идентификаторы запросов и семейства в матрицу не попадают.
Векторизатор обучается только на train; отдельные validation-поля в него
не добавляются. Суммарный вес запросов одного train-семейства равен единице.

## Зафиксированное разделение

Из прежних 50 development-семейств стабильным хэшем выделены 40 train и
10 внутренних validation-семейств. Прежние 19 контрольных связей не используются
ни в fit нового ranker, ни во внутренней валидации. Старый регрессор загружается
только для проверки происхождения и разделения данных; его веса не служат
инициализацией нового ranker.

План до измерений фиксирует параметры, подключения, семейства и SQL всех фаз.
Проверяется отсутствие пересечения исходных/переписанных форм между ролями.
Настройки единственного обученного варианта: 160 деревьев, max_depth=3,
learning_rate=0.05, random_state=42, n_jobs=1. По результатам validation
параметры не менялись и новый split не подбирался.

Для development использованы три составных сценария из предыдущей проверки
ранжирования, но на других связях таблиц: scalar aggregate + range,
DISTINCT JOIN + OR + range, внутренняя сортировка + grouping + HAVING.
Всего 150 запланированных SQL, по 2–3 кандидата. Прежние 57 контрольных SQL
в обучение не добавлялись.

Для финала заранее описаны ещё 57 SQL на 19 отложенных связях: COUNT(column)
с локальным фильтром, DISTINCT JOIN с NULL-предикатом и сочетание повторного
CTE, группировки, HAVING, сортировки и DENSE_RANK. Это новые составные формы,
не полностью новые БД. Они не выполняются до прохождения внутреннего gate.

## Сбор и качество

Read-only REPEATABLE READ, EXCEPT ALL, один прогрев и три чередующихся парных
замера. Statement timeout 1500 мс; бюджет сеанса 180 с проверяется между
случаями. Сбор продолжался из сохранённого состояния после достижения бюджета.

Один train-запрос с коррелированным COUNT по logistics.tracking_events превысил
тайм-аут исходного пробного выполнения. Он исключён целиком: не получил
нулевого времени и не включён в oracle по частично измеренным кандидатам.
Порог времени для него не повышался, не выполнялись повторы «до удачного
выигрыша». Это решение принято до fit и просмотра модельных validation-метрик.

Итого в fit вошли 119 SQL из 40 семейств; у 41 была ненулевая разница целевых
предпочтений. Валидация полная: все 30 запланированных SQL из 10 семейств,
80 кандидатов; полезный вариант присутствовал у 8 запросов. Неполная валидация
запретила бы переход к финалу. Аудит сверяет исходный SQL, список кандидатов,
роли, семейства, сырые прогоны, медианы и правила принятия.

## Внутренняя валидация

Бюджет каждой политики — проверить один выбранный кандидат, после чего
применить его только при фактическом выигрыше не менее 2 мс и 5%, иначе
сохранить исходный SQL. Все кандидаты измерялись для oracle; сравнение политик
является офлайн-replay, не живым тестом разного порядка выполнения.

| Политика | Средний log-regret | Найдено полезных вариантов |
| --- | ---: | ---: |
| Pairwise ranker | 0,00000 | 8 |
| Порядок генератора | 0,73466 | 2 |
| Оценочная стоимость | 0,39127 | 6 |
| NOOP | 0,73919 | 0 |

Ranker выбрал лучший принятый вариант во всех 8 полезных запросах данной
валидации. Это не «100% точность оптимизации»: остальные 22 не имели принятых
вариантов. Более того, модель выбрала кандидата, а не NOOP, во всех 30 случаях;
для 22 бесполезных запросов дальнейшая фактическая проверка вернула исходный
SQL. Полезный эффект явного NOOP в обучении ещё не подтверждён на практике.

Преимущество над стоимостью сконцентрировано лишь в двух дополнительных
успешных выборах. Bootstrap по 10 семействам (1000 выборок, seed=42) дал
95%-й интервал разности regret ranker и стоимости [-1,00026; 0,0]. Верхняя
граница не отрицательна. Поэтому замороженный строгий gate **не пройден**:
он требует не только среднего улучшения минимум на 5%, но и отрицательной
верхней границы относительно каждой базовой политики.

Итог: модель-кандидат обучена, `final_measurements_permitted=false`.
Фаза final проверена: она отказалась до подключения к БД; каталог `final`
не создавался. Порог достоверности не ослаблялся после просмотра результата.
Установленная система и модели из `models/` не изменены.

## Воспроизведение

Инструмент `python -m pqo.rewrite_pairwise` имеет три явные фазы. Для нового
эксперимента нужен новый каталог; загрузка joblib разрешена только из
доверенного локального источника.

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pqo.rewrite_pairwise --phase collect --output artifacts/rewrite-pairwise/new-experiment --reference-model artifacts/rewrite-learning/expanded-experiment-20261023/candidate.joblib --reference-journal artifacts/rewrite-batches/expanded-clean-20261023/journal
.\.venv\Scripts\python.exe -X utf8 -m pqo.rewrite_pairwise --phase train --output artifacts/rewrite-pairwise/new-experiment
.\.venv\Scripts\python.exe -X utf8 -m pqo.rewrite_pairwise --phase final --output artifacts/rewrite-pairwise/new-experiment
```

Для продолжения collection добавьте `--resume`; для финального сбора он также
поддерживается. После fit модель не перезаписывается. Перед разрешённым финалом
проверяются хэши плана, модели и данных, а gate validation пересчитывается.
При отрицательном gate final возвращает код 2 без SQL-вызовов.

Артефакты текущего опыта: `artifacts/rewrite-pairwise/experiment-20261025`:

- `plan.json` — зафиксированные роли, параметры и все SQL;
- `development/` — состояние и полный журнал измерений;
- `development-audit.json` — исключённый train-запрос и полнота;
- `candidate.joblib` — ranker, векторизатор и provenance;
- `validation-report.json` — метрики и конкретные выборы;
- `final-decision.json` — отказ от открытия финального контроля.
