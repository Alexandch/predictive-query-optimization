# Развивающий эксперимент: тяжёлые агрегации

22.10.2026 собрана отдельная нагрузка retail: соединение orders, customers,
addresses, order_items, payments и shipments с SUM, FILTER и COUNT DISTINCT.
Это нагрузочные запросы для прогноза времени; их суммы не следует принимать
за бизнес-отчёт, поскольку соединения дочерних потоков размножают строки.

До измерений заданы шесть семейств группировок. Четыре используются для
обучения, две оставлены для проверки, включая обычные и DISTINCT-агрегаты.
Получено 36 SQL: 24 обучающих и 12 проверочных. Каждый SQL прогрет один раз
и измерен трижды, целью служит медиана. Запечатанные logistics/CH-контроли
не читаются и не используются в обучении. Основной датасет и модель сохранены.

Запуск из корня проекта:

```powershell
.\.venv\Scripts\python.exe scripts\aggregation_development_experiment.py
# Повторить обучение по сохранённым замерам:
.\.venv\Scripts\python.exe scripts\aggregation_development_experiment.py --reuse-measurements
```

К исходным данным добавлены новые обучающие SQL; обучен XGBoost-кандидат
с прежней архитектурой, identity-целью и балансировкой шаблонов.

| Проверка | Основная модель | Кандидат |
|---|---:|---:|
| MAE, 12 новых отложенных SQL | 353,03 мс | 178,91 мс |
| Медианный Q-error на них | 1,662 | 1,342 |
| MAE, 500 существующих SQL | 10,59 мс | 10,22 мс |
| Внутренний parameter holdout MAE | 14,18 мс | 14,37 мс |
| Внутренний unseen-template MAE | 47,75 мс | 36,99 мс |

Ошибка на новой отложенной нагрузке уменьшилась на 49,3%. Проверка 500
существующих SQL — регрессионный экран, не независимый контроль: основная
модель видела эти данные. Внутренние holdout-метрики построены на различающихся
датасетах и разбиениях и не заменяют прямое сравнение на общей выборке.

Кандидат не назначен основным: существующее правило допуска требует отсутствия
ухудшения MAE/R² в обеих внутренних проверках, а parameter holdout MAE
увеличилась на 0,19 мс. Порог не изменялся ради кандидата. Для общего вывода
выборка из 12 SQL слишком мала; следующий этап — расширить отдельный
развивающий контроль и повторить парное сравнение.

Артефакты: `artifacts/aggregation-development/measurements.csv`,
`training.csv`, `candidate/`, `report.json`. Веса основной модели не заменены;
улучшение относится к экспериментальному кандидату, не к установленной модели.

## Скорость выдачи результата в 0.8.17

На пользовательском запросе logistics без выполнения SELECT, после загрузки
моделей: до изменений весь быстрый анализ занимал 529–615 мс; после изменений
прогноз готов за 132–198 мс, рекомендации завершаются за 314–391 мс.
Это три локальных запуска, не SLA и не сравнение времени выполнения SQL.
Первичная загрузка библиотек всё ещё требует времени; приложение запускает её
в фоновом потоке при открытии окна. Повторные обращения используют ограниченный
кэш моделей с проверкой изменения файла и кэш признаков SQL для кандидатов.
Прогноз и полный анализ имеют отдельные показатели длительности в строке состояния.
