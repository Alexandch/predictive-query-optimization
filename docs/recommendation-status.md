# Процедура статусов индексных рекомендаций – 0.8.38

Закрыта серверная доработка из подраздела 4.2 записки: добавлена настоящая
PostgreSQL PROCEDURE, вызываемая клиентом через CALL. Она управляет только
метаданными `pqo.index_recommendation`, не выполняет `proposed_ddl`, не создаёт
индексы и не подтверждает их пользу. Структурные советы хранятся в другой
таблице, их существующий сценарий не подменён индексными статусами.

## Контракт и атомарность

```sql
CALL pqo.set_recommendation_status(123, 'proposed', 'accepted');
```

Параметры: положительный bigint ID, ожидаемый статус, новый статус. Матрица:

- proposed → accepted либо rejected;
- accepted → applied;
- applied → reverted.

Повторные, обратные и остальные переходы запрещены. SELECT FOR UPDATE
сериализует изменения одной строки; после ожидания проверяется фактический
статус. При устаревшем ожидании клиент требует обновить историю, не повторяет
решение автоматически. На REPEATABLE READ/SERIALIZABLE возможен штатный
serialization failure; его также нельзя выдавать за успешное изменение.

SQLSTATE: 22023 – неверные входы; P0002 – отсутствующий ID; 55000 – устаревшее
ожидание; 23514 – недопустимый переход. Тайм-ауты/ошибки БД не считаются успехом.
Клиент ограничивает ожидание блокировки и восстанавливает исходные локальные
тайм-ауты после успешного CALL. При переданном подключении используются
транзакция/savepoint вызывающего кода без самостоятельного COMMIT.

Существующий триггер аудита остаётся единственным писателем
`recommendation_audit`. Процедура не дублирует запись. Новый guard-триггер
блокирует неправильные переходы и при прямом UPDATE. Статус, updated_at и
аудит участвуют в одной транзакции: внешний ROLLBACK отменяет их вместе.
SECURITY INVOKER не повышает права роли; процедура не выполняет COMMIT.
Это не замена правам PostgreSQL: владелец/администратор может изменить схему,
а INSERT с произвольным начальным статусом не является защищённым API создания.

## Установка на существующей служебной БД

Новый пустой Docker-том получает `database/init/013_recommendation_status.sql`
по обычной последовательности инициализации. Существующие тома init не повторяют.
Администратор применяет **только к служебной БД со схемой pqo** этот файл явно:

```powershell
Get-Content -Raw -Encoding UTF8 database/init/013_recommendation_status.sql |
  docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -1 -U query_optimizer -d query_optimizer
```

Параметры роли/БД должны соответствовать реальному локальному контейнеру.
При другом развёртывании выполнить файл через psql/pgAdmin в транзакции.
Повторное применение допускается; существующие рекомендации и аудит не меняются.
Без миграции чтение истории работает, попытка решения выдаёт понятное сообщение.
Автоматического DDL при открытии истории нет. Откат API/guard без удаления данных:
`database/migrations/013_recommendation_status.down.sql`.

## Пользовательский сценарий

1. Включить «Сохранять в историю pqo» на подключении со служебной схемой и
   выполнить быстрый анализ, сформировавший индексный кандидат.
2. Открыть «История», нажать «Обновить», выбрать строку. В колонке рекомендации
   отдельно показаны ID и статус кандидата.
3. Нажать «Принять индексный кандидат» либо «Отклонить индексный кандидат».
   Кнопки работают только для proposed и блокируются на время фоновой операции.
4. После конфликта/ошибки обновить историю. Смена подключения/неполные настройки
   не позволяют отправить ID старой БД в новую. CSV/JSON содержат ID и статус.

Принятие кандидата не разрешает автоматически применять непроверенный DDL.
Фактический глубокий анализ/применение управляемых индексов остаются отдельным
сценарием с проверками и собственным журналом. Ручных кнопок applied/reverted
нет: эти состояния нельзя выставлять в интерфейсе вместо фактической операции.
Процедура сама не доказывает, что индекс физически создан или удалён.

## Проверка

```powershell
.venv\Scripts\python.exe -B -m pytest tests/test_recommendation_status.py tests/test_recommendation_status_desktop.py
$env:PQO_STATUS_INTEGRATION_TESTS = '1'
.venv\Scripts\python.exe -B -m pytest tests/test_recommendation_status_postgres.py
```

Вторую команду запускать только на доверенном лабораторном сервере с CREATEDB.
Тесты создают новую пустую БД, устанавливают только служебную схему, проверяют
все 25 пар статусов, конкурентное ожидание реальной блокировки, откат аудита,
тайм-аут, READ ONLY и повторную/обратную миграцию. Затем удаляют только свою БД
по точному имени с проверкой OID/владельца, без FORCE и завершения чужих сессий;
отсутствие подтверждают новым подключением. Настроенная исходная БД не мигрируется.
