# Подготовка обучения оценки переписываний

Это следующий исследовательский этап после локального журнала в 0.8.22.
Для автоматического сбора новых опытов есть [пакетный сборщик](rewrite-batch.md).
Интерфейс и установленные модели не изменяются. Инструмент работает из
исходников, не подключается к БД и не исполняет SQL. Он пока не меняет порядок
проверки вариантов в приложении и не заменяет проверку эквивалентности.

## Что уже реализовано

- Аудит всех записей с причинами исключения. Встроенные smoke-тесты исключены,
  даже если их идентификаторы явно вписаны в manifest.
- Независимая проверка исходных измерений: завершённая проверка без ошибок,
  совпадение мультимножеств, минимум три парных прогона с чередованием порядка,
  по одному прогреву, положительное конечное время, совпадение медиан и сырых
  последовательностей. Одного флага `runtime_training_eligible` недостаточно.
- Явное разделение development/control через отдельный JSON. Исходные журналы
  не редактируются. Неприсвоенные записи не используются для обучения.
- Группирование по формам обоих SQL, включая связи «вариант стал исходным»,
  замены литералов и записи из разных БД. Пересечение ролей вызывает отказ.
  Промежуточные неприсвоенные записи тоже учитываются при поиске связей.
- Повторные измерения той же пары в том же контексте оценочных признаков
  объединяются медианой целевой величины; суммарный вес каждого семейства
  при обучении и контрольных метриках равен единице.
- Признаки структуры AST обоих SQL, идентификатор правила и разрешённые
  оценочные признаки EXPLAIN. Фактическое время, actual-планы, буферы и решение
  «принят/отклонён» в признаки не попадают.
- Экспериментальная регрессия XGBoost: цель `log(Tисходный / Tвариант)`.
  Положительная цель означает ускорение, отрицательная — замедление; оба вида
  примеров полезны. Это оценка эффективности одного кандидата, ещё не
  подтверждённый многовариантный ранжировщик.

## Аудит

Запуск из корня проекта; для каждого отчёта нужен новый путь:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pqo.rewrite_learning --directory "$env:LOCALAPPDATA\PredictiveQueryOptimization\artifacts\rewrite-journal" --report artifacts/rewrite-learning/audit-01.json
```

Можно несколько раз указать `--directory`, например добавить журнал исходников.
Точные копии одной проверки не увеличивают объём. Разные записи с одинаковым
run_id считаются конфликтом. Повреждённые файлы не мешают аудиту остальных.
`technical_candidates` означает техническую пригодность до назначения ролей,
а не число обучающих семейств. `unassigned_run_ids` помогает составить manifest.

## Явный выбор данных

Создайте отдельный файл, вписав реальные ID проверок из отчёта:

```json
{
  "development_run_ids": [],
  "control_run_ids": []
}
```

Пустые списки намеренны: инструмент не превращает пользовательские проверки
в обучение молча. Контроль нужно зафиксировать до сравнения моделей. Уже
помеченные `dataset_role=control` нельзя переназначить в development; тестовые
данные нельзя назначить ни в одну из этих ролей.

Формальный минимум — 30 независимых development-семейств и 10 контрольных.
Это только предохранитель от обучения на нескольких нажатиях, не доказательство
статистической достаточности. Нужны разные правила, структуры, размеры таблиц,
варианты с выигрышем, без выигрыша и с замедлением. Новые литералы одного SQL
не создают независимые семейства. Сходство по хэшу формы не заменяет ручной
проверки близких шаблонов, алиасов и происхождения данных. Для утверждений
о новых БД нужен дополнительный контроль с полностью отложенными БД.

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pqo.rewrite_learning --directory "$env:LOCALAPPDATA\PredictiveQueryOptimization\artifacts\rewrite-journal" --manifest artifacts/rewrite-learning/split.json --report artifacts/rewrite-learning/experiment-01.json --train-output artifacts/rewrite-learning/experiment-01
```

Если данных мало, сохраняется отчёт с `training_refused`, модель не создаётся,
код завершения — 2. Существующие пути не перезаписываются. При достаточных
данных `candidate.joblib` остаётся отдельным офлайн-артефактом, даже если качество
оказалось плохим; он содержит версию признаков и происхождение выборки.

## Как оценивается эксперимент

Контрольные данные не используются в подборе параметров. MAE вычисляется
в логарифмической шкале ускорения и сравнивается с константной и отдельной
для каждого правила оценкой, рассчитанными только по development-данным.
`beats_baselines=true` означает минимум 5% улучшения MAE над обеими базовыми
оценками. Это диагностический признак, а не разрешение активировать модель.
Не следует многократно подгонять параметры по этому контролю.

До интеграции в приложение ещё нужны отдельная валидация ранжирования нескольких
кандидатов одного запроса, проверка пользы при ограниченном бюджете измерений,
оценка неопределённости и регрессионные тесты GUI. Ни высокий точечный прогноз,
ни хороший MAE не разрешают применять SQL без EXCEPT ALL и фактической проверки.
XGBoost прогноза времени запросов и DQN индексных рекомендаций этот этап
не переобучает и не заменяет.

## Текущая проверка

Аудит 23.10.2026 обнаружил 9 записей в двух локальных журналах: 8 тестовых
и 1 технически пригодную пользовательскую проверку без назначенной роли.
Обучение на них не запускалось. Результат:
`artifacts/rewrite-learning/audit-20261023.json`.

Синтетические данные в unit-тестах проверяют только работоспособность кода,
не качество реальной модели. Полный SQL остаётся в исходном журнале; отчёт
аудита не дублирует его литералы. Храните журналы и будущие артефакты с учётом
конфиденциальности. Не загружайте чужие непроверенные joblib-файлы.
